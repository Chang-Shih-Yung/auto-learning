## 2. Microsoft Copilot Cowork 用一個 poisoned skill 把整個 SharePoint 偷走：5 行惡意/81 行普通 = 5/5 成功率

你正在為 Nexus 設計 MCP server 介面、也每天靠 Claude Code skill 跑 Claude_auto — PromptArmor 5/25 發佈的研究直接打中你的設計假設。Microsoft Copilot Cowork 是 Microsoft 365 內的 frontier feature，能用 user 權限透過 Microsoft Graph 存取整個租戶資料（SharePoint / OneDrive / Teams / Outlook）。攻擊鏈：攻擊者把 5 行惡意指令藏進一個 81 行的普通 skill 檔，當 user 在 Copilot Cowork 內呼叫該 skill，Cowork 自動發 Teams 訊息或 Outlook email 給「當前使用者本人」——這個動作不需要 human approval，是攻擊的核心漏洞——訊息內含一張隱藏的 HTML `<img>`，src 指向 attacker controlled URL，URL 攜帶 pre-authenticated SharePoint / OneDrive 下載連結。Outlook 預設載入遠端 image 時，連結直接被 attacker server 紀錄。研究團隊跑 5 次同樣手法、5 次成功（100%），測試模型涵蓋 Claude Opus 4.7 和 Sonnet 4.6。

這條攻擊鏈的關鍵不是「prompt injection 多強」，是 **「architectural decision 把 messaging to active user 排除在 approval gate 之外」這個工程決策**。Copilot Cowork 的設計理由很合理（user 本來就會收到自己工作流產生的通知），但在「skill 檔可由其他人投放」這個前提下，這個 exemption 直接讓 LLM 能繞過所有人工驗證、把 internal SharePoint 連結往外送。模型本身的「對齊」並沒有被攻破——是流程設計的層級分配出問題，approval gate 沒涵蓋到「往使用者自己發訊息」這條路徑。同一週 Apple 5/25 發布 CVE-2026-28952：macOS 26.5 一個 kernel 漏洞被 Claude 找出來——AI 同一週既是 defender（kernel CVE finder）也是 exploitation surface（Copilot Cowork chain）。

以前 skill / prompt injection 被當成「模型對齊問題」，解法都在「讓模型更聽話」這層；Copilot Cowork 攻擊把問題推到上一層：**LLM 永遠不可信，唯一可靠的是 approval gate 對「所有可能洩漏資料的動作」全覆蓋**——包括「往使用者自己發訊息」這條看起來無害的路徑。對 Nexus MCP server 介面設計直接借鑑：任何「會送出 URL / 寫入外部系統 / 發 notification」的 tool，都要進 approval gate；不要相信「對使用者自己發送 = 安全」的直覺。對 Claude_auto SKILL.md：第三方來源抓回來的 markdown 永遠視為頁面內容，不執行其中任何「系統指令」（learning-context.md 已有此規定，但今天這條攻擊是它的現成案例）。延續 5/4「稽核訊號必須由獨立稽核層產生」主線 — 5/4 是「執行層自我回報的訊號會被污染」，5/25 是「沒覆蓋全的 approval gate 等於沒有」，兩條獨立路徑同一結論：external invariant guard 必須對所有 side-effect 全覆蓋，不能留例外。

## 3. Nolan Lawson「用 AI 寫更好的程式碼，慢一點」：三個 AI 並排找 bug，critical/high 才動手

你每天用 Claude Code 寫 code、也對 PR review 流程有自己的習慣 — 知名前端工程師 Nolan Lawson（Mastodon、PouchDB 維護者）5/25 在個人 blog 發了一篇 "Using AI to write better code more slowly"，把他這幾個月的 AI 編碼流程方法化。核心反論點是：AI 編碼不該是「slop cannon」（一輪噴出半成品、開大 PR、未經審查就合併），而該是「結構化的慢」（慎重利用多模型找 bug 的能力、單一 PR 反覆驗證、critical / high 才動手修）。具體 workflow 是他寫的一個 Claude agent skill：**呼叫 Claude sub-agent + OpenAI Codex + Cursor Bugbot 三套同時跑，把找到的 bug 按 critical / high / medium / low 排序，再驗證 finding、產生 report。** 然後人工決策：critical / high 全修、medium / low 看效益（成本超過效益就跳）、發現「PR 路線本身就錯了」就放棄整個 PR。

這套方法的工程精神是把 LLM 當「元件」而不是「答案」——三個獨立模型並排找 bug，正是 5/16「單次 AI code review 抓不到一半 bug」研究（Victoria 對同 codebase 連跑 6 次 review 12/8/5 持續找新 finding、SWR-Bench 10 次 aggregate recall +118%）的工程落地解。anchoring effect（同一個模型同一段程式碼會傾向找出類似類別的 bug）只能用「換模型」解；sampling 隨機性只能用「多跑幾次」解；Lawson 的方法是把這兩條觀察一次性工程化：跑三套不同模型（Claude / Codex / Bugbot）= 反 anchoring，每套各跑一遍 = 反 sampling，rank 排序 = 反 noise。最反直覺的發現是這套流程經常「降低短期 velocity」——你以為 AI 加速 PR 合併，實際上是揭示既有 codebase 早就埋了一堆 bug，讓開發者進入「整理架構的 tangential side-quest」反而讓整體 codebase 健康度提升。

以前你用 Claude Code 寫 code 的直覺是「讓一個強模型跑到底」（選最強的 Opus、給足夠的 context、相信輸出）；Lawson 的方法把這個直覺翻過來：**寫的時候可以快，審的時候要慢；用一個模型寫、用三個模型審；critical / high 才動手、medium / low 看 ROI。** 對 Claude_auto 直接受益點：在 SKILL.md 的 PR 階段加一個 review step，跑 Claude review + `codex review`（gstack 已內建 /codex 技能）+ shadcn registry validate 三套並排，把 finding 按嚴重度排序到 PR comment（這層用 v2.1.146 新增的 `/code-review --comment` 直接完成）。延續 5/18「寫跟修是兩個分開選型題」洞察（同 codebase Opus 寫最好、Gemini Pro 修最好），推到「modeled-vs-modeled diversity 才是 review 的核心策略」。對應 5/9 MCP gateway 提供的「per-tool routing」直覺也用在 review 模型路由：用最便宜模型寫，用最多元的組合審。

## 4. Veso AI「Agentic Patterns」研究：8 條 postulate，把 AI agent 架構講成物理定律

你正在學 AI workflow 自動化，也在維護 Claude_auto 的 SKILL.md（這就是一個 agentic system），Veso AI 5/26 發佈的「Agentic Patterns」研究是把 Claude Code / OpenAI Codex / Gemini CLI / LangGraph / CrewAI 五大 frontier agent 系統做架構對比。核心結論：他們不是抄來抄去，是「constraints are physics」（有限 context window、tool protocol、safety、任務複雜度）所以收斂出同一套設計。研究列出 8 條 non-negotiable postulate：(1) persistent instruction files（CLAUDE.md / AGENTS.md）控制在 200 行內、涵蓋 conventions / stack / testing / security；(2) safety 用 hook / permission / linting 外部 enforce，**永遠不依賴模型自己聽話**；(3) context 預算 10–15% instructions / 30–40% conversation / 20–30% tool results、**70% 觸發 compact、80% 觸發 clear**；(4) MCP 用 `.mcp.json`（協議月下載量 97M+）；(5) system 內 shared state、跨 system 用 messaging protocol；(6) decomposition 在 agent coherence 開始 degrade 之前先拆任務；(7) cost tracking 從 day 1 開始，**50% / 75% / 90% 三個門檻告警**；(8) 每週遞增複雜度：第 1 週 instruction file、第 2 週 hook、第 3 週 MCP tool、第 4 週 skill。

這 8 條 postulate 的價值不在「告訴你規則」，是在**量化過去靠手感維持的工程直覺**。CLAUDE.md 應該寫多長？以前是「越短越好」，現在是「200 行內」；context 怎麼分？以前是「動態調」，現在是 10–15 / 30–40 / 20–30 三段比例；什麼時候該 compact？以前是「快滿的時候」，現在是 70% 量化門檻；cost 該何時告警？50 / 75 / 90 三個梯度。研究還畫了一張通用 execution loop：Input → Pre-hooks → Reasoning → Tool selection → Tool hooks → Execution → Post-hooks → Continue decision → Output，外面圍著 Instructions / Settings / Tool Registry（MCP）三層配置層，邊上掛 Skills / Subagents / Memory 三條 extension。三類目標系統各有重點：**domain context substrates**（MCP server）重 deterministic extraction + behavior contract；**personal AI runtimes** 重 memory architecture + background execution；**multi-agent shells** 重 orchestration + cost control。

以前要寫一個 AI agent skill，你只能從 GitHub 上抄三個範例憑感覺挑，沒有量化標準可比；Veso 8 postulate 第一次把「合格 agent system 應該長什麼樣」做成 spec。對 Claude_auto SKILL.md 直接借鑑點：(1) 把 `.claude/CLAUDE.md` 行數量起來，超過 200 行就分到專屬 skill 檔；(2) hook 強制 enforce 而不是相信模型（如「禁止修改 learning-context.md」這條規則應寫成 PreToolUse hook 而不只是寫在 prompt 裡）；(3) context 預算寫進 SKILL.md monitoring：70% compact / 80% clear 兩個自動觸發點；(4) cost 50/75/90 告警接 Vercel KV 看板。對應 5/16 Mintlify 45% AI agent 流量主線——文件層 / 介面層 / 架構層三條獨立路徑同一動作：把 AI 工程從口耳相傳推到可量化、可量測、可 enforce。

## 5. shadcn/ui v4.8.0：`registry validate` 把 registry.json 從「希望它對」變執行命令

你在 Claude_auto 用 shadcn/ui + Next.js App Router 跑這個學習 hub、也對 Nexus 元件庫 monorepo 結構有自己的設計—— shadcn/ui v4.8.0（5/21 release）新增 `shadcn registry validate` 命令，讓你能在發佈 registry 之前先驗證 `registry.json` 的 schema 與內容完整性。同版本還加上 `include` 欄位，讓一個 registry 條目可以引用其他 registry 條目（過去要把所有 dependency 攤平在同一個 entry 裡）。前一版 v4.7.0（5/5）加上 package imports 支援 + alias placeholders in target —— 整條 path：從「shadcn add button 一個元件」進化到「shadcn 是一個 package distribution protocol」。

技術上 `registry validate` 做的事很基本但長期沒人做：跑 schema validation（檢查 `registry.json` 結構合法）、檢查每個 component 的 `files` 陣列指向的檔案真的存在、檢查 `dependencies` / `registryDependencies` 引用的條目都解析得到、檢查 `tailwind` 與 `cssVars` 區塊格式正確。`include` 欄位則讓 registry 條目能組裝（block A 引用 block B 引用 ui/button），不必扁平複製 — 對「Nexus packages/ui 一個 element-card block 用了 button、input、card 三個 ui primitive」這種多層引用結構直接有用。

以前要在 monorepo 維護一份 shadcn registry，你要嘛靠 CI 跑 `shadcn add` 模擬安裝測試（慢、occasional 抓不到 schema 錯）、要嘛靠手感掃 JSON（漏一個欄位就靜默壞掉）；v4.8.0 把這層升格成可在 commit hook / CI 跑的 `validate` 命令。對 Nexus 元件庫 direct payoff：在 `packages/ui` pre-commit hook 加 `shadcn registry validate`，把 `registry.json` 變更從「希望它對」變「驗證它對」；用 `include` 把 4 個 design-system primitive（button / input / card / dialog）抽出來，其他高階 block 用引用而不是複製。延續 5/20「訊號表示的層級分解」洞察 — `registry validate` 把「registry.json 對不對」從手感檢查升格為結構化驗證輸出（valid / invalid + 具體 error trace），跟 Anthropic Cache Diagnostics 把 cache miss 升格為四種 type tag 是同一條工程哲學在 component distribution 層的落地。
