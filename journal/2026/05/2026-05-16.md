## Hermes Agent 7 天自我演化——你 Claude_auto 的 session-log + learning-context 雙檔設計剛好對應這個 trade-off

dev.to 5/16 一篇實驗報告把 5/10 你讀到的 Hermes Agent 從理論變成具體數字——作者讓 Hermes 跑「每日 AI/dev 新聞策展 → Telegram 推送」這個任務連續 7 天、零人工介入，只看 skill 檔案怎麼自己進化。**第 1 天的 skill 檔案 12 行**，內容只有「search + post Telegram」兩件事；**第 7 天變成 62 行**——多了來源去優先化（自己學會降權 TechCrunch / VentureBeat）、評分標準三維度（technical depth 0-4、novelty 0-3、relevance 0-3）、7 天去重窗口、低新聞日 fallback 門檻、Telegram 失敗告警——**5 倍的 procedural complexity**。第 1 天輸出是 6 條沒過濾的條目、第 7 天輸出是 3 條策展+去重+評分過的條目，作者自己估算每日省 30-40 分鐘人工掃讀時間。

這個實驗的真正 insight 不是「Hermes 變強了」，而是 Hermes 跟其他 agent framework 的設計分歧：LangChain / AutoGen / CrewAI 在每個 session 結束時把學到的東西鎖在 wrapper code（你下次 import 同樣的 chain、得到同樣的行為），而 Hermes 把學到的 procedure 寫進**可讀、可版控的 skill 檔案**，下次 session 從上一次的 skill 檔案出發、不從零開始。換句話說，前者把學習藏在程式碼、後者把學習推到可審計的文字檔——這跟你 Claude_auto 的 `memory/session-log.md` 開放給 Claude 自寫、`memory/learning-context.md` 鎖定不准動的雙檔設計是**同一個哲學的兩個分工**：你已經提前一步處理了 Hermes 沒處理的問題——「自我演化」必然會 drift，所以把**過程**（session-log，可演化）跟**規則**（learning-context.md，鎖定）分開兩個檔。

Before：你看 5/10 session-log 那條 Hermes 條目時可能覺得「self-improving skills 聽起來不錯但要怎麼驗證真的有改善」——這篇實驗報告給了具體 baseline（6 條 vs 3 條、12 行 vs 62 行、5× 複雜度），也暴露一個被忽略的問題：自我演化的 skill 檔可能變好（learn 出評分標準）、也可能變壞（drift 成過度保守、把好內容也刷掉），Hermes 沒有 invariant guard、純信任 agent 自我修正。After：你 Claude_auto 雙檔設計（鎖定的 `learning-context.md` 當基準線、開放的 `session-log.md` 當演化軌跡）剛好把「學習」與「規則」拆成兩層——值得做的補強是定期 review session-log 的 drift（例如評分標準有沒有不知不覺從 4 分降到 3 分、來源篩選有沒有越來越窄）、把每月一次的 retro 做成 first-class 步驟，而不是被動等發現問題才查。

## 「單次 AI code review 抓不到一半 bug」——你 /qa /review /codex 三層工作流的量化證據

dev.to 5/15 一篇文章把「為什麼 AI code review 跑一次永遠不夠」這件事用具體數字壓住了。作者 Victoria 對同一個 codebase 連跑 6 次 review：**第 1 次 12 個 issues、第 2 次又 8 個、第 3 次又 5 個、第 6 次還在找新問題**——同一個程式沒改、模型沒換、prompt 沒改，發現的問題每次不同。她引用 Semgrep 2025 研究：對同個 codebase 跑三次獨立 review 分別抓到 **3 / 6 / 11 個不同 finding**；SWR-Bench 研究進一步量化：**跑 10 次 review 並 aggregate 結果，bug detection recall 增加 118%**——換句話說，單次 review 找到的 bug **不到實際存在 bug 的一半**。

這個現象的成因不是「模型不夠強」，是三個結構性原因：(1) 每個 token 生成都帶 sampling 隨機性、temperature 不為零本質上不是 deterministic；(2) **anchoring effect**——LLM 一旦在一個 issue type 上抓到第一個 finding，會傾向繼續在同類型 finding 上挖、忽略其他類型（很像人類 reviewer 看到一個 SQL injection 就拼命找 SQL injection、漏掉旁邊的 path traversal）；(3) 大型 codebase 過長時 context compaction 會 lossy 丟細節。對應的工程解法不是「跑更多次」，是**結構性切割**：把 codebase 按功能邊界拆成 handlers / store / infrastructure 等模組、**每個模組 fresh session 跑**（new session 重置 anchoring）、給每個 session **明確 checklist**（Security / Performance / Reliability / Code Quality 四維度）、最後跑一輪只看 module 邊界的 integration pass。

Before：你 Nexus 跑 /qa 或 /review 時把整個專案丟給 Claude、跑一次看 7 個 finding 就停、覺得「應該差不多」；遇到 production bug 才回頭發現同個 review 跑第二次出來不同 finding、心裡犯嘀咕但說不上來該怎麼修這個 workflow。After：「跑一次抓不到一半」是 SWR-Bench 量化過的事實、不是你感覺問題——對你 /qa /review /codex 三層工作流可以重新設計：每個 packages/ 子目錄起一個 fresh session、跑 4 個 checklist（其中 Security 走 codex 因為 Codex 在 security 議題上跟 Claude 看到不同切面，等於用「不同模型」當「不同 session」減 anchoring）、最後 /review 只看 packages 之間的邊界。這條工作流不是更慢、是 SLA 從「跑一次手感判斷」升到「四維度 × N 模組 × 兩模型」可量測的覆蓋率指標。

## Mintlify 公告:Claude Code 對它的流量比 Windows 上的 Chrome 還大——文件的目標讀者已經從人變成 AI agent

文件平台 Mintlify 公布 2026 年 Q2 一份內部數據:**所有 Mintlify-powered docs 的請求中,45% 來自 AI coding agent**;單獨切出 Claude Code,**它對 Mintlify docs 的流量比 Windows 上的 Chrome 還大**;Claude Code + Cursor 合計占所有 AI agent 流量的 **95.6%**。同時 Mintlify 改寫了自家 CLI 給 coding agent 用——`mint analytics`(看 page view、search query、feedback、assistant 對話 in terminal)、`mint dev`(本地 preview 含 AI assistant)、`mint login` / `mint new`(coding agent 接得進去),同期推「Workflows」功能(always-on agent for knowledge management,使用者設 trigger + 寫 prompt + 讓它跑)。3 月還收了 Helicone(open source LLM observability + AI gateway)的團隊與技術。

這份數據真正的意義是 **文件設計的目標讀者結構性翻轉**。三年前 docs 寫給工程師讀,排版優先級是視覺層級、scanability、code block 高亮;現在主要讀者是 LLM,優先級變成 **結構化資料、`llms.txt`、明確的 navigation hierarchy、不要塞表情符號、不要把資訊塞圖片**。Mintlify 把這條趨勢工程化的方式是 (1) 把 docs 當成 AI 介面(`llms.txt` 慣例擴張)、(2) 把 CLI 改成 agent 可呼叫(`mint analytics` 在 terminal 而不在 web)、(3) 把 docs 平台跟 LLM observability(Helicone)合併——同一份 doc 既是文件又是 prompt 註冊處又是 telemetry 入口。這是 5/11「介面層往機器讀格式重寫」洞察走到「整個文件平台都重新設計」的具體里程碑。

Before:你 Nexus 元件庫的 docs 主要讀者你想的還是「裝 Nexus 的工程師」、設計時想著「人類能不能快速找到 button props」;但現實是裝 Nexus 的工程師有 45% 用 Claude Code 跟 Cursor 開檔案、那 45% 真正讀 docs 的其實是 LLM 在他們背後 query。After:Nexus docs 應該為「LLM agent reader」做一份對應設計——`packages/ui/docs/llms.txt` 列出所有元件入口、`packages/ui/docs/components/<name>.md` 用 5/11 AGENTS.md 慣例的 6 段式(summary / export / type / usage / decision tree / common mistakes 對照),這樣 Claude Code 進來查 `Button` 用法時讀的是專門設計過的版本、不是 web 排版版本。等於把你 Figma → JSON → CSS Token 的 SSOT 哲學再延伸一層——同一份元件 metadata,推到三個介面(Figma plugin、人類 docs site、AI agent docs)。
