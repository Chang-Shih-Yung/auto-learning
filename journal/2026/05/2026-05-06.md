## Cursor 3.3：把「context 預算」可視化，「Build in Parallel」把 plan 拆成並行子代理

**來源：** [What's New in Cursor — Cursor Changelog](https://cursor.com/changelog) ｜[Cursor Release Notes — Releasebot](https://releasebot.io/updates/cursor)

你用 Claude Code 跑長任務常會撞到一件事：context window 滿了、agent 開始亂答；以前你只能猜「是 rules 太肥還是 MCP 工具太多？」——5/6 GA 的 Cursor 3.3 把這個猜謎結束了：新版的「Context Usage Breakdown」會把當前 context 預算切分成 rules / skills / MCPs / subagents 四個分項，顯示每一個各佔幾 K tokens、佔總預算百分之幾。對 Henry 你在 Claude_auto 推的 always-on / on-demand / slash command 三層分工是直接的儀表板——以前你寫了 60 行的 feature doc 不知道實際吃掉多少預算，現在打開介面看一眼就知道。

同一個版本還推了「Build in Parallel」——當 Cursor 拆完 plan 後，會自動識別 plan 中互相獨立的步驟，把它們塞給多個 async subagent 並行跑，相依步驟仍然按順序執行。背後的核心是把 5/8（你之前讀過的）「agents need control flow」那條原則往 IDE 層下推——以前 agent 跑 5 步是 sequential 5 步，現在可以是「step1 + step2 同時、step3 等兩個都完成、step4 + step5 同時」這種 DAG-shaped execution。對 Cursor 來說這不只是速度提升（plan 跑完時間從 N 步乘以平均時間 → DAG 深度乘以平均時間），更是「LLM 當元件、程式碼控流程」原則在工具層的具體落地。

以前你在 Claude Code 寫 skill 時最大的盲點是「不知道哪一條 rule 在吃 context」——只能靠刪減重新測試的 trial and error；Cursor 3.3 把這個拆解直接送到使用者眼前，從「啥都看不見」變「分項預算表」。對 Claude_auto 工作流的應用點：把 always-on rules 的預算占比設一個上限（比如 < 5K）、on-demand skill 的預算占比設一個上限（比如 < 10K），超過就強制壓縮——量測一旦量化就能設預算，這跟前端的 performance budget 是同一個工程直覺。

## Coder Agents Beta：把 AI coding agent 整套放回企業 firewall 內，支援 5 種 LLM provider

**來源：** [Introducing Coder Agents — Coder Blog](https://coder.com/blog/introducing-coder-agents) ｜[Coder Sets a New Standard — GlobeNewswire](https://www.globenewswire.com/news-release/2026/05/06/3288916/0/en/Coder-Sets-a-New-Standard-for-AI-Coding-with-Self-Hosted-AI-Model-Agnostic-Coder-Agents.html)

你在台灣金控業、醫療業、政府單位看到的內部開發環境——所有 source code 必須留在 firewall 內、不能傳到外部雲端、要過 SOC 2 與本地法規稽核；對這些團隊 Cursor / Claude Code 是「想用但不能用」的工具。5/6 Coder Technologies（不是 Anthropic 的 Claude Code，是另一家公司 Coder.com）發表的 Coder Agents Beta 切入了這條空缺——「self-hosted、model-agnostic 的 native AI coding agent」，由 Coder 的 control plane 集中管理，只在需要執行 code 時才動態 provision workspace、agent 從 Anthropic / OpenAI / Google Gemini / AWS Bedrock / 自家 self-hosted 模型五選一，全部活動都留在企業自家 infra 內。

Beta 期間（到 9 月底）所有功能都免費、無 usage limit，定價要等 GA 才公布。商業設計上這是直接挑戰 Cursor / GitHub Copilot / Claude Code 的「SaaS-only」假設——對 regulated industry（金融、醫療、軍工、政府）的工程團隊，「資料留在自己機房」不是 nice-to-have 而是合規必要條件。技術設計上 Coder 押注「model-agnostic」這條路——他們不綁某一家 LLM，給企業留逃生門，這條路徑跟 5/7（你之前讀過的 val.town 從 Clerk 搬到 Better Auth）那條「library-first、避免 SPOF」是同一個工程直覺，只是搬到 LLM provider 這一層。

以前你跟客戶談「能不能用 AI 寫 code」答案要嘛是「Cursor 但資料外洩風險」要嘛是「不能用」；現在你可以說「Coder Agents、活動全留在你機房、模型自由選」。對 Nexus 未來要推到企業客戶時是個直接借鑑——`/plugins/` 結構應該預留「model-agnostic adapter layer」，讓客戶可以指定用 Anthropic、Bedrock、或自家 Llama-3 跑設計 token 同步任務；而不是把「呼叫 Claude」hardcode 在 codebase。

## Snyk 把 Claude Opus 4.7 嵌進 AI Security Platform：弱點掃描 + 自動修補建議

**來源：** [Snyk Embeds Anthropic's Claude — Yahoo Finance](https://finance.yahoo.com/sectors/technology/articles/snyk-embeds-anthropics-claude-advance-174900036.html) ｜[Snyk integrates Claude — Help Net Security](https://www.helpnetsecurity.com/2026/05/08/snyk-ai-security-platform/) ｜[Claude Code Security: A Welcome Evolution — Snyk Blog](https://snyk.io/blog/claude-code-remediation-loop-evolution/)

你用 Snyk 跑過 npm dependency 掃描就知道——它能告訴你「your-package@1.2.3 有 CVE-2026-xxxx」、但接下來的「怎麼修」要你自己想；5/6 Snyk 宣布把 Claude Opus 4.7 嵌進 Snyk AI Security Platform，現在 Snyk 不只告訴你哪裡有弱點，還會直接生成 developer-ready fix——包含 code、dependency、container image、AI-generated artifact 四個面向。同時 Anthropic 自家的 Claude Security 也進 public beta（前身是 Claude Code Security），對所有 Enterprise 客戶開放。

技術機制是 LLM-as-judge 的具體落地：傳統 SAST 在程式碼層看「pattern matching with known vulnerable patterns」，誤判率高、給的建議是通用 advice；Opus 4.7 看的是「pattern + 整份 codebase 的呼叫上下文 + dependency tree」，能給出帶 context 的具體 patch——比如「這個 SQL injection 不只是改 raw query 用 prepared statement，而是改 sanitizeInput()，因為這個 codebase 已經有這個 helper 在 utils/sanitize.ts」。CrowdStrike、Microsoft Security、Palo Alto Networks、SentinelOne、TrendAI、Wiz 也都同步把 Opus 4.7 嵌進自家工具。

以前你跑完 Snyk 看到 50 個 CVE，要花一整天去研究「哪個重要、怎麼改」；現在 Snyk + Claude 直接給你「按 impact + 修補難度排序的 issue list，每個都附上可直接套用的 patch」。對 Henry 你在前公司做過 GitLab SAST 白箱資安整合的經驗是直接驗證——傳統 SAST 是「找出問題、開 issue 給工程師、工程師查解法」三步；現在是「找出問題、Claude 給 patch、工程師 review」兩步，省下「查解法」這一段，平均每個 CVE 處理時間從 2-4 小時降到 15-30 分鐘。

## 今日總結

5/6 是「AI 工具的 context 治理」往兩個方向同時收斂的一天——三條獨立線索匯流到同一個工程結論：**AI 工具的下一個瓶頸不是模型多強，是「context 預算 / 部署邊界 / 修補建議」這三個治理面誰先做到工程化**。

1. **context 預算可視化**：Cursor 3.3 把 rules / skills / MCPs / subagents 各自的 token 占比做成 first-class UI，「performance budget」這個前端工程概念現在搬到 LLM context 層——可量化、可設 SLA、可警告超標。
2. **AI 部署邊界往企業 firewall 內收縮**：Coder Agents Beta 把整套 AI coding agent 搬到 self-hosted、model-agnostic 架構，給 regulated industry 留逃生門——這是 5/7 val.town「library-first 避免 SPOF」的延伸到 LLM provider 層。
3. **修補建議從「通用 advice」進化到「contextual fix」**：Snyk + Claude Opus 4.7 + 同期 6 家資安廠商把 LLM 嵌進 vulnerability scanner，從「找出問題」進化到「給出貼合 codebase 命名的具體 patch」。

應用點：把 Cursor 3.3 的 context breakdown UI 思路寫進 Claude_auto 的 skill performance budget 機制；把 Coder Agents 的 model-agnostic adapter 設計寫進 Nexus 企業版 roadmap；把 Snyk + Claude 的 contextual fix 機制套用到 Nexus 設計 token 自動修補的 POC。
