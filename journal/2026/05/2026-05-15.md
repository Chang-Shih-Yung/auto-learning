# 2026-05-15 學習日誌

## Claude Code v2.1.142——你的 Claude_auto 排程任務同時拿到三層升級

如果你每天都在用 Claude_auto 跑排程任務，5/14 釋出的 Claude Code v2.1.142 是這個月對你影響最大的單次更新——同一個版本一口氣動了三個你會直接感受到的設計點。第一，Fast mode 從 Opus 4.6 升到 **Opus 4.7** 預設（要回退就設 `CLAUDE_CODE_OPUS_4_6_FAST_MODE_OVERRIDE=1`），你 daily-ai-news 那種「篇幅長、要組織訊息、要做品質判斷」的任務直接吃到主線模型升級的紅利；第二，遠端 HTTP/SSE 形式的 MCP server 過去被硬寫死的 **60 秒 timeout** 終於被 `MCP_TOOL_TIMEOUT` 環境變數真正接管（之前設了沒用、底層還是 60 秒卡死），你接外部分析 API 或長查詢的 MCP 不會再無聲被砍；第三，`claude agents` 子命令這次補上 **8 個新 flag**——`--add-dir` / `--settings` / `--mcp-config` / `--plugin-dir` / `--permission-mode` / `--model` / `--effort` / `--dangerously-skip-permissions`——讓你從一個 background session 起 sub-session 時可以挑不同的 settings、不同的 MCP set、不同的 permission mode，而不是被父 session 的配置綁死。

技術上這三件事是同一個成熟度曲線的不同切片。Fast mode 升 4.7 是 Anthropic 把「快」當成 first-class 模式之後，跟著主線模型版本走的常規動作（不再是「打折扣的 4.6」、而是「同樣 4.7、輸出更快」），對排程任務這種「成功率優先於延遲」的場景 quality drift 是要監控的指標。MCP timeout 之前 hardcode 是因為 remote HTTP/SSE 還沒被當主流——v2.1.139（5/11）`/goal` 開始把跨 turn 等待當合法狀態之後，遠端長查詢自然會冒出來，這個 60 秒上限 5/14 才真正被環境變數接管。`claude agents` 從 5/11 引進子 session 統一面板，但配置只能跟父 session 共用；v2.1.142 把 8 個 flag 補齊之後，子 session 才算真的可以獨立配置——這延續了 5/12「契約顯式化」洞察，從「終止條件 first-class」推到「子 session 配置 first-class」。

Before：你 Claude_auto 半夜跑那篇日誌時，fast mode 在跑 Opus 4.6、遠端 MCP 抓 GitHub Releases 偶爾超過 60 秒就被砍掉沒提示，所有 sub-task 共用同一份 settings.json——你想要一個 sub-session 用較嚴的 permission mode 跑 git push、另一個用較鬆的 mode 跑 WebFetch 就辦不到。After：fast mode 跟著主線 4.7 直接拉品質、`MCP_TOOL_TIMEOUT=300` 一行打開 5 分鐘的遠端容忍、`claude agents --permission-mode acceptEdits --settings .claude/journal-settings.json` 起一個專跑寫作的 sub-session、`claude agents --permission-mode default --mcp-config .claude/git-mcp.json` 起另一個專跑 push 的 sub-session——同一份 SKILL.md 第一次可以用「不同配置跑不同步驟」這個比文字描述更硬的方式來組織流程。

## Codex 進 ChatGPT 手機 App——AI agent 從「綁在 desktop」變成「跨裝置服務」

OpenAI 5/14 把 Codex 的遠端控制塞進 ChatGPT 手機 App（iOS / iPad / Android，Windows 還沒），對你這種「白天通勤、晚上家裡、週末咖啡廳」三段式工作場景的工程師會很有感。設定步驟簡單到可以一句話講完：你 MacBook 上跑著 Codex for Mac，desktop 端產生一個 QR code、手機掃一下就配對成功；之後你在通勤路上能做的事包括**批准命令**（agent 想跑 `rm -rf node_modules` 時你手機收到請求）、**切換模型**（從 5 號車廂用 GPT-5.1 改成 GPT-5.4-mini 省 token）、**看 active threads** 的即時 code diff / terminal output / screenshot、開新對話、改任務方向——而本機檔案、SSH key、git credentials、env vars 全部不離開你的 Mac，手機只是 control plane。需求是雙端 App 都要更新到最新版。

架構上這個設計跟 GitHub Codespaces 或 Replit 那條「把整個 dev environment 搬上雲端」的路線是反向的選擇。Codespaces 把 code、credentials、disk 都搬上 cloud，好處是任何裝置打開就能寫；Codex Mobile 反過來——code 跟 credentials 永遠在你 Mac 上，**控制平面**才是被同步的東西，手機端拿到的是 live state 鏡像（code diff、terminal 輸出、test 結果），不是 source of truth。這個選擇影響的是信任模型：如果你公司要求「source code 不能上 cloud」（金融、軍工、醫療），Codespaces 直接不能用，但 Codex Mobile 可以——你的 code 從來沒離開 Mac、只是你用手機在控制 Mac 上的 agent。同一動作的兩種架構，分別對應不同的 compliance 邊界。

Before：你 Claude_auto 半夜跑出問題、手機通知響了，你只能爬起來開電腦看；或者你寫程式中途要去接小孩、agent 走到一半卡 approval、回家後才能繼續。After：approval 通知直接彈到手機可以批准、code diff 在手機看得清楚、需要切模型也能在手機做——agent workflow 從「綁在 desktop 工具」變成「跨裝置服務」，但跟 Codespaces 那條「資料上雲」路線是相反的——你的 code 跟 credentials 始終在 Mac、手機只是遠端搖控器。對你 Nexus 多裝置 dev 場景（公司 Mac + 家用 Mac）也適用：兩台 Mac 都跑 Codex、手機分別 QR 配對，在外想看哪台都行。

## arXiv 1 年封禁政策——「未驗證 = 作者責任」從工程界擴張到學術界

如果你以為 AI 生成內容的審核問題只是工程界的事，5/14 arXiv 上路的新政策會告訴你不是。arXiv（最大的學術預印本平台）對所有提交論文加了一條規則：**論文裡只要有 AI 幻覺出來的假引用（不存在的論文、編造的 DOI、湊起來的作者名），作者被禁言 1 年；解禁後也不能直接上傳，要先拿到正規 peer-reviewed venue 接受才能再用 arXiv**。背後的數據令人震驚——假引用 3 年增加 10 倍：2023 是 1 in **2,828** papers、2025 是 1 in 458、2026 年初已經是 1 in **277**；NeurIPS 2025 那場 top-tier 會議有 **53 篇通過 review** 的論文裡共塞了 **100+ 個假引用**——這代表「多位 human reviewer 都沒去 verify 論文是否真的存在」。arXiv 政策最強硬的一句是給出責任歸屬：「By signing your name as an author of a paper, each author takes full responsibility for all its contents, irrespective of how the contents were generated.」

這條原則的工程意涵比學術圈更廣。policy 不是怪 LLM 出錯（LLM 出錯是基本假設）、也不是禁用 AI 寫 paper（沒禁、也禁不了），而是把「**未驗證的 AI 輸出 = 作者主動選擇了沒驗證**」變成 enforceable rule。對應你 5/4 session-log 那條洞察——「稽核訊號必須由獨立稽核層產生，不能由執行層回報」——當時三個案例是 VS Code Copilot 把 Co-Authored-By trailer 默默注入 commit、Anthropic 自家研究 47% debugging 技能退化、typia 作者把 Go port CI 綠燈造假，三個都是「執行層自己給自己合格」。arXiv 把同一個工程結論搬到學術界並升一級：不再依賴執行層誠實，而是讓**未驗證**本身具有後果（1 年封禁），等於把責任邊界從「做錯事」推到「沒驗證」這個更早的決策點。

Before：你 review 自己用 AI 生成的 code 或文章時，「驗證 AI 給的 reference / API name / 版本號真的存在」是個「我應該做但有時懶得做」的責任感問題；別人交給你的 AI 生成內容你也只能信任他驗過。After：arXiv 把整個產業基準從「希望大家驗證」推到「不驗證有具體後果」——對你 Nexus 元件庫推企業客戶這個場景特別有意義：以前 AI 生成的元件文件你可以說「等被發現問題再修」，今年起客戶會問「你 build pipeline 有沒有 AI 內容驗證層」；對 Claude_auto 也立刻適用——每次寫日誌前必須確認引用的工具/版本/star 數真的存在（這條規則 learning-context.md 已經寫好了，這次政策只是讓你更知道為什麼這條規則重要）。

## 今日總結

三條看似獨立的新聞（Claude Code v2.1.142 / Codex Mobile / arXiv 政策），匯流到 2026-Q2 的同一個主題——**「AI agent 的責任邊界正在被工程化地拆解」**。

- **Claude Code v2.1.142** 把「子 session 該用什麼配置」從約定俗成升格為 8 個 first-class flag，等於把「責任歸屬」做進子 session 的配置層——延續 5/12「契約顯式化」、5/13「界線重劃」兩條主線往下一層推。
- **Codex Mobile** 把 control plane（手機批准、切模型）與 data plane（code、credentials 留在 Mac）分離——這是「source of truth 在哪、view 在哪」的責任歸屬設計，跟你 Nexus 那條 Figma → JSON → Token 的 SSOT 哲學完全同構，只是從設計系統推到 AI agent runtime。
- **arXiv 政策**把「未驗證 = 作者責任」變成 enforceable rule，等於把責任邊界從「做錯事後追責」推到「沒驗證就有後果」這個更早的決策點——延續 5/4「稽核訊號必須由獨立稽核層產生」洞察並擴張到學術界，對你 Nexus 推企業客戶時的「AI 內容稽核層」這個賣點立刻有引用憑據。

對 Claude_auto 立即可動的應用點：(1) 立刻在 settings 設 `MCP_TOOL_TIMEOUT=300` 避免遠端 MCP 被默默砍；(2) 試把 SKILL.md 拆成 `fetch-settings.json` / `write-settings.json` / `push-settings.json` 三份配置，用 `claude agents --settings` 切換；(3) 在 git pre-commit hook 加一支 verify-mentions 腳本，自動驗證日誌裡提到的工具是否真的存在、是否符合 stars / downloads 門檻——把 learning-context.md 「工具引用驗證」這條規則從文字變成 invariant guard。
