## GitHub Spec-Kit v0.8.7：把 PRD 從「靜態文件」變「程式碼生成源頭」，40K stars Apache-2.0

**來源：** [github/spec-kit GitHub](https://github.com/github/spec-kit)（40K+ stars、Apache-2.0）｜[Spec Kit Documentation](https://github.github.com/spec-kit/) ｜[Meet GitHub Spec-Kit — MarkTechPost](https://www.marktechpost.com/2026/05/08/meet-github-spec-kit-an-open-source-toolkit-for-spec-driven-development-with-ai-coding-agents/)

你現在用 Claude Code 寫 feature 的流程是「跟 LLM 對話 → 邊聊邊決定 spec → 邊聊邊 generate code → 邊聊邊 debug」——spec 永遠在你腦中、code 永遠在演進中、兩者沒有正式對應關係；GitHub Spec-Kit（5/7 GA v0.8.7，5/10 那週為 current）把這條 workflow 反過來：先寫一份正式 PRD（產品需求文件）、把它當「程式碼生成源頭」、`/speckit.plan` 從 PRD 產 implementation plan、`/speckit.implement` 載入「constitution context」確保生成的 code 不違反專案治理規則。Spec-Kit 本身是 Python CLI、Apache-2.0、40K+ stars、支援 30+ AI coding agent（Claude Code、Copilot、Amazon Q、Gemini CLI）。

v0.8.6（5/6）的最大進展是「constitution context」進到 `/speckit.implement`——以前你寫了一份 spec、Claude Code 照 spec generate 後可能還是違反你的內部規範（比如「不能用 axios 必須用內建 fetch」「色彩必須來自 design token 不能 hardcode」），spec-kit 現在把這些規範包成「constitution」隨 implementation 一起載入，讓 LLM 在 generate 時就 enforce，而不是 review 才發現。v0.8.7 加進了 lingma 支援與 agent-orchestrator community extension，讓同一份 spec 可以由不同 LLM 接力產出（比如用 GPT 5.4 做 plan、Claude Opus 4.7 做 implementation）。

以前 spec / PRD 是「寫完就被忘掉」的文件，工程師憑記憶寫 code、QA 憑記憶找 bug；現在 spec 是「持續被 LLM 讀取的活源頭」，需求變了就改 spec、改完 re-run `/speckit.implement`，code 跟 spec 永遠對齊。對 Henry 你在東捷 EQS 做過 100+ 表單流程卡控的經驗是直接對標——當時是用 Confluence 寫 spec、工程師對著 spec 寫 code、PM 對著 spec 寫測試案例，三方都靠人腦同步；Spec-Kit 把「三方同步」這道工程化成 PRD → code → test 的自動鏈，少掉「業務改規格、工程師不知道」這條典型失敗模式。

## Hermes Agent：Nous Research 開源的「自我改進」AI agent 框架，57K-110K 星週量級

**來源：** [Hermes — get-hermes.ai](https://get-hermes.ai/) ｜[Hermes Agent v0.9 Review — heyuan110](https://www.heyuan110.com/posts/ai/2026-04-14-hermes-agent-guide/) ｜[OpenClaw vs Hermes Agent — Petronella](https://petronellatech.com/blog/openclaw-vs-hermes-agent-2026/)

你看完 Anthropic 官方的 Managed Agents、Cursor 3.3 的 Build in Parallel，會以為 agent framework 的設計題已經被大廠定案——5/10 那週的 Hermes Agent 證明社群還有不同路線。Nous Research（推出 Hermes-3 LLM 系列的 open-weight 團隊）2026-02-25 開源的 Hermes Agent，到 5 月已從 57K star 衝到 ~110K star（10 週累積）；它不綁某個 LLM provider，而是當「always-on autonomous agent harness」——支援 Anthropic、OpenAI、OpenRouter catalog、DeepSeek、MiniMax、Kimi、Nous Portal、以及 Ollama / vLLM / SGLang 等本地 runtime。

Hermes 押注的設計直覺跟 Cursor / Claude Code 不一樣——它不是「coding agent in IDE」，而是「persistent agent + 訊息 gateway」：跨 session 持久記憶（不是每次 conversation 重來）、self-improving skills system（agent 自己改自己的 prompt）、cron scheduling（定時自動跑任務）、訊息 gateway 接 Telegram / Discord / Slack / WhatsApp、tool execution、always-on autonomous。對 Henry 你的 Claude_auto 排程設計直接對標——你每天用 Claude Code scheduled task 跑 journal 生成、news 整理，Hermes 想做的就是把這個從「Anthropic 排程器跑 Claude Code」這條鏈，搬到「自家機器持續跑 + 跨 LLM provider」這條更 portable 的鏈。

以前你要做「持續跑的 AI agent」要嘛靠 cloud SaaS（Replicate、Modal、Anthropic Managed Agents）要嘛自己寫一堆 systemd service + cron + LLM API wrapper；Hermes 把這條手刻路徑做成 110K star 的 open-source framework，讓社群少做重複造輪。對 Claude_auto 工作流的應用點：你目前依賴 Anthropic 的 scheduled task 機制，未來若想搬到自家 server（為了 portability 或省雲端費），Hermes 是現成的 harness——把現在的 SKILL.md 轉換成 Hermes 的 skill format，cron 排程從 Anthropic 端搬到 Hermes 端、訊息 gateway 換成 Slack 通知。

## 上週生態回顧：AI 工具設計權正在從「中心化平台」往「協議 + 自選後端」漂移

**來源：** [AI News Weekly Summary May 2-10 — Dev|Journal](https://earezki.com/ai-news/weekly-summary-2026-05-10/)

把過去一週（5/2-5/10）的訊號排在一起，會看到一個共同方向——AI 工具的競爭核心從「誰家模型最強」漂到「誰家的協議 / 介面最 portable」：5/2 Anthropic Skill 慣例（capability/trigger/cost 三軸量化）、5/3 Cloudflare Code Mode（MCP token 1.17M → 1K，介面壓縮）、5/4 GitHub Copilot Co-Authored-By 自動注入（中心化平台 vs IDE 訊號污染）、5/5 anthropics/financial-services（plugin 結構讓 deploy 粒度從 stack 降到 workflow）、5/6 Coder Agents（model-agnostic self-hosted）、5/7 val.town Better Auth 取代 Clerk（library-first vs SaaS）、5/8 Anthropic Managed Agents v0.100.0、5/9 MCP Gateways 7 種比較（3-4ms 到 100-300ms 治理 overhead）、5/10 Hermes Agent（自家 harness 跨 LLM provider）。

九條獨立路徑指向同一條工程直覺：**控制權往使用者方向漂移**。以前 AI 工具的「強」是「平台幫你決定模型、決定治理、決定 deploy 方式」；2026-Q2 開始這條假設正在反轉——好工具的標準變成「協議公開、後端可換、邊界清晰、能 self-host」。對使用者而言這是好事——你不再被某家公司鎖住、可以混搭不同 LLM、可以把活動留在自家機房。

對 Henry 你做 Nexus 元件庫的 lessons learned：別把「呼叫 Claude」hardcode 在 codebase，預留 adapter layer 讓客戶換 LLM provider；別把「設計 token 同步」綁死在 Anthropic Skill，預留通用 prompt protocol 讓使用者選 LLM；別把「企業客戶資料」一定送 Vercel，預留 self-host 部署選項。這三條設計約束在 2026-Q1 還是「nice to have」，到 Q2 已經是「企業客戶選型時的決勝題」。
