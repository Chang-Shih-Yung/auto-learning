# 2026-05-13 學習日誌

## DuckDB Quack——把「in-process 資料庫」這個假設打破

如果你做過 ECharts 戰情室或 MES 看板，你會立刻看懂 DuckDB 在 5/12 釋出的「Quack」協定在解什麼。DuckDB 一直以來最迷人也最受限的設計是「in-process」——你不需要架 server，DuckDB 就是程式裡的一個 library、查 Parquet/CSV 比 PostgreSQL 快幾十倍。但這個架構在一個情境上會立刻撞牆：當你需要**多個 process 同時寫同一份資料**——比方說多台機台的 telemetry 一直推資料進來、Dashboard 端要即時讀——in-process 就會變成單點瓶頸。Quack 用 HTTP 在 9494 port 上重新攤開這件事，60M 行的批次轉移 **4.94 秒**（vs Arrow Flight 17.40 秒、PostgreSQL 158.37 秒，等於對 PG 快 **32 倍**、對 Arrow Flight 快 3.5 倍），8 條平行寫入做到每秒 **5,434 transactions**（PG 只有 4,320）。已經在 DuckDB **v1.5.2** 釋出（`core_nightly` extension），預計秋季的 v2.0 正式入主線。

技術上 Quack 沒走 Arrow Flight 那條主流路線，原因有兩個：Arrow Flight 每個查詢至少要兩次往返（先 GetFlightInfo、再 DoGet），對需要低延遲互動的場景（戰情室）每次多一個 round-trip 就會被使用者感受到；而 Arrow 格式是外部標準、DuckDB 自己想要演化序列化格式就會受限。所以 Quack 用 DuckDB 內部序列化、**單次 round-trip 完成查詢**、預設用 random token 認證但留 callback 讓你可以接 LDAP 或 SSO。同時跟 DuckLake 整合就可以做 remote catalog——你 MES 多廠區的數據可以用 Quack 中心化、本地保留 DuckDB 引擎跑分析、Wasm browser 端也能直接連，整條鏈不需要任何「跑得起 PG」的 infra。

Before：你 MES 戰情室 ECharts 那條鏈是「SignalR push 新數據 → 後端寫 PG → 前端再 query PG → ECharts 重繪」，中間每一段都吃延遲、PG 的 50K 行 aggregation 在尖峰時段會明顯卡。After：DuckDB Parquet 檔分區存放、本地 Quack server 每秒 5K+ tx 寫入、ECharts 端 query 直接走單次 round-trip——同樣的 dashboard 後端從「需要 PG + Redis 兩塊 infra」降到「一個 DuckDB process + Parquet 檔」，部署從 GB 等級降到 MB 等級、查詢延遲從幾百毫秒降到幾毫秒、查詢語法還是熟悉的 SQL，剛好打中你正在學 SQL 這個技能轉折點。

## Statewright——把 AI agent 的「tool 可見性」做成狀態機

如果你想到 5/8「agents need control flow」那條筆記——確定性狀態機是 agent 可靠性的真正關鍵——5/12 在 HN 上 trending 的 Statewright 就是這條哲學最直接的落地。它的口號很直白：**「Agents are suggestions, states are laws.」** Agent 在每個工作階段只能看到該階段允許的工具，其他工具完全隱形，連看都看不到——以解 bug 為例：`planning` 階段只開放 read + grep、`implementing` 階段才解鎖 edit + write、`testing` 階段才開放 bash 跑測試、`completed` 階段才能 commit。Research benchmark 顯示這個約束對小模型助益最大——13.8 GB / 19.9 GB 的本地模型在 5 個 SWE-bench 任務上從 2/10 提升到 **10/10**，避免「read-loop death spirals」（agent 重複讀同一個檔但從不 edit）。

技術上做了四層約束：每個 state 限制工具 visibility（不只是 access 控制，連描述都不送進 context）、Bash 區分 read-only vs destructive（rm/redirect 在非 write state 直接被擋）、Edit guards 限制每個 state 改的行數與檔案數、approval gates 卡 high-risk 動作。Plugin 目前支援 Claude Code、Codex、opencode、Pi、Cursor，安裝是 `/plugin marketplace add` + `/plugin install` + `/statewright start <workflow>`。技術直覺很簡單：與其期待 agent「自我克制」，不如把「現在這個階段允許看到什麼工具」做成可組態的 state machine——你寫一份 YAML 定義 state 與 transition，Statewright 在 plugin 層 enforce，agent 連嘗試走偏的機會都沒有。

Before：你跑 Claude_auto 排程任務，得在 SKILL.md 用「請先 X 再 Y」這種文字描述執行順序，agent 走順序對不對全看 prompt 寫得多嚴；想要避免 agent 把 journal 寫一半就跑去 push，得寫一堆「不要做 X」的反向約束。After：用 state machine 把 daily-ai-news 切成 `fetch → filter → write → verify-mdx → commit → news-gen → log-update` 七個 state，每個 state 只開放對應的工具（fetch 階段不能 Edit、commit 階段不能再 Read 新內容），avoid death spiral 的不是 prompt 寫得好，是工具根本拿不到——這條哲學跟 5/12 你筆記裡「契約顯式化」三條主線是同一個結論的下一步：契約不只要顯式，還要由外層 enforce 而非由 agent 自我宣告。

## Needle——26M 模型把 tool calling 帶到手錶上

如果你以為 function calling / tool use 一定要 GPT-4、Claude 3.5、Gemini 2.0 那種等級的模型才能準確，5/12 釋出的 Needle 把這個假設拆了。Cactus Compute 把 Gemini 3.1 的 tool calling 能力**蒸餾**進一個 **26 百萬參數**的「Simple Attention Network」——比 Gemma-270m 還小、可以在手機、手錶、AR 眼鏡這種 resource-constrained 裝置上跑，benchmark 上單發 function call 任務超越 FunctionGemma-270m、Qwen-0.6B、Granite-350m、LFM2.5-350m 這四個專做工具呼叫的小模型。Cactus 自家 infra 上跑出 **prefill 6,000 tokens/s、decode 1,200 tokens/s**——這個速度意味著你按下按鈕到 tool 被觸發的延遲是「人類感受不到」的等級。模型權重、資料集生成程式碼、Web UI playground 都開源，MIT 授權，可在 Mac/PC 本地 fine-tune 自訂工具。

訓練細節：先在 16 顆 TPU v6e 上預訓練 200B tokens 花 27 小時，再用 2B tokens 的 function-call 資料 post-train 45 分鐘——對比 Gemini 3.1 那種 trillion-token、million-GPU-hour 的訓練成本，這個量級的 fine-tune 是「個人開發者一個下午能跑完」的規模。技術直覺有兩層：第一，tool calling 任務本身比 general reasoning 窄很多——你不需要模型懂量子力學，只需要它能從一段使用者自然語言抽出「呼叫哪個 function、帶哪些參數」，這個窄任務適合用蒸餾把大模型的「知道怎麼做」壓縮成小模型的「能做這一件事」；第二，端裝置跑 tool calling 解鎖了「離線 AI agent」這個一直被卡住的場景——你的 MacBook、AR 眼鏡、智慧手錶不需要連雲端就能跑 agent。

Before：你 Nexus 想做一個 Figma plugin、讓設計師問「把這個元件改成 dark mode 配色」，你得呼叫 Claude/GPT 雲端 API、延遲 1–3 秒、設計師資料離開電腦、按次計費。After：26M 小模型嵌進 plugin 本身、本機推論、200ms 內回應、零訂閱、設計師檔案不離開設備——這條哲學打通你過去三年 Nexus 在「設計到程式自動化」這條鏈的最後一塊：tool calling 從「雲端依賴」降到「端裝置原生能力」。

> ⚠️ 目前 440 stars，新工具，使用前請自行確認安全性。權重與 dataset 開源 MIT 但 production 採用前要評估 Cactus Compute 的維護承諾、跑自己的 benchmark、確認蒸餾結果在你的工具集上不會失效。

## Magic Pointer + Googlebook——指標從「定位」進化到「意圖」

如果你做設計背景出身，你會立刻看出 Google DeepMind 在 5/12 發表的「AI Pointer」是把「滑鼠指標」這個 40 年沒變的人機介面打掉重做。傳統指標只回答一個問題：「**這個座標被點到了**」；DeepMind 用 Gemini 把指標升級成回答兩個問題：「使用者指的是哪裡」+「使用者指的是什麼語義」。四條設計原則一字排開：**(1) 維持心流**——AI 能力不應該強迫使用者切換到「AI 工具視窗」，要在現有 app 流程中無縫運作；**(2) 看了就懂**——指標自動捕捉視覺與語義上下文，使用者不需要寫長 prompt；**(3) 接受「這個」與「那個」**——使用者可以說「修這個」「移那個」，指標當代詞綁定；**(4) 把像素變實體**——視覺元素被即時轉成可互動的結構資料（地點、日期、物件）。技術上由 Gemini 同時理解 location（指到哪）與 semantic（指什麼），demo 已在 Google AI Studio（影像編輯、地圖導航）放出，Chrome Gemini feature 與**秋季 2026 上市**的 Googlebook 筆電都會整合「Magic Pointer」。

Googlebook 本身也值得注意——這是 Google 第一次推自家品牌筆電，由 Acer / Asus / Dell / HP / Lenovo 五家代工，定位是「為 Gemini Intelligence 設計」的筆電：除了 Magic Pointer，還有 Create My Widget（自然語言生成桌面 widget）、Cast My Apps（不裝 app 直接跑 Android）、Quick Access（與 Android 檔案同步）、鍵盤上有專屬 Google 鍵。重點是 Google 把「OS 級 AI 整合」當成這台筆電的差異化敘事，「**Intelligence is the new spec**」這句 tagline 等於宣布：以後筆電的核心 spec 不是 CPU、RAM、GPU，是「AI 能力深度」。

Before：你 Nexus 在做「Figma → Angular 元件」這條 design-to-code 鏈，AI agent 是被你「召喚」的工具——你打開 Figma、選一個元件、按下 plugin 按鈕、AI 才開始幫你產 code。After：在 Magic Pointer 這條哲學下，AI agent 在 OS 層常駐，你用指標「指」一個 Figma 元件就能說「**幫我把這個變成 Angular**」、不用切換到 plugin、不用寫 prompt——「指 + 自然語言代詞」變成新的 input 方式。這條哲學跟 5/5 Anthropic Claude for MS365 把「跨 app 共享 context」帶到 Office 是同一個 OS 層 SSOT 直覺，今天 Google 用 Magic Pointer 把同樣的事帶到滑鼠指標層——對你 Figma → Angular 工作流的影響：未來「設計到程式」的入口可能不是 plugin 按鈕，是指標本身。

## 今日總結

今天四條線索全部指向同一個工程主題——**把原本被當「固定假設」的邊界拆掉、變成可重新設計的契約**：

- **DuckDB Quack** 把「資料庫只能 in-process / 要架 server 才能跨 process 共享」這條 boundary 拆掉，用 HTTP + 自家序列化 + 單一 round-trip 把 60M 行轉移做到 4.94 秒（vs PG 158 秒）
- **Statewright** 把「AI agent 該不該用某個工具靠 prompt 或人類審查」這條 boundary 拆掉，用 state machine 在 plugin 層 enforce 工具 visibility，13.8 GB 本地模型從 2/10 衝到 10/10
- **Needle** 把「tool calling 必須由大型雲端模型完成」這條 boundary 拆掉，用 26M 蒸餾模型在端裝置上跑，6,000 tokens/s prefill 等級
- **Magic Pointer** 把「滑鼠指標只負責定位」這條 boundary 拆掉，用 Gemini 同時理解 location + semantic，秋季 2026 Googlebook 上市同時 ship

這條主線延續 5/12「契約顯式化」洞察但更激進：5/12 講的是把契約從「約定俗成」升格為「first-class 物件」（workflow trigger / turn 邊界 / 終止條件），5/13 講的是把這些 first-class 物件**本身**當成可重新設計的工程題——in-process / out-of-process 的 trade-off、tool 可見性的 state binding、模型大小與部署位置的選擇、指標的語義能力，全是原本被當「就是這樣」的假設、現在被拆開重做。

對你 Nexus + Claude_auto 的應用點：
1. **MES 戰情室後端**現在可以從「PG + Redis 雙 infra」遷移到「DuckDB + Parquet 單檔」，後端工程量降一個量級、查詢延遲降到毫秒級——剛好接上你正在學 SQL 這個技能轉折點
2. **Claude_auto SKILL.md 終止條件**從 5/11 已升格為 `/goal` 設定（5/12 v2.1.140 還補了一個 disableAllHooks 場景的 hang fix），下一步是把整個 daily-ai-news 流程的工具 visibility 升格為 Statewright state machine
3. **Nexus Figma plugin** 短期可以用 Needle 級的小模型做本地 tool calling、預演 Magic Pointer 那種「指 + 語義」的 design-to-code 體驗，中期 Magic Pointer + Googlebook 上市時 Nexus 已經有 plugin 原型可以遷移到 OS 層

界線重劃是 2026-Q2 的工程主旋律——下一步觀察的是：哪些 boundary 還沒被拆？package manager 與 runtime 邊界？module federation 與 deployment 邊界？這些都還在 「就是這樣」的假設區。
