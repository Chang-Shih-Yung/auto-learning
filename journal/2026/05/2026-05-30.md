## MCP is Dead? — 一條 Linear issue 查詢 200 tokens vs MCP 12,957 tokens 的真實成本

你在 Nexus 已經實作 MCP Server 對 Claude / Cursor 暴露元件查詢介面，現在 Quandri 團隊 5/29 在工程 blog 公開算清了用 MCP 的真實 context 成本：他們的 stack 接 4 個 MCP server，**光是 tool definitions 就吃掉 Claude 200K context window 的 10.5%**（約 21K tokens），其中 Linear MCP server 一個就占 12,800 tokens 載入 42 個 tool。同一件事的對照組：**用 CLI 查一個 Linear issue 約 200 tokens、用 MCP 查同一個 issue 約 12,957 tokens——65 倍差距**。性能也對不上理想：他們 benchmark 同一個 Jira 查詢路徑，**MCP 路徑每次呼叫慢 3×、第一次（含 initialization）慢 9.4×**。換掉之後他們的方案不是「不用 MCP」，是「用 Claude Code Skills 包既有 CLI」——skill 文件用到時才載入（lazy load）、CLI 是工程師早已會的工具、token 從 21K 降到「skill 觸發時」才算——claim 是「freed ~21K tokens of context」且 initialization failure 直接歸零。

這條 blog 不是在說 MCP 不能用，是在點出 **MCP 把所有 tool definition 在 session 開頭一次性塞進 context 的設計選擇——在 4 個以上 server 連線時開始把 context budget 吃掉一成**——而且這個成本在 long-running agent 場景下會被乘以「session resume 次數」（每次 resume 都重載），不像 prompt 你只付一次。三個成因可拆：(1) MCP `tools/list` 是 init time 全展開、不是 query time 動態取，所以你接的每個 server 都把全部 tool 名稱 + JSON schema + description 餵進去；(2) 每個 tool 的 description 要寫得詳細才能被模型正確選用，但詳細 description 在 idle 時不會被「壓縮」——它是裸佔 context budget；(3) MCP 的 server-client 協議有額外 overhead（stdio JSON-RPC 來回、retry、stateful handshake），所以單次呼叫 3× 慢、cold start 9.4× 慢的差距是協議本身。對應 5/27 你看到的「契約 first-class 物件本身的『屬性』也要 first-class 化」——MCP 把 tool definition 升格 first-class，但沒把「載入時機」升格，所以 always-on 載入成本就被低估了。

以前你做 Nexus MCP server，思路是「暴露越多 tool 越好」——元件查詢、token 同步、ECharts schema、Figma node-id 解析全塞進去；現在你看到 4 個 server 就 10.5% context、單一 Linear 12,800 tokens 的真實數字，你會重新設計 Nexus MCP 的 surface：(1) 把 tool 拆成「核心 5 個 always-on」+「進階 20 個 on-demand」，後者只在 trigger phrase 出現時透過 skill 動態載入；(2) 每個 tool description 用 `< 100 tokens` 為門檻寫精，跟 Veso AI 5/26「CLAUDE.md < 200 行」postulate 同源；(3) 提供一份 CLI fallback（`nexus query <id>`）給 Skill 包，讓 Claude Code 使用者可以「不接 MCP server 也能用 Nexus」——對應 5/27「契約 first-class 物件本身的屬性也要 first-class 化」中「載入時機」這個漏掉的屬性。對 Claude_auto SKILL.md 直接動：把現在 always-on 的 MCP 連線改成 `disallowed-tools` 先全關、需要時才透過 skill 啟用——同時用 v2.1.157 的 `/usage` per-category 看哪些 tool 真的被叫到、哪些只是占 context 不被用。

你已經知道 Henry 在意「on-device 設計助手」這條路線，現在 Liquid AI 5/29 釋出 **LFM2.5-8B-A1B**——**總參數 8B、active 參數 1B 的 MoE 架構**，38T tokens 訓練（前代 12T 三倍跳）、**context window 128K**（前代 32K 四倍跳）、**詞表 128K**（前代 65K 翻倍，多語系覆蓋擴大）。重點數字是硬體門檻：**laptop CPU 推理可以「stay under 6GB」RAM**、手機 GPU 上「holds ~30 tokens/s」——也就是你 16GB MacBook 不必獨立顯卡就能跑、手機端聊天速度可達秒回。基準分數對照同級 Gemma-4-E4B-IT (8B)：**IFEval 91.84 vs 87.74**（指令跟隨）、**MATH500 88.76 vs 65.00**（數學推理大幅領先）、**BFCLv4 48.50 vs 33.92**（function calling），AA-Omniscience Index -24.70 vs -50.67（指標越高越好）。模型 weights 開放在 Hugging Face、官方 playground 可以直接試。

## aislop — 把「AI 生成程式碼壞味道」變成 0–100 分的 deterministic 掃描器

你在 Nexus 已經有 60% 元件是 AI 生成，現在 aislop（GitHub 192 stars，TypeScript 99.2%、MIT）提出一個專門針對 AI 生成程式碼的掃描器——不是傳統 linter 的 style 偏好，是 **六個專門類別**：(1) **AI Slop**（自我解釋程式碼上面的敘述性註解、swallow 掉 exception、`as any` cast、幻覺出來的 import、重複出現的 helper、dead code、TODO stub、過大 function）、(2) **Formatting**（接 Biome / ruff / gofmt / cargo fmt / rubocop / php-cs-fixer）、(3) **Linting**（接 oxlint / ruff / golangci-lint / clippy）、(4) **Code Quality**（複雜度上限、未用檔案 / 未用依賴、dead code）、(5) **Security**（eval / innerHTML / SQL injection / shell injection / 依賴 audit）、(6) **Architecture**（自訂 import 禁令、分層規則，opt-in）。它跑出來給 **0–100 分**，sub-second 完成，**deterministic（runtime 不呼叫 LLM，純 regex + AST）**，支援 7 種語言（TS / JS、Python、Go、Rust、Ruby、PHP、Java）。

設計意義有三層。第一層是 **「AI 生成程式碼的 smell 跟人寫的 smell 不一樣」這個假設第一次被工程化**——傳統 ESLint / Prettier 抓的是 style（縮排、引號），aislop 抓的是 AI 行為痕跡（`as any` 是 Claude / GPT 寫不出正確類型時的逃生路徑、敘述性註解是 LLM 把 prompt 解釋寫進註解的習慣、幻覺 import 是訓練資料舊版庫名稱漏修）。第二層是 **deterministic 是刻意的設計決定**——掃描器自己用 LLM 會把成本疊到 review 環節，aislop 用 regex + AST 在 sub-second 內跑完，0 token 成本，可以放 pre-commit hook 不擔心拖慢開發循環。第三層是 **0–100 分數機制給 SLA 用**——對應 5/26 你看到的 Veso AI「cost 50/75/90 告警」postulate，把直覺門檻數字化；你可以對 Nexus 訂「主要 packages/ui aislop score > 85」當 CI gate，PR 不過不能 merge。

以前你在 Nexus 60% AI 生成元件，review 時靠手感看「這個 helper 是 Claude 重複生的還是真的需要」「這個 `as any` 是必要 escape 還是 LLM 偷懶」；現在 aislop 把這個判斷規則化、跑一次出個 0–100 分。對 Nexus 的具體應用：(1) 加進 pre-commit hook，packages/ui 改動 commit 前跑 aislop scan、分數 < 85 直接 block；(2) CI gate `aislop ci --json` 輸出機器可讀格式，發 PR 把分數變化 inline comment（如 5/26 看到的 `/code-review --comment`）；(3) 對 Nexus 賣企業客戶時的論述加一條「AI 生成元件有 SLA 控管」，aislop score 可以放在 Nexus dashboard 當「設計系統健康度」儀表板的一條指標。對 Claude_auto SKILL.md 的延伸：在 Step 5 commit 前跑 aislop scan，分數低於門檻代表 journal MDX 自己也寫得糙了，session 失敗回報而不是默默 push。

## 同一個 NestJS prompt：Claude 6 個資安錯誤 vs Gemini 2 個——「modeled-vs-modeled diversity」的具體案例

你在 Nexus 60% 元件 AI 生成、Claude_auto 用 Claude 寫文章，現在 dev.to 上 Ofri Peretz 5/29 做了一個直接可複製的對照實驗：同一個 prompt「Build a NestJS users service. Authentication, registration, login, profile endpoint, admin panel.」，丟給 **Claude Sonnet 4.6（Anthropic API）** 跟 **Gemini 2.5 Flash（Gemini CLI）**，再用 ESLint NestJS security 規則組合（6 條規則全開 error）對生成的 controller 跑驗證——大約 3 秒就跑完。結果：**Claude Sonnet 4.6 觸發 6 個 security 錯誤**（沒對任何 route 加 authentication guard、API response 把 password 跟 refresh token 露出、login endpoint 沒 rate limit、缺 ValidationPipe、role 欄位用裸 `string` 沒 `@IsEnum`、debug endpoint 不帶驗證就回 `DATABASE_URL`）；**Gemini 2.5 Flash 觸發 2 個 security 錯誤**（auth endpoint 沒 `@Throttle()` decorator、login / register 缺 rate limiting）。**兩個模型都漏掉 auth endpoint rate limiting**——作者結論：「rate limiting is a _rate-at-which_ constraint, not a _what-does-it-do_ constraint」，從「功能描述」prompt 推不出「速率限制」這種約束。

這篇不是要證明哪個模型比較強，是把 5/26 Nolan Lawson「modeled-vs-modeled diversity 反 anchoring」洞察推到具體可複製的實驗：(1) 兩個模型寫出的結果**錯誤類型不重疊**（Claude 6 個錯誤裡 5 個是 Gemini 沒寫到的、Gemini 2 個錯誤裡 1 個是 Claude 也漏的 rate limiting）——這證明單看一個模型輸出無論多強都會有盲點；(2) Claude 6 個 vs Gemini 2 個不能直接比較，因為 Gemini 寫出來的程式碼更骨架化（功能少），錯誤少不代表寫得對；(3) 兩個模型都漏「速率限制」這種**從功能描述推不出來的約束**——這類 cross-cutting concern 必須由獨立的驗證層 enforce，不能靠 prompt engineering 補。對應 5/26 Microsoft Copilot Cowork 那 5 行 injection 攻破 5/5 案例——「相信單一模型輸出」是同一個失敗模式。對應 5/15 你看到的「責任邊界工程化拆解」——這篇直接把 review 責任從「相信 AI」拆到「ESLint security plugin + 多模型對照」兩個獨立稽核層。

以前你在 Nexus 用 Claude 跑元件生成，review 時靠手感看「這個元件的 a11y 屬性夠不夠」、「event handler 有沒有 prevent default」；現在你有一個直接可複製的 pattern——同一個 prompt 跑 Claude + Gemini（或 Claude + Codex）兩套，輸出 diff 後跑 deterministic linter（如 ESLint 對應領域規則 + aislop）二級驗證。對 Nexus 具體應用：(1) `nexus component check <name>` 命令同時跑 Claude + Codex 生成版本、用 aislop + 自訂 a11y 規則 lint，列出兩版的差異供作者選擇；(2) 對企業客戶把「multi-model adversarial review」做成 Nexus CLI 的一級命令，**對應的 SLA 是『單一模型輸出 ≠ 可信，必須對照才能上 production』**；(3) 對 Claude_auto 立刻可動：commit journal 前把 5 篇文章標題餵 Codex 跑 fact-check，輸出 diff 才推；漏抓的數字 / 錯誤引用比相信單一模型穩。
