# 2026-06-23 學習日誌

## LLM-as-Judge 給 0.85，trace-based 評估給 0.000——同一份 agent 答案

你跑一個 Claude agent 問 Confluence 文件裡的某條規格，兩個 frontier judge model 各自獨立打分 0.85。看起來是綠燈：兩個 LLM 都認為答案夠好。但實際 trace 顯示——agent 從頭到尾沒打開過任何文件、沒下過任何查詢、沒搜尋過該頁。它「自信地」宣稱文件不存在，然後從這個未驗證的前提繼續推理。同一份答案用 GroundEval（trace-based scoring）打分：**0.000**。Judge model 看不到 agent 走過的路，只看到終點是否跟標準答案像，這個架構性盲點讓 0.85 和 0.000 可以並存。

LLM-as-judge 的根本限制是：judge 只比對「最終答案 vs 正確答案」，看不到三件事——agent 有沒有真正存取它引用的證據、證據在查詢當下是否可得、「找不到」的結論是否經過充足搜尋。文章原句：「judge model 讀完最終答案，是在檢查地圖跟目的地有沒有對上，無法檢查 agent 是真的走完路線，還是運氣好瞬移到終點。」修法不是換更強的 judge，而是改變評估架構——三件 deterministic state contract：access policy（agent 能存取什麼）+ event log（agent 實際存取了什麼）+ artifact timestamp（證據何時可得），在 trajectory 對著 contract 機械化檢查，**部署前就 fail，不靠事後 judge**。

以前評 AI agent 品質要嘛跑昂貴 human eval、要嘛信兩個 judge model 加總過半的多數決——這兩條路 6 個月內已成預設。現在拿這個 0.85 vs 0.000 案例對照，預設值需要重寫：judge model 只能補強不能取代 trace verification。Henry 的 Claude_auto SKILL.md Step 5 自我優化迴圈寫的就是「Claude 自己評自己這次 session 寫得好不好」，這條洞察直接套用——下一刻度 SKILL.md 加 trace contract：必須驗證 Claude 真的 Read 過 sources.yaml、user-profile.md、session-log.md（不是宣稱讀過），驗證每個 AnnotationCard 的 skill ID 真的對應 skill-taxonomy.yaml 既有 id，才算過關，不再單靠 Claude 自我評分。

## GLM-5.2 在你的 Mac Studio 上跑——unsloth 量化 1-bit 到 8-bit 的 RAM 對照表

你手上有一台 256GB unified memory 的 Mac Studio Ultra M3，下載 unsloth 的 GLM-5.2-GGUF 2-bit 版本（UD-IQ2_M），總共需要 245GB 記憶體——剛好塞得進你機器。一行 install：`curl -fsSL https://unsloth.ai/install.sh | sh`，一行 run：`./llama.cpp/llama-cli --model unsloth/GLM-5.2-GGUF/UD-IQ2_M/...gguf --temp 1.0 --top-p 0.95`。同樣的權重 744B 總參數 40B active MoE，2-bit 量化後 top-1 accuracy 仍保留約 82%。1-bit 版本更激進——223GB 記憶體、76.2% accuracy、體積比完整模型小 86%。完整未量化版本是 1.5TB，需要一整櫃 H100；今天 unsloth 把這個門檻砍到「單台桌上型機器」。

技術上是兩層配合：第一層 GGUF 量化把模型權重從 float16 壓到 int1/int2/int4 不同精度，每個格式對應一張 quality/size 曲線上的點；第二層 KV cache 量化（cache-type-k/v 從 f32 降到 q4_0/q4_1）把推理時暫存的 attention key/value 也壓縮，省下大塊推理記憶體。Unsloth 額外加 dynamic quantization（UD- 開頭那層）——對 attention head 跟 router 用較高精度保留、對 expert FFN 用低精度壓——同樣 2-bit 平均比例下 accuracy 比 uniform quant 高 4-6%。Apple Silicon 走 llama.cpp Metal 後端，預設啟用 GPU offload，配合 MoE 推理時每 token 只啟動 40B/744B 的少數 expert，速度比想像中可行。

以前要在本地跑 frontier 等級模型（SWE-bench Pro 62.1% / GPQA Diamond 91.2% / AIME 2026 99.2%），你需要兩張 H100 的 vLLM 集群或租 Z.ai API（$4.4/M output token）；現在你的 Mac Studio 一台機器跑 2-bit GLM-5.2，所有資料留在本機。延續 6/18 的「容器設計也要 first-class 化」——當天角度是 1M context + 商業 API price + benchmark，今天角度是 unsloth 量化 + 本地 RAM 表格。對 Henry 的 Nexus packages/ui token review 主線：6/18 提的 GLM-5.2 自架方案從「找兩張 H100」翻成「Mac Studio 256GB 一台」可行性翻倍；客戶採購 deck 的「資料不出本地網路」差異化從口號變成具體 RAM 數字可展示。

## Claude Code v2.1.186——`claude mcp login` 進 CLI、bash 命令輸出自動觸發 Claude 回應

你過去要授權一個 MCP server，得在互動模式打 `/mcp` 開選單、開瀏覽器 OAuth、回 terminal 看結果——在 SSH 環境完全跑不動。v2.1.186（6/22 release）加 `claude mcp login <name>` 跟 `claude mcp logout <name>` 兩個直接 CLI 命令，配上 `--no-browser` 走 stdin redirect 完整 SSH 流程不開瀏覽器。另一件配套：`!` bash 命令現在預設會讓 Claude 自動對輸出回應（不再只當 context），舊行為要在 settings.json 加 `"respondToBashCommands": false` 顯式 opt-out。背景 subagent 的 permission 處理也翻了——過去未在前景的 subagent 撞到 permission prompt 直接 auto-deny，現在會把對話框 surface 到主 session，明確標示「哪個 agent 在問」，Esc 只 deny 那一支工具不影響其他。

技術細節三件：(1) `Agent(type)` deny rule 跟 `Agent(x,y)` allowed-types restriction 過去對 named subagent spawn 不生效，這版修好——延續 6/16 v2.1.178 `Tool(param:value)` 精準權限的設計思路，補上 named subagent 漏網之魚；(2) Workflow `agent({schema})` subagent 過去撞到 schema validation 失敗會無限重試，現在 5 次後 abort，避免燒 token 卡死；(3) sleep wake bug 修好——筆電合蓋過夜醒來 streaming 不再撞「Content block not found」或 JSON parse error。皮膚層也有變：subagent panel 30s auto-hide 之外加 status filter `f` 鍵、Skills 入口進 `/plugin` Installed tab、`teammateMode: "iterm2"` 設定當 auto mode 找不到 it2 CLI 會跳警告。

以前你的 Claude_auto 排程任務在 macOS 喚醒邊界跑會偶發中斷，原因是合蓋 → 喚醒 streaming 連線斷掉沒 retry——這條風險今天歸零，跨晚 fetch 不再需要外掛 wake 防護。`claude mcp login --no-browser` 把 MCP server 配置從「本機 GUI 開瀏覽器」推到「SSH 一條命令」，未來你給遠端 Nexus 開發機接 MCP server 不需要 X11 forwarding。Workflow agent 5 次 abort 機制配上 6/22 Recall 99★ extractive summarization 洞察可以同時動：自我優化迴圈 schema 驗證失敗 5 次 abort、Recall 提供本地 TF-IDF 補位。

## Trust 不是 scalar——typed provenance for agent chains 把信任拆 4 軸

你把 RxJS Observable 想成「一條值的流」，但同時你知道每個值還帶 timestamp、來源、是否新鮮——這篇文章把 agent 輸出的「信任」也拆成同樣 typed metadata。Provenance 不是一個 0-1 信任分數，而是一個 vector：4 個 axes（Freshness 資料新鮮度 / Capability 模型強度 / Tool 工具呼叫是否成功 / Verification 是否驗證過 ground truth）各自 0.0-1.0 獨立打分。資料結構是 `dataclass Provenance(axes: dict[Axis, float], tainted_by: dict[Axis, set[str]])`——除了 axis 分數，還記錄是哪一步上游讓哪一軸退化。Merge 上游 provenance 時用 **`min` per axis 而非 average**，因為「averaging 正是把危險軸洗掉的方法」。

關鍵分離：**provenance 是值「怎麼產生」的 metadata；trust 是 consumer「要不要採用」的判斷**。同一份退化過的輸出，給兩個下游 consumer 處理結果可能完全相反：summarization step 可以容忍弱模型但需要新鮮資料、price calculation 需要新鮮資料但可以接受弱模型。Scalar trust flag 一刀切——要嘛兩個都 reject（過度防衛），要嘛兩個都 pass（過度放行）。Vector 讓每個 consumer 用自己的 `Policy(floors: dict[Axis, float])` 設門檻，同一份 provenance 在下游做出不同決策。文章建議實作節制：每個 axis 必須對應**不同的 recovery action**才加（refetch 對 Freshness、reroute 對 Capability、escalate 對 Verification），兩軸若永遠一起動、觸發相同回應，就合併成一軸。

以前你的 RxJS forkJoin 在 MES 戰情室並行 API 拿多源資料，每筆只帶值本身，可信度是 binary（成功 / 失敗）——上游一個 API 慢了 30 秒回，下游圖表還是當「正常資料」畫上去。這個 typed provenance 概念可以直接套——forkJoin 改成 `forkJoin({stream1, stream2}).pipe(map(...))` 後在 map 內附加 4 軸 provenance，下游 ECharts series 根據自己的 floor 決定是 grey-out 還是顯示。對 Henry Nexus packages/ui 設計 token 鏈：Figma → JSON → CSS Token → Angular 三段轉換，每段都可能退化（Figma export 漏 token、JSON schema 過時、CSS Custom Property override），每段帶 provenance 4 軸（Freshness/Capability/Tool/Verification）讓 consumer（packages/ui CI / Storybook / Angular runtime）各自決定要不要套用。

## 今日總結

今天 4 條獨立路徑同一個工程動作——**「verdict 從 scalar 升格為 traceable vector」**：

- **LLM-as-judge 0.85 vs trace-based 0.000**：agent 答案的 verdict 從「judge 給的單一分數」升格為「access policy + event log + artifact timestamp 三件可機械檢查的 contract」
- **GLM-5.2 unsloth 量化表（1-bit 76.2% → 8-bit）**：模型可用性的 verdict 從「能不能跑」二元升格為「在多少 RAM 下能跑多高 accuracy」的連續曲線
- **Claude Code v2.1.186 named subagent permission**：subagent 行為的 verdict 從「auto-deny / allow」二元升格為「surface 到主 session 並標示哪個 agent 在問」可追溯動作
- **Typed provenance 4 軸 + min merge**：agent 輸出的 verdict 從「scalar trust flag」升格為「Freshness/Capability/Tool/Verification 4 軸 + tainted_by 上游追溯」vector

延續 6/22「procedure 升格為基礎設施一級物件（可壓縮 / 可合規 / 可拆解 / 可分發 / 可延遲抽象）」推到下一層——procedure 升格之後，承載 procedure 的「verdict」（評估結果、可用性判斷、權限決策、信任分數）也要 first-class 化：可追溯（trace contract）、可量化（量化表）、可標示（surface + tainted_by）、可組合（per-axis policy floor）。對應 5/27「契約 first-class 物件本身的『屬性』也要 first-class 化」的下一個刻度——以前 verdict 是「打個分數說 OK」一件事，現在 verdict 升格為「分數本身要可被驗證、可被追溯、可被組合」三維可量化工程目標。
