# 2026-06-02 學習日誌

## shadcn 4.10.0 — GitHub Registries 把「任何公開 repo」變成 `pnpm dlx shadcn add` 可用源

你在 Nexus 已經做完 packages/ui 元件庫 + 自家 CLI（`npx @nexus/cli add`），現在 shadcn 6/1 釋出 4.10.0 把「registry」這層拉到 **任何 GitHub 公開 repo**：repo 根目錄丟一個 `registry.json`、定義 items + files + target，使用者直接跑 `pnpm dlx shadcn@latest add <owner>/<repo>/<item>` 就拉得到。同版本還支援版本鎖定（`#v1.0.0` 或 commit SHA）、`--dry-run` / `--diff` / `--view` 預覽、`registryDependencies` 跨 repo 相依、巢狀 `include` 把大型 registry 拆檔組織；驗證面有 `registry validate <owner>/<repo>` 跑 schema + files exist + dependencies resolve 三件事。前一版 **4.9.0（5/31）** 加了 `npx shadcn eject`——以前裝完 shadcn 元件改不回 npm 套件、現在 eject 把元件「打包」出來；**4.8.3（5/29）** 補 template 處理與 RTL transform 在 className 內 quote 保留兩個 bug。

設計意義有三層。第一層是 **「registry」這層從 SaaS 撤回到 git**——以前 component distribution 是 npm（黑盒、要發版）、或 shadcn 自家 registry server（要中心化託管），4.10.0 把這層直接架在 GitHub 公開 repo 上、不必額外 host。第二層是 **registry 不只是元件**——文件明說可以放 prettier / tsconfig / vitest config、CI/CD workflows、agent rules（CLAUDE.md / AGENTS.md）、testing setups、automation scripts；換句話說「shadcn add」變成 **任何工程慣例的分發協議**。第三層是 **版本控管的層級對齊**——`#commitSHA` / `#tag` / `#branch` 把 component 版本綁到 git ref，跟 npm semver 平行存在；對應 5/26 你看到的 shadcn v4.8.0「registry validate」postulate，這次再往上推：registry 不只能驗證、還能從任何 GitHub repo 安裝、還能鎖到 SHA。

以前你做 Nexus，CLI 是「使用者要先裝 @nexus/cli」、components 要走 npm publish 流程、企業客戶吃私有 registry token；現在 shadcn 4.10.0 直接示範另一條路：**Nexus 自己變成一個 GitHub registry**。具體做法：(1) 在 `chang-shih-yung/nexus` repo 根目錄放 `registry.json`、把 packages/ui 各元件 + tokens + AGENTS.md + CI workflow 全列成 items，使用者跑 `pnpm dlx shadcn@latest add chang-shih-yung/nexus/data-card` 就拉到一份元件 + 必要 token + 對應 ESLint 規則一次裝進專案；(2) 用 `registryDependencies` 把 `card → tokens → icons` 相依顯式表達，跟 5/27 你看到的「契約 first-class 化」同源——以前相依靠 README 寫，現在升格為 first-class 欄位；(3) 對企業客戶推「Nexus design system as a registry」這個 narrative，把「設計 token + 元件 + a11y 規則 + CI gate」一次性 `add` 進客戶 monorepo；(4) `4.9.0 npx shadcn eject` 給「想接 Nexus 但怕 vendor lock-in」的客戶一個明確退場路徑——這條退場路徑反而是賣點。對 Claude_auto 的延伸：把 `.claude/skills/auto-learning/` 也 expose 成 registry item，別人想複製這套 daily digest 工作流，`pnpm dlx shadcn add chang-shih-yung/auto-learning/skill` 直接拿到。

## Debloating The AI-Grown Codebase — `/goal-sloc` 把 19,772 行 Flutter 砍到 13,509 行（31.7%）335 測試全綠

你在 Nexus 主導 60% AI 生成元件，最頭痛的事不是「AI 寫錯」而是「AI 寫對但寫太多」——Maxim Saplin 6/1 在 dev.to 公開了一份戰報：一個 ~20,000 行 Flutter 媒體播放器 app，用一支自製的 Claude Code skill `/goal-sloc` + Opus 4.8 `/goal` 模式跑一個週末，**總 app code 從 19,772 行降到 13,509 行（-31.7%）**、其中 **Dart 程式從 15,859 行降到 9,924 行（-40%）**、**335 個測試全程綠燈**、**順手挖出 2 個隱性 bug 修掉**。技巧不是「叫 Claude 刪程式碼」——這樣 AI 會 **作弊**：把註解、空白行、ASCII 圖砍光來衝指標。`/goal-sloc` 的核心是反作弊規則：preflight 檢查跑測試確認 baseline、**「誠實減量順序」**（先 dead code、再 placeholder 子系統、再 dev scaffolding、再重複）、**self-audit 規則**把每一次 reduction 分類成「結構性 vs cheap」（cheap = 純註解 / 純格式化、結構性 = 真的拿掉一層抽象），cheap 不能算分。

他點名的「AI 增重模式」六種值得記下來：(1) **冗長 README + 解釋顯而易見的程式碼的註解**——Claude 把 prompt 解釋寫進註解的習慣；(2) **placeholder 子系統全接好但沒功能**——AI 把「之後可能要的東西」先 wire 起來；(3) **正式檔裡留 debug / test 程式碼**；(4) **多餘的狀態層 mirror 其他層**——Provider 包 ChangeNotifier 包 Riverpod state 包 BLoC 這種；(5) **過度工程 scaffolding（managers / services / providers）圍著一個 feature 轉**；(6) **No-op 抽象——為了一個已經消失的問題而存在的層**。這六種痕跡正好補上 5/30 你看到的 aislop（192★ 6 大類別掃描器）漏掉的「跨檔結構性增重」——aislop 抓 `as any` / 幻覺 import / 重複 helper 這些 **單檔局部** smell，`/goal-sloc` 抓 **跨檔系統性** 增重，兩者組合就把「AI 生成程式碼怎麼客觀控管」的兩個維度都覆蓋了。

以前你 review Nexus AI 生成元件，判斷「這個 Provider 多包一層是不是必要」「這個 store 跟元件 props 是不是重複狀態」都是手感題；現在 `/goal-sloc` 把這條 review pipeline 結構化：preflight 跑測試 + 標 baseline 行數、按優先序砍、self-audit 強迫分類、stop condition 防 endless refactoring。對 Nexus 直接套：(1) 每個 sprint 結束跑一次 `/goal-sloc` 對 packages/ui 全包，sprint 累積的 AI 生成 noise 一次清掉；(2) `self-audit` 規則改成 Nexus 專屬版本——「以下這幾種 Angular 增重模式優先砍」（NgRx store mirror props、無用 RxJS pipe 層、Service 包 Service）；(3) 對企業客戶的「設計系統 onboarding」加一條「導入後 6 個月自動跑一次 `/goal-sloc`」，把「設計系統用久會膨脹」這個事實先講清楚、解法也先給。對應 5/28 你看到的 Hermes 30 天 4-5 → 1 prompt 收斂——`/goal-sloc` 是「AI 增 → AI 減」的閉環，補上 5/28 缺的下半段。

## Nobody installs your MCP server — 「第二次安裝」這個漏掉的 onboarding 階段

你在 Nexus 已經實作 MCP Server 對 Claude / Cursor 暴露元件查詢介面、5/29 學到 Quandri 量化的 65× token 成本，現在 6/1 dev.to Carl-W 另一篇從 **採用率** 角度切：MCP server 採用有 **兩個** 安裝門檻，傳統 docs 只解第一個。**第一個安裝**是技術連線——使用者在 Claude Desktop / Cursor / Windsurf 各自的 config 檔（每個 client 格式 + 路徑 + 欄位名都不同）填 JSON、貼 API key、重啟 client、看到一個 ✅ 圖示；這層 docs 通常都有。**第二個安裝**才是真正的採用——使用者連上之後回到 chat box，**面對一個空白 prompt 不知道能幹嘛**、模型不會主動宣告連到新 server、不會 suggest「你現在多了 X 能力」，於是「連上但不用」變成 MCP server 默默死掉的最大原因。作者引述：「他們連上、回到工具、盯著空白 prompt、然後離開。」

提出的解法是 **dedicated onboarding 頁** 而不是 `npm i + 改 config`：(1) 按 client 切 tab 各放對應的 config block；(2) 預先生 API key（不要叫使用者再去 dashboard 翻）；(3) 真實 verify 第一次 tool call（裝完跑一條 test query 確認真的能用）；(4) 提供 **starter prompts** 給使用者直接貼進 chat box（這是「第二次安裝」的關鍵——把「能用什麼」具體成可貼指令）；(5) 跟 agent rules（CLAUDE.md / cursor rules）整合，把 capability 持續寫進 agent context 而不是仰賴模型自己想到。作者預測：「一年內 README 配 config block 作為主要安裝路徑會死」——native distribution（Claude 的 connector directory 之類）會把整個安裝體驗搬進工具自己的 UI。

以前你做 Nexus MCP，docs 就是 README 一段 JSON config + 一句「貼進 claude_desktop_config.json 重啟 Claude」，然後等使用者來問為什麼沒反應；現在你看到「第二次安裝」這個未命名階段，會重新設計 onboarding：(1) docs 加 **starter prompts pack**——「列出我的設計系統有哪些 button variants」「比對 Figma frame 1234 跟 packages/ui 對應元件的差異」「找出沒用 token 寫死顏色的元件」這 10 條 starter prompts 直接給使用者貼；(2) MCP server 第一次被叫到時回一段 **welcome message** 列當前可用 tool + 一句 example prompt（5/27 v2.1.152 `MessageDisplay` hook 剛開放，正好可以做這層 server-to-user 引導）；(3) 對企業客戶推 Nexus MCP onboarding 從「文件 + config」升級成「dedicated 內網頁面：選你的 client、一鍵生 token、跑 verify query、複製 5 條 starter prompts」；(4) 結構上呼應 6/2 上一篇 CS336 CLAUDE.md 的「SHOULD 正面表列」——MCP server 也該有一份「這台 server 提供的能力 + 範例 prompt」首屏，把「連上但不知道能幹嘛」這個 gap 用文字填掉。對 Claude_auto SKILL.md 的延伸：把 SKILL.md 開頭那段「可用技能列表」改寫成 starter prompts 風格（不是「我能做什麼」，是「你可以對我說什麼」），讓未來別人 fork 這個 skill 第一眼看到能幹嘛。

## Claude Code v2.1.158 → v2.1.160 — Auto mode 上 Bedrock/Vertex/Foundry，shell startup file 寫入加 prompt
