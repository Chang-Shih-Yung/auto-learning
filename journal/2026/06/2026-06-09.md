# 2026-06-09 學習日誌

## Xiaomi MiMo TileRT：8 張商品 GPU 跑 1T 參數模型，每秒 1000+ tokens

你以前以為「1 兆參數模型推理速度卡在 60-80 tokens/s 是 LLM 物理限制」——Xiaomi 6/8 釋出的 MiMo-V2.5-Pro-UltraSpeed 把這條物理重新繪製：1T 參數 MoE 模型在「單一標準 8-GPU 商品節點」上跑出 1000+ tokens/s decode（real-time 約 1200 tokens/s），15× 快過 ChatGPT 或 Claude 的一般推理速度。Limited-time API 6/9-6/23 開放申請（標準 MiMo 三倍價但十倍速），FP4 quantized checkpoint 直接開源在 `huggingface.co/XiaomiMiMo/MiMo-V2.5-Pro-FP4-DFlash`，Cerebras 跟 Groq 那條「靠專用硬體把 LLM 推理拉到 1000+ tokens/s」的路線今天第一次被「commodity GPU + 三層工程選擇」走通。

技術上是三層獨立優化相乘起來達成 15× 提速。第一層 FP4 quantization 只壓 MoE Experts 那塊權重（其他位置保持原始精度），訓練階段直接走 QAT 把「量化後權重算 loss」整合進 forward pass，FP4 capability 跟原 model essentially on par。第二層 DFlash speculative decoding 不做傳統 sequential drafting（draft model 一個 token 一個 token 預測再交 target model 驗證），改成 block-level masked parallel prediction——單次 forward pass 填滿一整個 block 的 masked positions，acceptance length 4.29-6.30 tokens（依場景）。第三層 TileRT runtime 把推理路徑換成 persistent kernel execution model，消除傳統 operator boundaries 的同步開銷。三層獨立工程但相乘起來才達到「15× ChatGPT 速度」的最終數字。

以前 Henry 的 MES 戰情室要在 ECharts dashboard 加「AI 自動註解」這條功能（operator 看到一條異常曲線，後台叫 LLM 看截圖回「這個 spike 跟 5 分鐘前那條相似、可能是 X 機台 sensor drift」）——做了會發現 LLM 回應 3-5 秒，使用者已經滑到下一頁，整個 feature 變成「只能離線批次跑」。MiMo 把這條物理改變：1000+ tokens/s decode 代表「異常曲線截圖 → AI 註解出來」可以壓到 sub-second，第一次能放進實時 dashboard 而不破壞 interaction 節奏。對應 6/6 Gemma 4 QAT 那條「on-device 1GB」路徑，今天 MiMo 走的是另一邊：「雲端但 commodity 硬體 + 三層 stack」，兩條路一起把 LLM 從「離線批次工具」推進「實時互動 substrate」。

## Claude Code v2.1.169：`--safe-mode` 把 debug 動作從翻七個檔案壓成一個 flag

你在跑 Claude_auto 排程的時候遇到「明明昨天還好今天就壞」這種狀況——以前的 debug 流程是：grep `~/.claude/CLAUDE.md`、`.claude/CLAUDE.md`、`.claude/settings.json`、`.claude/skills/auto-learning/SKILL.md`、`.mcp.json`、plugins/ 目錄、env vars 七個地方一個一個排除，30 分鐘起跳。Claude Code v2.1.169（6/8 release）多三件直接打中這條場景的工具：`--safe-mode` flag 啟動時直接跳過 CLAUDE.md / plugins / skills 全部客製，把 session 縮回「只有 Anthropic 預設」的 anchor 狀態；`/cd` 命令讓 session 移到新工作目錄而不破壞 prompt cache（以前要重開 session 失去整段 conversation）；`disableBundledSkills` setting + env var 把 Anthropic 內建 skills/commands 對模型隱藏，你想客製 SKILL.md 時模型不會偷偷跑回 Anthropic 預設的 `/code-review` `/simplify` 等指令。

背後同一個工程動作：把「debug 時你需要一個保證能跑的 anchor」這個需求從「使用者自己 backup + restore」升格為一級 CLI surface。以前 Claude Code session 同時載入 ~/.claude/CLAUDE.md（user 層）+ .claude/CLAUDE.md（project 層）+ settings.json（permission 層）+ skills/（capability 層）+ plugins/（packaging 層）+ MCP servers（integration 層）+ env vars（runtime 層）七層 context 疊在一起，任何一層壞了出現的症狀都長一樣：「model 不做你期望的事」。`--safe-mode` 跟 Linux `init=/bin/sh` 同源——給你一個「我知道這個 mode 一定能跑」的 anchor，從這裡反推誰壞了；`disableBundledSkills` 是 anchor 的另一面，告訴 model「即使 Anthropic 內建 skill 在，這次也當作沒看到」，避免「客製 SKILL.md 跟內建 skill 衝突」這條隱性失敗模式。

以前 Henry 排程的 Claude_auto 出問題時要打開 launchd plist + memory/learning-context.md + .claude/skills/auto-learning/SKILL.md + ~/.claude/CLAUDE.md 四個檔案 binary search——現在 `claude --safe-mode -p "echo test"` 一行確認 Claude Code 本身沒壞、再回正常 mode 開始找哪一層壞了，debug 時間從 30 分鐘壓到 2 分鐘。配合 6/5 v2.1.163 釋出的 `requiredMinimumVersion` managed setting，現在你的 `.claude/settings.json` 可以同時鎖「Claude Code 版本 ≥ 2.1.169」+ 「啟動先跑 --safe-mode anchor」兩條保證，把整套 Claude_auto 從「希望它跑」升格為「明確可診斷」。

## Magnitude（~1.9k★）：vision-first AI 測試框架把 selector 層拔掉

你的 Nexus packages/ui 元件庫每加一個 Button variant 都要記得加 `data-testid="button-primary-lg"`、QA 寫 Playwright `page.click('[data-testid="button-primary-lg"]')`、CI 跑 e2e——下次設計改 className、改 DOM 結構、把整個按鈕從 `<button>` 換成 `<a role="button">`，所有 selector 都壞了，CI 紅燈，前端工程師回頭加 testid。Magnitude 是 6/8 Show HN 第 3 名（179 點 44 留言）約 1,900★ 的 open-source AI-native 瀏覽器測試框架，把這條 selector substrate 整個拔掉：你寫 `act("Click the submit button")`、`check("Verify dashboard is visible")` 自然語言，雙 AI agent 跑「vision-first」模式——一個 agent 看截圖判斷該點哪裡、另一個 agent 看截圖判斷有沒有達到斷言狀態，完全不靠 CSS selector / data-testid / XPath。

技術上是把 Playwright 那層 selector layer 換成「視覺 + 自然語言意圖」當 selector substrate。Playwright 寫 `page.click('button[data-testid="submit"]')` 要求 frontend 維護 data-testid 不變；Magnitude 寫 `act("Click the submit button")` 把這個判斷推給 vision model（看截圖找 submit button）。兩條路差別在 UI 改了之後誰負責：Playwright 路線是「selector 壞 → CI 紅燈 → 前端加 testid」、Magnitude 路線是「button 外觀改了 → vision model 還能認出來 → CI 繼續綠」。trade-off 是 vision model 有 noise（同一個 button 偶爾被認成「Send」）、token cost 跟 latency 比純 selector 高一個量級、視覺辨識的可重現性（同一張截圖兩次跑可能略不同）需要 retry / temperature 控制。

以前 Henry 的 Nexus packages/ui 元件庫 e2e test 走 Playwright + data-testid 路線，每加一個 variant 都要前端記得加 testid、QA 寫 selector、CI 跑——現在 Magnitude 提供「視覺 + 意圖」路線給 design system 元件 test：寫一個 test 說 `act("Open the Button story with size=lg, variant=primary")`、`check("Button shows 'Click me' with primary background")`，元件 variant 換、props 改、設計 token 換主題色，這個 test 不動。對 packages/ui 的 visual regression layer 變成兩條互補：Percy screenshot diff 答「視覺一致嗎」、Magnitude 答「功能對嗎」。一條看 pixel、一條看意圖。

## dev.to「Skill, MCP, Plugin, or just a CLI: lightest first」：Claude Code 擴充的反潮預設

你在規劃 Claude_auto 或 Nexus 接 Claude Code 整合時的直覺是「先做 MCP server」——最潮、最高科技、看起來最完整。dev.to rapls 6/8 這篇給你一張反方向的四選一決策樹：(1) **Skill** — 用於 procedure 跟 knowledge，預設首選；(2) **CLI from Skill** — 偶爾需要外部資料且 CLI 已存在；(3) **MCP** — 需要 live data、深度日常整合、結構化存取；(4) **Plugin** — 用於打包+分發以上三種。作者標的數字：MCP tool definitions 一旦載入吃 context window 49.3%（接續 5/30「MCP is Dead」65× token 差距那條主線推到「lightest first」default）；GitHub MCP 27 個 tool 約 18k tokens、每 turn 都載入、不管你那個 turn 有沒有用到；對比 Skill 啟動時只載 name + description、full content 按需開啟。

背後原則是「nested, not flat choices」——Plugin 裝 Skills 跟 MCP configs；Skill 可以叫 CLI tool。作者實作例：標準化 commit message → Skill（一條 procedure）；檢查 staging post 數 → CLI invoked from Skill（偶爾用、wp-cli 已存在）；每天操作 production dashboard → MCP（高頻 + 結構化）；分發 release steps → Plugin（打包 + 分享）。常見錯誤是「拿 Skill 去抓 live WordPress.org 統計」——Skill「沒有腳走出去」（no legs to go outside），這需要 CLI 或 MCP。把選 extension type 的責任從「先選最潮」改成「先選最輕能跑的」是這篇的核心反潮論點。

以前 Henry 寫 Claude_auto 或規劃 Nexus 接 Claude Code 都會直覺先做 MCP——現在這篇給你一個明確的 default：先問「能不能寫成 SKILL.md procedure？」、不能再問「能不能 wrap 既有 CLI（pnpm dlx shadcn add / figma-cli）」、再不能才升級到 MCP。對 Claude_auto SKILL.md 體檢直接命中：抓 sources、過濾、寫 journal、commit、push 五階段都是 procedure + WebFetch + Bash，整套工作流根本不需要 MCP server。對 Nexus packages/ui 接 Claude Code 整合的 roadmap 也是同一條 default：「先做 Skill 拆 design token + 生成 component」→「需要 Figma live state 才升級 MCP」，省下 ~40% context budget 給實際工作。

## 今日總結

今天四條獨立路徑收斂到同一個工程動作：**「每一層 substrate 都被『換成最輕的選擇』這個動作刷新預設值」**——延續 6/8「責任歸屬重新分配」推到下一層：責任搬完之後，每個責任分配下游的「實作 substrate」也要選最輕的選擇，不必為了看起來完整而扛重的層級。

- **MiMo TileRT**：1T 模型推理 substrate 從「Cerebras / Groq 專用硬體」換成「commodity 8-GPU + 三層工程選擇（FP4 + DFlash + TileRT）」，1000+ tokens/s 證明「最輕的硬體 + 最厚的軟體 stack」可以贏過「最重的硬體 + 標準軟體」
- **Claude Code v2.1.169**：debug substrate 從「使用者自己 grep 七個檔案 backup + restore」換成「`--safe-mode` 一個 flag 啟動 anchor」，30 分鐘 debug 壓到 2 分鐘 binary search
- **Magnitude**：e2e test substrate 從「CSS selector + data-testid + retry + wait-for」換成「vision + natural language intent」，UI 改了測試不動，責任從「前端維護 testid」轉嫁到「LLM 認得對」
- **Lightest-first extension picker**：Claude Code 擴充 substrate 從「先做 MCP 看起來最潮」換成「先做 Skill 再升級」，省 ~40% context budget 給實際工作

這四件事同時動的意義：5/27「契約 first-class 物件本身的『屬性』也要 first-class 化」這條主線推到下一個維度——**「substrate 的重量」這個屬性也要 first-class 化**。當你做架構決策時要明確問「這層 substrate 我選的是最輕能達成目標的選擇嗎？還是因為看起來完整選了重的？」——MiMo 選最輕的硬體（commodity GPU 而非 Cerebras）、CC v2.1.169 選最輕的 debug 動作（一個 flag 而非整套 backup script）、Magnitude 選最輕的 test 表達（自然語言而非 selector tree）、lightest-first 選最輕的擴充類型（Skill 而非 MCP）——四件事的共同 default。

對 Henry 的三條工作脈絡可同時動：
1. **MES 戰情室**：拿 MiMo 1000+ tokens/s 那條 substrate 規劃「異常曲線 sub-second AI 註解」feature；以前因為 LLM 回應 3-5 秒被當成「只能離線批次」，今天 substrate 換掉後可以放進實時 dashboard
2. **Claude_auto SKILL.md 體檢**：(a) 用 `--safe-mode` 寫 doctor 腳本 anchor-based debug、(b) frontmatter 加 `requiredMinimumVersion: 2.1.169`、(c) 拒絕未來加 MCP server，把 SKILL.md procedure 路線跑到盡頭
3. **Nexus packages/ui**：(a) Magnitude vision-first test 接 Storybook 給 design system variant 測試免維護 testid、(b) AI 整合 roadmap 改成「Skill → CLI → MCP」漸進升級 default、(c) 把 MiMo / Gemma 4 12B 雙 substrate（雲端極速 vs 本地 16GB）寫進企業客戶採購 deck 當「Nexus 不鎖 inference provider」中立保證
