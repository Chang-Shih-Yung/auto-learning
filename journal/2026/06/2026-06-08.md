# 2026-06-08 學習日誌

## Linear 把「source of truth」從伺服器搬到瀏覽器，TTFP 改善 59%、記憶體降 70-80%

你在 Mac 上打開 Linear 拖一張 issue 卡片，動作完成那一刻就看見結果——不是「按下後等 300ms」，是「按下即顯示」。同一個 Linear web app 跑在 Safari，time-to-first-paint 比 2025 年版改善 59%、記憶體用量降 70-80%、總 minified JS 21MB 但被切成「幾百個 route-level chunk」按需載入，動畫一律壓在 100ms 以下（業界標準 200-350ms）。Cold cache 載入 10-30% 更快，全靠四次 bundler 換代（Parcel → Rollup → Vite → Rolldown）+ 鎖定現代瀏覽器砍掉 ~50% 程式碼。

這背後的設計反轉是 Linear 工程文章的核心句：「the server as a sync target, not a source of truth」——server 不是真相來源，是同步目標。所有 mutation 先寫 IndexedDB 再透過 WebSocket 非同步送 server，所以你看不到任何 spinner。Service Worker 在登入畫面就 precache ~1,200 個 asset，下次開啟瞬間載入並支援離線。Auth 也是反過來：先檢查 `localStorage.ApplicationStore` 存在就直接 render，憑證在 API call 過程中驗證——把「驗證再渲染」改成「渲染再驗證」。MobX 用 observable 追蹤個別 property，50 個 issue 更新只觸發 50 個 cell 重繪而不是整個 list 重繪。

以前你以為「速度是 server 優化的事」（多台 PostgreSQL replica、CDN edge、HTTP/3）——現在 Linear 證明：當你決定「server 不是真相來源」這個架構選擇，前述優化都不必，瀏覽器自己就是 DB。對 Henry 的 MES 戰情室從「Angular + RxJS forkJoin + SignalR + ECharts」這套以伺服器為中心的即時數據鏈來說，Linear 提供了反方向：把 IndexedDB 當 primary、SignalR 從「推資料」改成「推 sync delta」、ECharts dashboard 從「向 API 要 50 個 issue」改成「向 IndexedDB 要 50 個 issue 並後台同步」——上工操作 1分20秒→20秒的 75% 改善，下一階段可能來自「server 不是 source of truth」這個架構翻轉。

## Google Gemma 4 12B：拿掉 vision/audio encoder，16GB RAM 跑多模態

你的 Mac 16GB 統一記憶體（M2 / M3 / M4 都算）現在可以本地跑 Gemma 4 12B——一次同時吃文字、圖片、音訊三種輸入，performance 接近 Google 自家 26B MoE 模型但記憶體用量不到一半。傳統多模態模型需要 ViT vision encoder（幾百 MB 額外權重）+ Whisper-like audio encoder（再幾百 MB），Gemma 4 12B 全砍——vision 換成「單一矩陣乘法 + position embedding + normalization」的 lightweight embedding module，audio 直接把原始訊號投影到跟 text token 同一個 dimensional space，是 Google 第一個原生支援 audio 輸入的中型模型。

這個架構選擇背後的工程結論是「encoder 這層其實是 legacy」——2020-2024 主流是「modality-specific encoder → projection layer → LLM」，每加一個 modality 多一個專門訓練的 encoder。Gemma 4 12B 證明你可以把這層整個拿掉，直接讓 transformer 自己學會跨 modality 對齊，省下來的記憶體預算用在更深的 decoder。模型在 Hugging Face Transformers / llama.cpp / MLX / vLLM 全平台立刻可用、Apache 2.0 license、Google Cloud Model Garden + Cloud Run + GKE 部署選項都有，Gemma 系列累積已破 1.5 億下載。

以前你要做「螢幕截圖 → LLM 看 UI → 給出 UX 建議」這條工作流，得串 GPT-4o vision API 或開 Anthropic Claude Vision 帳號、token 走網路、Figma file 不能外送——現在同一條工作流可以放本機 Apple Silicon 跑，Figma 設計稿截圖丟給 Gemma 4 12B，要它對照 design token JSON 判斷「這個 spacing 跟 OKLCH 主題哪裡不一致」——回應 0 token cost、0 round-trip、0 data exfiltration。對 Nexus packages/ui 的 design token QA 工作流是直接的下一個實驗檔次：把 visual regression 從 Percy screenshot diff 升級到「Gemma 4 12B 看截圖 + 對照 token JSON 給出文字 review」，本地跑、Apache 2.0、無雲端依賴。

## Lathe（555★）：LLM 不是替你寫，是教你寫

你想學 distributed systems 但找不到好的線上課程、ChatGPT 給你答案太快讓你跳過理解、官方文件假設你已經懂 80%。Lathe 是 6/7 Show HN 第 12 名（247 點）、555★ Go 寫的 CLI，安裝 `brew install devenjarvis/tap/lathe` 後給它一個自然語言 prompt（例：「教我怎麼從零實作一個 Raft consensus 模組」），它生成多章節 hands-on tutorial：每段有概念解釋、原始碼附 attribution、檢查點 exercises（要你動手算/動手寫）、deeper-thinking 旁註、optional skill 驗證測試。寫作 tone 可以選「voices」（嚴謹 academic / 對話風格 / 簡潔 reference）但事實性鎖死不放鬆。Library 介面有 tag / status / version 搜尋。

技術上 Lathe 把「LLM 角色」這個 substrate 從「答案產生器」翻成「教學設計者」——同樣呼叫 frontier model（Claude/GPT），但 prompt 結構強制要求「先給 exercise 再給解答、先給 sub-note 再給結論、每段帶 source attribution」，配合本地 web UI 走 markdown render + checkpoint state，避免使用者一鍵跳到最後一行答案。作者 Deven Jarvis 的核心句是「use LLMs to teach you, rather than think for you」——這是對 6/7 那篇 HN 811 點「LLMs are eroding my software engineering career」最直接的工程回應：問題不在 LLM，在使用者把 LLM 當捷徑。

以前你要學一個新領域（你正在學的 SQL / Containers）有三條路：花錢買 Udemy 課程（內容固定 + 兩年前過時）、看官方文件（假設你已懂前提）、問 ChatGPT（給答案太快讓你跳過理解）——現在第四條路出現：給 Lathe 一個 prompt，得到一份按你目前等級量身打造的 hands-on tutorial，每段強迫你動手才能繼續。對 Henry 的「做中學」學習偏好（user-profile.md 明列）這是直接命中：SQL 不必再從 W3Schools 那種「先看範例再寫」開始，而是 prompt Lathe「教我怎麼從 Angular MVVM 已有的 RxJS forkJoin 經驗對接到 SQL window function」，得到一份從你既有知識點切入的 tutorial。

## office-open-xml-viewer：Claude 全自動寫出 184★ WASM 文件渲染引擎

你想在瀏覽器裡開 DOCX / XLSX / PPTX 而不用上傳到 server（公司資料不能外送、客戶要在 PWA 裡預覽合約）——以前要嘛走 server-side LibreOffice / Aspose（後端維護、隱私問題）、要嘛靠 Google Docs viewer iframe（檔案要 public、跨域、UI 寫死）。office-open-xml-viewer 給第三條路：Rust 寫 parser 編譯成 WebAssembly，main thread 走 Canvas 2D 渲染，Web Worker 跑解析，整套在瀏覽器 tab 內完成、預設零外連、ZIP 解壓縮有 cap 擋 zip bomb。Headless API（`DocxDocument` / `XlsxWorkbook` / `PptxPresentation`）讓你自己組 UI 不被內建介面綁住，math 公式走 optional MathJax tree-shake 出去省 bundle，文字可選取可複製。

整個 codebase 的工程故事比技術本身更有意思：作者明說「the entire codebase was implemented by Claude through iterative prompting, with no human-written application code」——TypeScript 49.8% + Rust 45.6% + Astro 2.1% 三語言混合、71 個 release、5 個 fork、184★，全部由 Claude 迭代寫出。這驗證了 5/30 主線「跑得久、跑得多線、跑得有客觀驗證」的下一個極端案例：一個原本需要小團隊三季 sprint 的「跨格式文件 viewer」工程量，現在被「人類定 spec → Claude 寫 + 71 次迭代釋出」這條 pipeline 吃下來。

## 今日總結

今天四條獨立路徑收斂到同一個工程動作：**「責任歸屬」的重新分配**——延續 6/7「AI agent 操作世界的正確粒度正在被重定位」推到下一層：粒度選好之後，每個粒度的「誰負責、責任放哪裡」也是一級工程決定，而且常常逆向（從 server 搬到 client、從 specialized encoder 搬到 unified transformer、從 LLM 搬回使用者、從工程團隊搬到 architect + AI）。

- **Linear**：source of truth 責任從 server 搬到 client（IndexedDB primary + WebSocket sync target），TTFP 59% + 記憶體 70-80% 改善的工程地基不在 backend 優化、在「誰是真相來源」這個架構翻轉
- **Gemma 4 12B**：多模態理解責任從 specialized encoder（ViT / Whisper）搬到 unified transformer（單一矩陣 + projection），16GB Mac 第一次原生跑「文字+圖片+音訊」三模態
- **Lathe**：「學會」責任從 LLM 搬回使用者，LLM 角色 substrate 從「答案產生器」翻成「教學設計者」，對應 6/7 Jane Street「不替你做、跟你一起做」同一條哲學
- **office-open-xml-viewer**：「能不能交付這個 library」責任從工程團隊搬到 architect + iterative Claude prompting，184★ + 71 個 release 證明單人可達成傳統三季工程量

這四件事同時動的意義：5/27「契約 first-class 物件本身的『屬性』也要 first-class 化」這條主線推到下一個維度——**「責任歸屬」這個屬性也要 first-class 化**。當你做架構決策時要明確問「latency 責任在 server 還是 client」「多模態理解責任在 encoder 還是 transformer」「學會的責任在 LLM 還是使用者」「交付的責任在團隊還是 architect+AI」——這些以前隱含的選擇現在每一個都是顯式的工程決定。
