## GLM-5.2 在 Semgrep IDOR cyber benchmark 39% 贏過 Claude Opus 4.8 28%——open weights 從 general benchmark 推到 production security 任務

你跑 Nexus packages/ui SAST review、或想把 Claude API 換成自架 model 跑安全任務時，這份 Semgrep 6/28 公開的 IDOR（Insecure Direct Object Reference）benchmark 第一次給出可重現數字：**GLM-5.2 在最簡 prompt + 最簡 harness 下 F1 score 39%、Claude Code（Opus 4.6）37%、Claude Code（Opus 4.8）28%、Semgrep 自家 Multimodal 配 GPT-5.5 61%、Multimodal 配 Opus 4.8 53%**。同時間經濟學：GLM-5.2 每找出一個 vulnerability 約 **$0.17**——「約等於 frontier model 的六分之一成本」。IDOR 是哪種漏洞？「應用把內部 ID（user ID）放進 request 但沒檢查 caller 是不是真的有權存取那個物件」——這要 cross-file 推理「哪些 endpoint 缺少 authz check」，不是 grep 規則找得到的字串 pattern。HN 473 點 231 留言，作者特別加註：「一個任務、一個 dataset、一輪實測」——不要外推到 IDOR 以外。

設計核心翻轉是「open weights agentic capability 不只在 leaderboard 數字，而是 production security 任務上真的能換掉 frontier」。6/18 Z.ai 第一方 API、6/23 unsloth 量化、6/25 Nathan Lambert「GLM-5.2 是 agent 的 DeepSeek moment」三條軸都在「open weights 能不能跟 closed 同檔」這條主線——今天 Semgrep 的數字加上第四維「同樣的最簡 harness、同樣的任務、同樣的評分標準，open weight model 39% 直接贏過 Claude Opus 4.8 28% 11 個百分點」。為什麼差距這麼大？Semgrep 沒給機制解釋，但兩個工程線索值得記：（1）IDOR 偵測是「找『缺』而不是找『有』」——要證明某條 endpoint「應該有 authz 但沒有」，比找已知 vulnerability pattern 難一個量級，模型對「missing structure」的敏感度在這條軸決勝；（2）Semgrep 自家 Multimodal（GPT-5.5 61% / Opus 4.8 53%）甩開兩個 base model 約 14–22 個百分點，證明 harness 設計（multi-pass + 跨檔索引 + RAG）才是真正槓桿，base model 差距在加上對的 scaffold 後可能被吸收。

以前 Henry 的 Nexus packages/ui 想做 design token review 一致性檢查（Figma → JSON → OKLCH → Angular 三段轉換每段可能 drift），6/18 第一方 API + 6/23 量化表 + 6/25 agent benchmark 三條已經把「GLM-5.2 自架 fallback」拉到桌面——今天 Semgrep 的 IDOR 數字補上「security 任務上 open weights 不是 trade-off 是 strict win」的第一份 production 證據。對應 6/26 Scorer vs Decider 條目「LLM 不做決策只打分數、decision 邏輯寫在 60 行 TypeScript」洞察——Semgrep Multimodal 把 GPT-5.5 base 53%（單跑 Opus 4.8）推到 61%（加 harness）正是 Scorer vs Decider 推到 SAST 層的實例：base model 是 scorer，harness（cross-file index + multi-pass）是 decider。對 Henry 三件可同時動：（1）Nexus packages/ui design token review 加 cyber benchmark 對標——把 token JSON drift（authz 缺漏類比）寫成可重現 benchmark 集，GLM-5.2 自架 + Claude API 雙 model 同 harness 跑同份 benchmark 數字攤開取低成本高 F1 那條；（2）packages/ui PR review 接 Semgrep Multimodal 風格 harness 設計——base model 跑單 file pass + 跨 file index pass + 結論 cross-check pass 三段，6/26 Scorer vs Decider tier-policy.ts 直接套到「multi-pass harness 結論信心 ≥ 0.85 才 auto-block PR」；（3）Claude_auto SKILL.md fallback chain 三層（Fable 5 / GLM-5.2 自架 / Gemma 4 12B QAT）的「自架層」從「合規顧慮 fallback」升到「成本/F1 同時優」第一選擇，security-sensitive task 預設走自架層而非 API。

## Claude Code v2.1.195——hook matcher 從 substring 改 exact-match，攻擊面跟 6/26 v2.1.193 同方向再砍一層

你 Claude_auto SKILL.md 用 hook 攔 `code-reviewer` subagent 或 `mcp__brave-search` MCP tool 時，v2.1.195（6/26 release，v2.1.193 一天後）把 hook matcher 從 **substring** 改為 **exact match**。以前 frontmatter 寫 `hooks: { PreToolUse: { matcher: "code-reviewer", command: "..." } }`——「code-reviewer」是 substring，會誤觸到任何含這串字的 tool 名（例如 `code-reviewer-strict`、`pre-code-reviewer-v2`），攻擊者只要塞個 `Tool(code-reviewer-bypass)` 就繞掉。今天 hyphenated matcher 走 exact match——只有完全等於 `code-reviewer` 才命中 hook，繞過 surface 當天消除。其他四件：`CLAUDE_CODE_DISABLE_MOUSE_CLICKS` 環境變數讓 fullscreen 模式關掉滑鼠點擊保留滾輪（給 tmux/screen 用戶誤點 abort），macOS 語音轉文字長 session 切麥克風後不再吃進無聲段，**日中泰三語沒空格也能 auto-submit**（過去語音輸入後要手動 Enter），background job 在版本升級時資料不掉/不消失，crashed background task 重開效能優化。

技術上「hook matcher 從 substring 升 exact match」是這版的結構性變動，跟 6/26 v2.1.193 `autoMode.classifyAllShell`「Bash 命令從子字串比對升分類器判斷」**完全同一條軸**：substring 比對的 attack surface 永遠在於「字串包含關係不等於語意等價」——攻擊者只要在合法 matcher 字串前後加字就繞過。v2.1.193 把這條原則套到 Bash 命令層（`rm*` 子字串擋不住 `bash -c "rm ..."`），v2.1.195 把同原則套到 hook matcher 層（`code-reviewer` substring 擋不住 `code-reviewer-bypass`）——兩天兩版同方向再砍一層 substring matching 的 implicit trust。日中泰語 auto-submit 是另一條軸：過去 voice dictation 用「偵測到空格」當「使用者說完話」的 cue，這條規則對日文「あの新しいAIモデルを使ってみました」、中文「我剛剛試了那個新的 AI 模型」、泰文這類無空格 script 完全失效——今天改用 prosodic boundary（停頓 + 語調下降）當 cue，把「空格 = 邊界」這條英文中心的隱性假設拔掉。

以前 Henry 的 Claude_auto SKILL.md 假設 hook matcher 對名字字串「精確匹配」——其實到 v2.1.195 之前 hyphenated matcher 一直是 substring，攻擊者可以註冊 `code-reviewer-bypass` 這類子字串擴展繞過 hook。今天起 hook matcher 升 exact match，加上 6/26 v2.1.193 `autoMode.classifyAllShell` 雙層配合，整套「permission 從靜態子字串升動態判斷 / 從子字串包含升精確等價」雙軸並進。對應 5/26 Veso AI「safety 用 hook/permission/linting 外部 enforce 而非靠模型聽話」+ 6/22 v2.1.186 named subagent permission 補洞——同一條主線「permission 機制本身要 first-class 化」往前推一格。對 Henry 三件 SKILL.md 升級：（1）frontmatter `requiredMinimumVersion` 從 6/26 v2.1.193 升 v2.1.195 鎖 hook matcher exact-match 修復；（2）排程任務的 voice memo 摘要支援中文 auto-submit，session 結束後可以直接「session 摘要：今天跑了哪些 fetch」中文錄音不用手動按 Enter；（3）background job 升級不掉資料這條 fix 直接對應 Claude_auto 跨晚 fetch——過去手動 update Claude Code 後背景 fetch session 偶發消失，今天起 update 不會中斷已啟動的 Step 1-7 流程。

## Adrafinil——把「macOS 是否睡眠」從靜態 caffeinate 翻成「跟著 agent session 動的 reference-counted assertion」

你跑 Claude_auto 跨晚排程任務時，過去要嘛 `caffeinate -d` 整晚不睡（電腦熱、電池吃緊）、要嘛靠 `pmset` 排定時間段（agent 提早跑完還是醒著）。Adrafinil 開出第三條路：**macOS menu bar app，只在 AI coding agent 真的在工作時才阻止系統睡眠，agent 結束就還原**。設計上是 reference-counted assertion model——agent 啟動時呼叫 `adrafinil acquire <session-key>` 註冊一個 active session，daemon 透過 privileged helper 用 `IOPMAssertion`（擋 idle sleep）+ `pmset disablesleep`（擋合蓋睡眠）阻止睡眠；agent 結束呼叫 `adrafinil release`，所有 session 都 release 後正常睡眠回來。九個 agent CLI 內建 hook 整合：Claude Code、OpenAI Codex、Cursor、Gemini CLI、Aider、Hermes、OpenCode、Cline、Pi——CLI 呼叫 acquire/release 50ms 內 round-trip。額外四件：合蓋觸發音效確認、皮膚/CPU 溫度過熱強制 release（合蓋 + 燙手條件成立時保護硬體優先於 agent 進度）、閒置 N 分鐘自動 release 死 session、開蓋顯示本次 session 執行時長 + 峰值溫度 + 熱事件歷史摘要。

技術上「sleep policy 從靜態翻動態 reference counted」是這套設計的結構性變動。傳統做法兩條：`caffeinate` 整段時間擋睡眠（時間維度死板）、`pmset` 排程表（事件維度死板）——都假設「我知道 agent 何時開始/結束」，但 Claude_auto 排程跑 Step 1-7 七步、每步時間 variance 大，靜態時間框不住。Adrafinil 把這條翻成「agent 自己宣告 active session、daemon 維護 active session counter、counter > 0 阻止睡眠 / counter = 0 還原」——sleep state 跟 agent state 從兩條獨立 timeline 縫成一條因果鏈。Thermal cutout 是另一層：把「擋睡眠」跟「保護硬體」做成 conflict 解決規則——皮膚溫度過閾值 + 合蓋條件同時成立時，強制 release 所有 assertion 讓系統睡眠，硬體保護 override agent 進度。對應 6/17 Wolfram「For AIs」分離渠道思路推到 OS 層——OS 對「使用者 vs agent」兩種 sleep policy 第一次被當成 first-class 區分，過去只有「使用者要不要睡」這條軸。

以前 Henry 的 Claude_auto 排程跑 22:00 後跨晚 fetch，本機要嘛整晚不睡（過熱）、要嘛靠 macOS 內建 `pmset` 排定 `22:00-02:00 disablesleep`（中間跑完早就該睡卻沒睡、跑超時 02:00 後 task 還沒完就睡掉）。Adrafinil 開出第三條路：排程 trigger 時呼叫 `adrafinil acquire claude-auto-nightly`、Step 7 結束呼叫 `release`——Mac 只在 fetch/filter/write/commit/push 真的在跑時擋睡眠，task 早完早睡、跑超時繼續醒。對應 6/18 Claude Code v2.1.181 `CLAUDE_CLIENT_PRESENCE_FILE`（OS 寫狀態檔通知 mobile push 靜音）+ 6/25 v2.1.191 sandbox network 權限對話框記住已批准 host 兩件——同一條軸「OS 跟 agent 之間的協調介面從靜態設定翻成 runtime 雙向 signal」往前推一格。對 Henry 兩件可動：（1）Claude_auto SKILL.md frontmatter 加 `presence-aware: true` 註解，未來如果跟 Adrafinil 整合，排程 trigger 自動 acquire / Step 7 完成自動 release，搭配 thermal cutout 在 M2 Mac 過熱時保護硬體優先；（2）Nexus packages/cli 設計「長時間 task 通用 presence assertion」概念——CLI 開始長任務時宣告 active session、結束時 release，OS / 通知系統 / mobile push 都可以掛這條 signal 做差異化反應。

## antoine MRI 第二意見——multi-subagent arbitration 是 single-context bias 的工程解法

你用 Claude Code 跑長 session 後想再驗證自己的判斷時——antoine.fi 的 MRI 第二意見實驗給了一份很乾淨的 production-grade workflow 範本。**Opus 4.8 (xhigh) 在 Claude Code 內**，**266MB DICOM 檔案**（一個右肩 MRI scan、幾百個無副檔名檔案）丟進去配最簡 prompt「右肩疼 2-3 週、安裝任何需要的 package」——大約**一小時**產出第一份完整分析報告。第一輪 Opus 結論「tendon 完整」，跟臨床放射科醫師結論「subscapularis 頂端 Grade III（>50%）partial-thickness tear」不一致。作者沒就此罷休——進第二輪 **arbitration phase**：Claude 比對「第一輪 AI 結論 + 臨床 radiologist 結論 + ChatGPT 對活動測試的補充討論」，**特意用 multiple subagent 跑這輪 arbitration 避免被前一輪 context bias**。第二輪結論翻轉：「Mild insertional tendinosis；NO discrete partial- or full-thickness tear identified」——靠近臨床診斷的方向但更保守。HN 356 點 459 留言，金句作者沒明寫但 workflow 已自證：**single-context multi-pass 容易陷入「我已經這樣判過了」的 bias，multi-subagent 跑 arbitration 才能拿到真正的第二意見**。

設計核心翻轉是「subagent 不是省 context、而是強制 bias-free 重新判斷」。傳統用法把 subagent 當「平行加速」：主 session 派三個 subagent 同時跑三個獨立任務、結果回主 session 整合——subagent 的價值在於擴大同時處理量。antoine 的用法翻成「**subagent 是 single-context 的 anti-pattern**」：第一輪 Opus 已經給出「tendon 完整」結論，主 session 後續任何「重新判斷」都會被這個結論 prime——即使 prompt 寫「請重新評估」，模型還是會傾向「找理由支持原結論」（confirmation bias 在 LLM 也存在）。Multiple subagent 解這條：每個 subagent 開新 context、只拿到原始 DICOM + 臨床結論 + 補充討論、沒看過第一輪 Opus 判斷——arbitration 從「同一個 model 重新評估自己」翻成「N 個沒看過原始判斷的 model 同條件下獨立判斷」。對應 6/22 Claude Code agent loop 1,400 行 9 種 failure mode「sub-agent completion 父迴圈接續子 agent」洞察推到下一格——subagent completion 不只是「父 agent 接續」，是「父 agent 主動丟掉自己的 context bias 換 subagent 的乾淨視角」。注意一個風險：MRI 的 ground truth（人類放射科醫師）在這篇剛好對齊 subagent 第二輪結論方向，但無法外推到所有領域——arbitration 改善的是 bias，不保證找到真相。

以前 Henry 的 Claude_auto Step 2a 「入選過濾」是 main session 連續跑「fetch → filter → write」三段——filter 階段被 fetch 階段的 context 強烈 prime（剛抓到的標題會影響「值不值得寫」判斷）。Nexus packages/ui PR review 同樣：reviewer agent 看過 PR 描述後跑 cross-file check 會被描述 prime。antoine 的 multi-subagent arbitration 直接打中這條矛盾：把「重要決策」從 main session 拉到獨立 subagent、subagent 只拿 raw artifact + 結論候選列表、不知道 main session 怎麼想——對應 6/26 Scorer vs Decider「LLM 不做決策只打分數」推到下一格「**LLM 的『重新判斷』不能在同 context 內做、要丟給沒看過原判斷的 subagent**」。對 Henry 三件可同時動：（1）Claude_auto SKILL.md Step 2a 升級——main session 跑 fetch 後產 raw 候選 list（不含「值不值得寫」傾向），開 subagent 拿 raw list + Henry skill-taxonomy.yaml 獨立打 relevance 分數，main session 拿分數做 inclusion 決策、不參與 scoring；（2）Nexus packages/ui PR review 拆兩階段——reviewer agent 看完 PR 後產 finding list，arbitrator subagent 拿 finding list + repo 規則獨立打 severity（沒看過原 PR 描述），對應 6/26 Scorer vs Decider tier-policy.ts 但 scoring 跟 deciding 進一步分到不同 context；（3）Step 5 自我優化迴圈——session 結束後開 subagent 拿原始 sources 跟 journal 輸出獨立比對「Henry 真會學到東西嗎」這條 meta-judgment，避免 main session 寫完文章自我感覺良好。
