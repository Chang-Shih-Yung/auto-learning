# 2026-06-11 學習日誌

> 今日主題：**「藏起來的成本」被顯式化、量化、變成可選擇的維度**——DiffusionGemma 把「token-by-token 的延遲成本」翻成可選的 diffusion 設計、PgDog 把「拼三個工具的 ops 成本」翻成單一 Rust 執行檔、Bunq 案例把「retrieved data 是可信的」這個隱含假設的攻擊面顯式化、Apache Burr 把 LangChain chain 抽象藏起來的 state 翻成一級 state machine、CLI over MCP 用 +5k token / turn 把 MCP schema 自動載入的 context tax 量化成可選擇的 trade-off。

## 1. Google DiffusionGemma：26B MoE 把文字生成從「一個一個寫」翻成「一塊一塊降噪」

**來源：** [Google 官方 6/10 release](https://blog.google) · [The New Stack 報導](https://thenewstack.io/google-diffusiongemma-text-diffusion/) · HN 283 點 6/10

你拿一張 RTX 5090（或單張 H100）就能在本地跑 DiffusionGemma，文字產出速度 **700+ tokens/秒**（H100 直接破 **1,000 t/s**）——同樣的硬體跑普通 Gemma 4 26B 一般是 200-250 t/s 級。對應 MES 戰情室戰情看板要 AI 即時註解「上工 1分20秒→20秒」異常曲線的當下，註解一段話從「等好幾秒」壓到「不到 1 秒」，使用者按下「為什麼跌停」幾乎沒有等待感。模型量化後吃 **18 GB VRAM**，26B 參數但每次推理只啟動 **3.8B**（Mixture of Experts），day-zero 支援 vLLM / Transformers / MLX / Unsloth，Apache 2.0。

傳統 LLM 一個 token 接一個 token 寫——每個 token 都要等前一個算完。DiffusionGemma 改用擴散模型那一套：把 **256 個 token 的「畫布」一次全填上隨機噪音**，然後一輪 forward pass 同時把 **15-20 個 token 從噪音「降噪」成正確答案**，跑十幾輪就把整塊填滿。bidirectional attention 看得到前後文，低 confidence 的 token 可以下一輪被「重新噪音化」再降一次——這是自回歸模型做不到的「邊寫邊改」。代價：同樣 benchmark 比標準 Gemma 4 略低一截，Google 自己標明「prioritizes speed and parallel layout generation」、「output quality is lower than standard Gemma 4」。

以前你要文字 token 跑超快，要嘛搬到 Cerebras / Groq 雲端硬體（每 token 0.5 ms 但帳單按請求數累），要嘛接受 Gemma 4 級別 200 t/s 的常識天花板。現在 Apache 2.0 開源、Hugging Face 一鍵下載、桌機 GPU 自架本地服務 700 t/s 不付任何 API key、不送任何資料出去。延續 6/9 Gemma 4 12B encoder-free 把多模態理解搬進 16 GB Mac 的路線，這一檔把「文字生成速度」這個維度也從雲端搬回本地——MES 戰情室那種「異常一冒出來就要 AI 解釋給作業員看」的場景第一次成立。

## 2. PgDog：4.7k★ Rust 單執行檔把 PgBouncer + HAProxy + Citus 三件事收成一件

**來源：** [pgdog.dev 官方](https://pgdog.dev) · HN 391 點 6/10

你 brew install pgdog（或 docker run pgdog）裝完，在你的 NestJS / FastAPI BFF 跟 PostgreSQL 之間多一層連接器，**100,000 個 client 可以共享池內的少量 PG 連線**、**每個 thread 每秒過 50,000 個 transaction**、replica 上自動分散讀請求並偵測 replication lag、寫請求 failover 時自動切到新 primary——這些以前你要 PgBouncer + HAProxy + Citus 三套工具拼接。已在 Coinbase、Ramp、Modal、Bitstack、Huntress production 跑 **10 TB+ sharded、每秒 100 萬+ query**。GitHub **4.7k stars**、Rust 寫的單一執行檔、Helm chart 與 Docker image 都有。

PgDog 是個 PostgreSQL wire protocol-aware 的中介層——它假裝自己是 PG server 讓你的 app 直接連，背後再幫你 multiplex 到真正的 PG cluster。三件事在同一個 process 內完成：(1) **connection pooler** 不固定綁 session 但仍保留 prepared statement 跟 session state 的正確性；(2) **load balancer** 用內建的 SQL parser 判斷讀寫、把讀請求散到 replica、寫請求集中到 primary、replication lag 太大的 replica 自動踢出；(3) **sharding** 透過兩階段提交（2PC）跨 shard 跑 ACID transaction，replicated tables 讓查詢自動 fan-out 平行執行、big integer key 自動產生。複雜度全收進這個中介層，application layer 還是「我寫普通的 SQL」。

以前你要做 PostgreSQL 水平擴展，要嘛接受單機天花板（垂直擴），要嘛上 Citus 改 schema 重 design 在程式碼裡標 distribution column。更常見的是各種「先 PgBouncer 套上、撐不住再說」拼湊路線——每多一層你就多一個 ops 人要會的東西。PgDog 把這三層收成一個 Rust 執行檔、Helm chart 一行裝、Docker 一行跑、application 不用改任何 SQL。延續 6/6 Microsoft pg_durable 把 workflow execution 推回 Postgres、5/26「複雜度推到正確的層」這條主線——PgDog 把分散式資料庫的複雜度推回 wire protocol 層而不是 application schema 層。

## 3. Blue41 揭露 Bunq 案例：一筆 €0.02 匯款就能讓銀行 AI 助理變成 spear-phishing 通道

**來源：** [Blue41 案例頁](https://blue41.com/blog/how-we-helped-bunq-secure-their-financial-ai-assistant/) · HN 166 點 6/10

你身為金融 / 客服 / 電商 AI agent 的設計者，可以從這個案例直接學到怎麼防「使用者沒有真的給指令、攻擊者卻成功操控 agent」的攻擊。Bunq 是歐洲第二大數位銀行、**20 M 客戶**。Blue41 揭露的攻擊鏈是：攻擊者匯一筆 **€0.02** 進受害者戶頭，匯款附註欄塞進精心設計的指令；當受害者跟 Bunq AI 助理問「最近交易」時，助理把那筆交易讀進 context 連同攻擊者的指令一起執行，於是合成出一則看起來是銀行官方的釣魚訊息——訊息可以引用真實交易金額、真實帳戶餘額、真實時間戳，credibility 比一般電郵釣魚高一個量級。攻擊者只需要付 €0.02 + 一句惡意 prompt。

這叫 **indirect prompt injection**——惡意指令不在使用者輸入裡，藏在 agent 會去讀的「外部資料」（這裡是交易描述欄位）。Payload 不需要 "ignore previous instructions" 這種明顯關鍵字，反而做得「在單獨閱讀時毫不違和」，等 agent 把它跟系統 prompt 拼接成 context window 才生效。傳統 input 過濾擋不到，因為使用者問的是合法問題「我最近有什麼交易」。Blue41 的修法是四件事疊加：(1) **minimize context exposure**——不把整個交易描述原文丟給 LLM、先萃取結構化欄位；(2) **treat retrieved data as untrusted**——把 retrieved data 包進明確標籤 `<untrusted_data>...</untrusted_data>` 並在 system prompt 教模型怎麼處理；(3) **constrain sensitive outputs**——敏感操作（請求密碼、產生轉帳指令、發送 email）不能由 agent 自由生成、要走固定範本；(4) **runtime behavioral monitoring**——偵測 agent 行為異常 pattern 即時告警。

以前金融 AI 安全敘事是「擋住惡意使用者輸入」——對應傳統 OWASP injection 思維。現在威脅樣貌徹底翻面：使用者完全正常、攻擊者不需要 user 帳號、攻擊面是「任何 agent 會讀到的資料源」（交易描述、客服 ticket、email 內容、CRM 備註、上傳檔案、Slack 訊息）。延續 6/6 Morgan Willis 的 inference theft、5/29 Anthropic 工程白皮書三類風險 × 三層防禦——這次第一次有商業銀行 production 案例把「retrieved data 是 untrusted」這條從 white paper 變成可發票的 incident response。EQS 100+ 表單流程卡控的那種「邊界精準度」精神第一次完整移植到 AI agent 工程。

## 4. Apache Burr：2.2k★ 把 state machine 從 LangChain 抽象底層拉出來當一級物件

**來源：** [burr.apache.org](https://burr.apache.org/) · [apache/burr GitHub](https://github.com/apache/burr) · HN 175 點 6/10

你 `pip install burr` 就能在 Python 裡寫 AI agent 應用——不用 LangChain 那一套 chain / runnable / lambda 抽象、不用學 DSL、不用 YAML。架構是 **state machine**：你用 `@action` 裝飾你的 Python function、用 transition 宣告狀態之間的跳轉、用 `ApplicationBuilder()` 把它們組起來。整套跑起來附帶內建 **monitoring UI** 可以即時追蹤每個 state 的 input / output / state mutation——debug 比 LangSmith 更直接因為直接看狀態機本身。Apache 2.0、GitHub **2.2k stars**、Apache Foundation incubating 中、最新 v0.42.0-incubating（2026-05-10）、整合 OpenAI / Anthropic / LangChain / Hamilton / Streamlit / FastAPI / PostgreSQL。

Burr 的設計哲學是「應用程式邏輯是個 state machine」這件事不該被框架抽象藏起來——chatbot 是 state machine、RAG 是 state machine、multi-agent orchestration 是 state machine，那就直接把 state machine 當一級 primitive，不要包成 chain。每個 action 是純 Python function 讀寫 state，state 是 dict（可掛 disk / DB / 自訂 backend persistence）、transition 是 `(from_state, to_state, condition)` tuple。**Human-in-the-loop** 用 pause point；branching / parallelism 直接寫 if 跟 asyncio；**replay** 把過去某次跑的 state 序列重放——unit test 變成「給 state，跑單個 action，斷言新 state」。LangChain 那種「chain 包 chain 包 lambda」三層才看得到實際做什麼的 debug 痛點消失。

以前 AI agent framework 選型只有兩種選擇：要嘛吃 LangChain / LangGraph 一整套抽象（學習成本高、debug 難、state 隱在多層 callable 裡）、要嘛從零拿 raw API 自己搓 state（沒有 observability、沒有 persistence、testing 痛苦）。Burr 把「state machine 是顯式 primitive」當成第一級設計決定——對 Henry 規劃 Nexus AI 整合 roadmap 從 6/9 lightest-first（Skill → CLI → MCP）漸進升級結論來說，Burr 剛好補位「需要 persistent state + human-in-the-loop + observability 但還不需要 MCP」這一檔。Angular MVVM + RxJS Observable + NgRx 早就教過 state machine 思維——第一次同一套思維可以直接套到後端 AI agent。

## 5. CLI over MCP：Copilot CLI 實驗給 6/9 lightest-first 結論第一份 +5k token 量化證據

**來源：** [Maxim Saplin dev.to](https://dev.to/maximsaplin/cli-over-mcp-a-small-chrome-devtools-experiment-in-copilot-cli-5gpi) · reactions 11

你拿這篇 6/10 dev.to 實驗可以直接拿到具體數字決定 Claude_auto SKILL.md frontmatter 不要把未來考慮的 MCP server 加回來。實驗對照同一個任務（**9 步驟 Chrome DevTools browser smoke test**）跑兩條路徑：直接接 Chrome DevTools MCP server vs. 用 `mcp2cli` 包成 CLI 工具讓 agent 呼叫。token 消耗 baseline **19k** → MCP 路徑 **24k**（+5k 純 tool schema 開銷）→ CLI 路徑 **19k**（schema 開銷 0）。MCP 跑得快一點（最快 101s vs CLI 141-259s）但成本是 token 浪費跟「tool surface 看得到所有 method 不論用不用」的脈絡污染——MCP 路徑 context volatility 16.1k-55.9k vs CLI 18-20.5k（CLI 穩定 ~10% 振幅，MCP 振幅高達 3.5 倍）。

MCP 規範要求 server 啟動時就把 full schema（包含 tool name、parameters、descriptions）餵給 client，所以 GitHub MCP 那種 27 個 tool 的 server 一接上就吃 18k tokens / turn 不論你用不用。CLI 路徑不一樣：`mcp2cli` 把同一個 MCP server 包成一個 CLI 命令（例如 `cdt navigate https://...`），agent 只需要知道「有個 CLI 叫 cdt」，要用什麼子命令時用 `cdt --help` 隨需發現。這就是漸進揭露（**progressive disclosure**）——schema 不一次塞滿，agent 透過跟 CLI 的對話逐步學會。trade-off 是每次發現要多耗幾秒，所以對單次任務 MCP 略快，對長期 / 多任務 / 大 context 場景 CLI 贏。

> ⚠️ `mcp2cli` 為小型 wrapper 套件，使用前請自行確認來源與安全性。

6/9 那篇 lightest-first（rapls dev.to）還只是哲學主張「先做 Skill 再升級」，6/10 這篇實驗給出**第一個量化證據**（+5k token、tool surface explosion、context volatility 3.5×）。對應 Henry 6/9 已決定 Claude_auto SKILL.md 拒絕加 MCP server——現在這份決定有了數字背書可以寫進 frontmatter 註解。更廣的影響：MCP 不再是「比 CLI 進階所以更好」的預設答案，而是「短任務、高頻、結構化深整合」這個特定區域的選擇；CLI 重新拿回「日常通用、context 敏感、語言模型友好」這個地盤。Anthropic 主動推進 `mcp2cli` 這類 wrapper 等於承認自家 ecosystem 不該全押 MCP 路線。

| 文章 | 藏起來的成本 | 顯式化後的選擇 |
|------|-------------|----------------|
| DiffusionGemma | 「token-by-token 是預設」的延遲成本 | 改用 256-token block 平行降噪 → 700-1000 t/s |
