## Z.ai GLM-5.2 — 744B/40B MoE MIT 開源，Intelligence Index 51 領先所有開放權重模型

artificialanalysis.ai 6/16 發表獨立 benchmark，HN 796 點 385 留言。Z.ai（智譜，前身清華大學 KEG 實驗室）推出 GLM-5.2：**744B 總參數 / 40B active 的 MoE 模型**，跟前代 GLM-5.1 同架構但 context window 從 200K 翻 5 倍到 **1M tokens**、權重 MIT 授權公開、Hugging Face 直接下載。Intelligence Index v4.1 拿 **51 分**——把 DeepSeek V4 Pro（44）跟 MiniMax-M3（44）甩開 7 分，首次有開放權重模型衝上這個區間。其他關鍵 benchmark：GDPval-AA v2 拿 **1524** 跟 GPT-5.5 xhigh 的 1514 同檔甚至略勝、GPQA Diamond **89%**、TerminalBench v2.1 **78%**。第一方 API 定價 **$1.4/M input + $0.26/M cache hit + $4.4/M output**——換算每個 Intelligence Index 任務約 $0.46，比 GPT-5.5 xhigh 約低一個數量級。每次 reasoning 任務平均吃 37k/43k 輸出 tokens，把推理過程顯式化進帳單。

技術上 GLM-5.2 的設計重點是**架構保守、context 激進、定價對抗**三件事。架構保守是因為跟 GLM-5.1 同 MoE 結構（744B/40B active），意味 vLLM / SGLang / Transformers / MLX 等推理引擎不用改 kernel 就能 day-zero 支援；context 激進是 1M tokens 第一次出現在開放權重旗艦（過去只有 Gemini 2.5 Pro 商業 API 有），把 Nexus monorepo 級別的整包餵入變成可行；定價對抗是 Z.ai 明顯瞄準的是「想自架但兩張 H100 嫌貴的中型團隊」，第一方 API 定價直接給「先試試手感再決定要不要自架」的折衷路徑。對比 6/17 Vicki Boykis 在 M2 Mac 64GB 跑 26B 模型拿 ~75% frontier 效果，GLM-5.2 是另一個刻度——往上推到 744B、需要 H100 集群，但拿到 Intelligence Index 51 的 frontier 同等效果，且 MIT 權重完全可自架，徹底拿掉「資料一定要送美國公司」這條過去隱性的合規顧慮。

Before：你要拿到 Intelligence Index 51 等級的 AI 能力，路徑只有兩條——走 GPT-5.5 / Opus 4.8 商業 API 每次 $50/M 輸出付完整 token 稅 + 上傳 prompt 給美國公司、或收編 DeepSeek V4 Pro / MiniMax-M3 等開放權重但 Intelligence Index 卡在 44 落後一個世代；After：同樣的 51 分換成 **MIT 權重 + $4.4/M 輸出 + 1M context + 自架選項**三條路同時開——Nexus monorepo review、客戶交付前的 token 一致性掃描、design system 文件問答全都可以在「不送 token 出本地網路」的前提下跑。對 Henry Nexus 三件可同時動：(1) **packages/ui token 一致性 review** 直接吃 1M context 餵整包 token JSON + Storybook source + Figma export，過去要拆三輪比對，現在一輪 Claude API 等級的判斷下完；(2) **客戶採購 deck 新增「AI 推理 sovereignty」差異化** ——把「Nexus 的 AI 工作流可用 MIT 權重自架，token 不出本地網路」明確寫進 slide，對應 6/13 Linear local-first 主線跟 6/16 Iroh 1.0 直連定址同節奏；(3) **Claude_auto SKILL.md 加 fallback 雲端推理路徑** 從 Fable 5 → GLM-5.2 API → 本地 Gemma 4 三層降級，API 預算/網路出問題自動往下走，三層都拿得到「能用」的結果。

## CADAM 4.3k★ — 開源 text-to-CAD：自然語言進、3D 模型 + 可調參數 sliders 出，全跑在瀏覽器

GitHub 4.3k★ 550 fork、GPL-3.0、TypeScript 88.4%。CADAM（Adam-CAD/CADAM）是一個跑在瀏覽器的 text-to-CAD 開源工具：你輸入「一個 V8 引擎，活塞行程 92mm，缸徑 88mm」，30 秒拿到完整 3D 模型可旋轉檢視，AI 自動 extract 出 **2-22 個可調維度**變成 React sliders 可即時拖拉，最後 export **STL / SCAD / DXF** 三格式（3D 列印 / OpenSCAD 原始碼 / 向量繪圖）。整個過程零安裝——OpenSCAD 引擎跑在 WebAssembly、UI 用 React 19 + Three.js 渲染、AI 透過 Anthropic Claude API 解析自然語言。Benchmark 範本包括 9 缸星型航空引擎、渦輪噴射、knurled 旋鈕、bevel gears、honeycomb 圖案托架、錐形機翼——複雜度遠超「玩具 demo」等級。

技術上 CADAM 把「設計意圖→可調參數模型」拆三層：(1) **Claude API 負責讀懂自然語言** 把幾何約束抽出來（活塞行程、缸徑、扭矩、葉片數）；(2) **OpenSCAD WebAssembly 把約束轉成 mesh**——OpenSCAD 是 functional script CAD 語言，原本要懂 `cylinder($fn=64, h=80, d=88)` 這種語法手刻；(3) **Three.js 把 mesh render 進瀏覽器** 同時把可變維度 exposed 成 sliders。關鍵設計是 **AI 不只生成 once-off 模型——它同時把「可變維度」抽出來作為一級參數**，等於把 LLM generation 跟 parametric design 兩種能力縫成一條鏈。BOSL / BOSL2 / MCAD 三套 OpenSCAD 標準 library 提供 primitive 庫，Claude 知道哪些 primitive 可用，組合出複雜 assembly 而不是從零生成。

Before：CAD 工作流要嘛跟著 SolidWorks / Fusion 360 商業訂閱 + Windows 本機跑 + 學鼠標操作半年、要嘛跟著 OpenSCAD 手刻 `.scad` 檔懂 functional script 語法 + 自己理解 BOSL library API；After：同樣的「我要一個 V8 引擎」需求在瀏覽器 30 秒解決，而且不是黑盒——所有參數都 exposed 成 sliders，最後拿到的是 SCAD 原始碼可繼續手改。對 Henry 三條工作脈絡：(1) **packages/ui Storybook controls 升級**——CADAM 的「AI 抽出可調維度 → 自動 expose 為 sliders」pattern 直接搬到 Storybook，設計師描述「Button 我要 size + density + tone 三軸可調」，LLM 自動寫出對應的 `argTypes` controls 跟 component variants，省去 Storybook 手動 boilerplate；(2) **Figma → JSON → Token 工程鏈下半段補位**——你現有的鏈把「視覺」翻成「靜態 token」，CADAM 示範下一步是「視覺意圖」→ 「可參數化視覺」，token 不只是靜態值而是「值 + 可變範圍 + UI 介面」三合一；(3) **客戶交付 demo 加 parametric primitive**——對標 CADAM 把 OpenSCAD primitives 包裝起來給 LLM 拼，Nexus packages/ui 可以把 Button/Card/Modal 包裝成「LLM 可組合 primitives」讓客戶提需求即時拼出新組件。

## rapls 戳破 MCP-tax 假設：AI agent 變笨不是 MCP，是 conversation history 吃掉 20% context

dev.to 6/17 文章 10 reactions，作者 rapls 也是 6/8「Skill, MCP, Plugin, or just a CLI: lightest first」洞察的提出者——同個作者一週後的續篇。論點直白：你在 Claude Code 跑一個探索性 session 兩小時後，agent 開始重複你早就回答過的問題、忘記你早講過的限制、輸出品質明顯下降。**本能反應是怪罪 MCP server 吃掉 context window**——但 rapls 用 agent 內建的「context 分類 breakdown」實測：MCP tool definitions 在 context 中的占比「比 rounding error 還小」，conversation history 才是 ~20% 的單一最大成分，**真正的元兇**。修法不是換 substrate（拿掉 MCP），是換 session 行為——結束探索性 session 而不是無限延長、寫進度摘要開新 session、轉移摘要而非完整 transcript。

技術上 rapls 提出一個比喻值得記住：**context window 是書桌，不是檔案櫃**。檔案櫃可以無限堆疊「以後可能用到」的東西；書桌只能放你「現在同時要用」的東西。Claude Code agent 在長 session 裡每一輪對話都疊上書桌，到某個點桌面塞滿了過時的探索路徑、被棄置的假設、跟當下任務無關的脈絡——agent 沒有變笨，是它的「現在同時看到的東西」訊噪比變差。診斷的優先順序比修法本身更重要：先量化 context window 各成分比例，再決定要拿掉哪一層；如果跳過量化直接砍 MCP，砍掉的是錯的東西，conversation history 還在膨脹，下一次 session 一樣會變笨。

Before：你看到 agent 變笨第一反應是「該換更大的 model」、「該砍 MCP server」、「該升級 context window 容量」——這些動作的共通假設是「問題在外面」，因為 conversation history 感覺像 native runtime 行為從不量測也從不主動清理；After：rapls 把問題重新定位到「session 自身的 conversation history」，這層第一次變成可量測、可主動清理的工程對象。對 Henry 6/11 已決「Claude_auto SKILL.md 拒絕未來加 MCP server」這條結論，這篇文章是反證——MCP 不是 +5k tokens/turn 的元兇，conversation history 才是；6/11 的論斷方向對（lightest-first）但**砍錯了 substrate**。正確的優化動作是在 Claude_auto SKILL.md frontmatter 加 `session-strategy: per-stage-clear`，把 daily fetch / filter / write / commit 四階段各自開新 session 不共享 conversation history，每階段結束自動 `/clear` + 寫摘要進 session-log.md 開下一階段新 session，把 conversation history 占比從 ~20% 壓回 < 5%。對應 6/17 Wolfram Agent Tools framework「每個 engine 做自己擅長的事」洞察——session 設計也是同樣思路，每個 session 只裝它當下要用的 context，不裝歷史。

## 今日總結

四條獨立路徑同一個工程動作——**「AI 工作流的成本不再是模型本身，而是承載 context 的容器」**。

Z.ai GLM-5.2 把 frontier 等級 Intelligence Index 51 開源到 **MIT + 1M context + $4.4/M 輸出**——比 GPT-5.5 xhigh 便宜一個數量級而能力同檔，open weights 容器第一次裝得下這個等級的 context；CADAM 4.3k★ 把 text-to-CAD 整條鏈塞進**瀏覽器 WebAssembly + Claude API**——容器從桌面 native 翻成瀏覽器 web，整個工作流不離開 tab；rapls 用實測數字戳破「MCP tax 是大頭」假設，conversation history 才是 ~20% 元兇——容器（session）本身的清潔度才是優化的真正槓桿；Claude Code v2.1.181 把 `/config` 推到對話 surface 同時修好 cloud-synced drive 寫檔截斷——容器（session + filesystem）的可調性跟可靠性同步升格。

延續 6/17「『本地』基板第一次被當成可量化、可挑選、可加速的工程選項」推到下一層——**基板選好之後，承載基板的「容器」也要被量化、清潔、設計**：

| 容器層次 | 過去當作預設 | 今天升格為工程決定 |
|---------|--------------|-------------------|
| 模型權重容器 | OpenAI/Anthropic 商業 API | GLM-5.2 MIT 權重 + 1M context + 自架選項 |
| AI 工作流容器 | 桌面 native CAD（SolidWorks） | 瀏覽器 WebAssembly + Claude API（CADAM） |
| Session conversation 容器 | 「能跑就好」無限疊加 | 量化 ~20% conversation history 占比、per-stage clear |
| Filesystem 容器 | 本地硬碟 vs cloud-synced 混用 | v2.1.181 修好 cloud-synced 寫檔截斷 + presence file 區分裝置 |
