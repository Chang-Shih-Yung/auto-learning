## 1. Jane Street 設計師：我設計用 Claude 比用 Figma 多——50 次迭代零摩擦

Jane Street 期權交易桌設計師 **Edwin Morris**（2025 年夏天入職）在公司工程部落格寫了一篇〈I design with Claude more than Figma now〉（HN 160 點，6/7 早晨上版）。他的工作流以前是：寫 spec 文件 → Figma 畫 mockup → 提案討論 → 工程師實作 → review 落差。**現在他直接在編輯器裡跟 Claude 對話寫 working prototype**，包含 JSQL 輸入框新增 LLM prompting 功能、全新內部應用程式的互動原型、甚至**涉及 data model 與 library 變動的 2,000+ 行 diff**——「以前要好幾天甚至好幾週 design / engineering 來回的功能」，現在他**單一個 feature 可以迭代到第 50 次**而不卡頓，最後送 review 的是「fully baked feature」而非靜態畫面。

技術機制是：Claude Code 把過去「Figma 是設計唯一語言、code 是工程唯一語言」的二分法直接拆掉。Edwin 的 prototype 是真的 React/前端 code，跑在 Jane Street 內部開發環境裡，連著真實的 JSQL 後端、真實的資料；他在編輯器裡描述「我想在這裡加一個 LLM 提示輸入框」，Claude 改 component、改 schema、改 library 三層一起改——這在 Figma 是不可能的，因為 Figma 不知道你的 backend schema、不知道你的 component library 限制、不會幫你寫 SignalR 連線。**設計的最小可驗證單位從「畫面長什麼樣」升格成「在真實資料上跑得起來」**，這就是為什麼 50 次迭代不痛——每次迭代不是重畫，是真的推進一步。

以前你（Henry，UI/UX 出身轉企業前端，做過 EQS 100+ 表單、MES 1分20秒→20秒）的 design-to-code 流程是：Figma → JSON → OKLCH Token → Angular component → 開發環境驗證。Edwin 的故事把這條鏈的**前三段直接收進編輯器內**——Figma 與 token 變成 backing reference，主要設計動作直接在 working code 上做。Edwin 自己也誠實列出 downside：「reviewer 拿到一個 fully baked feature 比較沒有共同設計的空間」、「擔心自己會被『Claude 做得出來的』綁住創意」、新應用程式他還是會先用 Figma 探索方向。這跟你 Nexus 既有的「Figma → JSON → OKLCH」工程鏈不是替換關係，是**互補**——packages/ui 元件庫的新元件你可能仍從 Figma 起步，但**既有元件的微調 / 組合 / 業務場景套用**可以直接在 Claude 編輯器裡跑 working prototype，把「畫到 95% 像」這段省掉、直接 push 到 dev 環境驗證手感。對應 5/27〈契約 first-class 物件本身的「屬性」也要 first-class 化〉的下一檔——**設計的「最小驗證單位」這個屬性本身也要 first-class 化**。

## 2. Forge：四層 guardrail 把 8B 本地模型從個位數推到 84%、Sonnet 3.5 從 85% 推到 98%

GitHub 上的 **Forge**（HN 687 點，2,000 stars，MIT，Python）是一個「self-hosted LLM tool-calling 可靠度層」。在它自家的 26-scenario v0.7 評估套件上：**8B 本地模型成功率從個位數 → 84%**，**Claude Sonnet 3.5 從 85% → 98%**（v0.6 數字）。意思是你不換模型、不加 GPU、不買大廠 API——只在客戶端裝一層 `pip install forge-guardrails`，agent 工作流的成功率就跨一個數量級。

技術機制是四層 guardrail 全部對使用者透明：
1. **Response validation** — 拿模型回傳的 tool call 對你宣告的 tool schema 驗一次，欄位錯就退回
2. **Rescue parsing** — 模型常常回 malformed JSON、Mistral 風格的 `[TOOL_CALLS]` 標籤、Qwen 的 XML，Forge 用 regex + AST 把這些都還原成正規格式不丟掉
3. **Retry loops with corrective messages** — 預設 3 次重試，每次把錯誤訊息（「你少了 `temperature` 欄位」）feed 回模型讓它修正
4. **Synthetic respond tool injection** — 有 tool 可用但模型卻回純文字時，自動補一個 `respond` tool 把那段文字包進 tool call，讓上層 agent 結構不會崩

這四層是「模型沒事先學過 tool-calling」也能用的薄殼——對你（Henry）正在跑 Claude_auto 排程任務的場景，意味著萬一未來想加入 self-hosted 本地模型當第二意見（例如本地 Gemma 4 跑「先檢查文章是否已寫過」這種便宜驗證），不用挑「原生支援 tool calling」的模型，任何能 instruct 的本地模型套上 Forge 都可工作。

以前要做 agent 工作流，預設「模型必須夠強到原生會 tool calling」，所以只能挑 Claude / GPT 這類雲端付費 API；不夠強的本地模型一遇到多步驟就崩，open source 路線無解。Forge 把這個假設打掉：**reliability 是工程問題不是模型問題**——validation + rescue parse + retry 三層補上去，弱模型的成功率追平強模型的原生表現。對應 5/29 Liquid LFM2.5-8B-A1B 把「on-device 不是玩具」打開、5/30〈MCP is Dead?〉把 always-on 載入的 65× token 成本量化之後，今天 Forge 把「弱模型怎麼當好 agent」這條剩下的路也補完——hybrid 架構（強模型負責策略、弱本地模型負責驗證 / 預檢 / 重試）的工程可行性現在成立。對應 6/5〈Neo + Claude Code 62% cost cut〉的下一檔——cost cut 之後輪到 reliability 補完。

## 3. Sem：在 Git 之上跑「函式級」diff / blame / impact——AI agent 準確率 2.3 倍

**Sem**（GitHub `Ataraxy-Labs/sem`，2,243 stars，Rust，Apache 2.0，HN 118 點）是一個 `brew install sem-cli` 就能裝的 CLI 工具。它把 Git 預設的「行級 diff / blame」**升格成「函式 / class / method 級」**：你看一個 commit，Sem 告訴你「新增了 `validateToken`、改了 `authenticateUser`、移掉了 `legacyAuth`」——而不是「+45 −12 行」。它還順手算出**依賴影響範圍**——`authenticateUser` 依賴 `db.findUser` + `rateLimiter`，被 `loginRoute` + `authMiddleware` 用，這一改透過依賴鏈影響 42 個 entity。

技術機制：26 種語言全部走 **tree-sitter**（語法解析器），不依賴 LSP（不用 IDE 啟動、不用語言伺服器、不用設定）。`brew install sem-cli && sem setup` 之後它把自己接成 git 預設 diff driver——你 `git diff` 看到的就是 entity-level 結果。內部速度：**8 ms 典型 diff**（比 IDE 啟動 LSP 還快幾個量級），4,000+ downloads，repo 2026 年 2 月才建。最關鍵的數字：作者引用內部測試，**AI agent 拿到 sem 輸出，準確率比拿到 raw line diff 高 2.3 倍**——agent 看「這個 commit 改了 `authenticateUser` 的 token 驗證邏輯」遠比看「line 42 改了 if 條件」可操作。

以前 AI agent 想理解一個 codebase 變動，預設手段是把 raw diff 丟進 context（吃 token、又雜訊多——format 改動、空行、import 順序全混在裡面），或者啟動一個 LSP（吃啟動時間、設定地獄、不跨語言）。Sem 把第三條路打開：**git 本身就理解語意實體**，diff / blame / log 全部變成「函式級事件」。對你（Henry）正在做的 Nexus 元件庫——你 commit 一個 `Button` props 改名，Sem 告訴你「`Button.size` → `Button.density`，影響 packages/demo 的 3 個 page 與 apps/www 的 5 個範例」，這是 monorepo 跨 package 重構最痛的事一次解掉。對你 Claude_auto 的延伸：每天 session 結束時跑一次 `sem log --since=yesterday`，把昨天 journal 的真正語意變動（不是 markdown 行數）丟給 Claude 做今日去重判斷比現在的「session-log 散文摘要」更精準。對應 5/26〈Veso 8 postulate〉的「驗證機制升格為一級工程動作」推到下一檔——**檢索的單位（行 vs 函式）這個屬性本身也要 first-class 化**。

## 4. Tokenomics 論文：Agentic 軟體工程的 token 開銷，**59.4% 燒在 Code Review 階段**

arXiv 上的 **Tokenomics: Quantifying Where Tokens Are Used in Agentic Software Engineering**（Mohamad Salim 等 4 位 Concordia 大學作者，6/7 上 HN 106 點）用 ChatDev 框架 + GPT-5 reasoning model 跑 30 個真實開發任務，追蹤 token 在 agent 工作流六個階段（Design / Coding / Code Completion / Code Review / Testing / Documentation）的分布。結論一句話：**Code Review 階段平均吃 59.4% 的 token**，超過剩下五個階段加起來。

技術機制是兩層：(1) Code Review 在 ChatDev 設計裡是「一個 reviewer agent 跟一個 coder agent 來回討論直到收斂」，這個 loop 不像 code generation 一發即定、而是反覆對話——每輪都把整段 code 重新 reload 進 context，所以累積得很快。(2) **input token 占總量 53.9%**（output 比較少）——意味著 token 大部分是「重複把過去脈絡塞回去給模型」而不是「模型生新東西」，這個 53.9 / 46.1 分布揭露 agent collaboration pattern 有結構性 inefficiency：**每次討論都要重新建立共識，沒有持久 shared state**。論文沒比 Claude Code / Cursor / Codex，但 ChatDev 是學界基準框架、訊號可移植到其他 multi-agent 系統。

以前談 agent 成本，預設「模型寫一行 code 多少錢」是主要 cost——所以優化方向是換便宜模型 / 用 prompt cache。Tokenomics 論文把這個直覺打掉：**code generation 不是大頭，「verification + refinement」才是**——而這部分剛好是「模型聊對話」的 cost，跟模型聰不聰明關係小、跟 collaboration protocol 設計關係大。對你（Henry）跑 Claude_auto 排程任務的延伸：你的每日 session 真正吃 token 的不是「寫 5 篇文章」這段，而是「Claude 跑 WebFetch 抓 10 個來源、判斷 7 個跳過、整合 3 條主線」這段 review-style 思考——這跟論文裡的 59.4% Code Review 同構。對應 6/5〈Neo + Claude Code 62% cost cut〉把「主 agent dispatch + sub-agent execute」拆開能省成本的結論——今天 Tokenomics 把**該往哪個階段拆**精準定位：Code Review 階段拆出去 ROI 最高，code-gen 階段拆不太省。

## 5. Statewright：把 agent 工作流拆成 state machine，「Agents are suggestions, states are laws」

**Statewright**（Claude Code 外掛 + 雲端 SaaS，Apache 2.0 + FSL-1.1-ALv2，HN 126 點）提供一套 **state machine guardrail** 讓你約束 agent **在不同階段只看得到不同 tool**：planning 階段只能讀（不能 edit、不能 bash）、implementing 階段才開放 edit、testing 階段才開放 bash、completed 階段全關。它自家的口號精確抓到設計哲學：**「Agents are suggestions, states are laws」**——agent 想做什麼是建議，狀態機決定他能做什麼是法律。

技術機制與效果是 SWE-bench 5-task 子集上的對照實驗：**gpt-oss:20b（13.8 GB）與 gemma4:31b（19.9 GB）兩個本地模型，沒有 state machine 約束時 2/10 通過、加上約束後 5/5 通過**；3.3–7.2 GB 的小模型不論加不加都失敗——因為 < 13 GB 的模型「能識別 bug 但無法做精準編輯」。實測一個典型 bugfix workflow 約 46 秒跑完整輪 planning → implementing → testing → completed。約束效果不是讓模型變聰明，是**把 tool space 收斂到模型 reasoning 能力範圍內**——planning 階段不給 edit tool，模型就不會「我猜這裡有 bug 直接改改看」陷入 read-loop death spiral。

以前約束 agent 行為靠的是「prompt 講清楚」——說「先看完所有檔案再修改」、「測試前不要 commit」。這條路在 demo 環境有效，到 production 不可靠——模型 80% 的時候聽話、20% 越界。Statewright 把這條路徑替換成**外部 enforce 的有限狀態機**：「現在這個 state、只暴露這幾個 tool」變成系統不變式，模型壓根看不到不該用的工具——這跟 6/5 Anthropic 工程白皮書「containment 升格為一級工程動作」、5/27 v2.1.152「skill `disallowed-tools` 在啟動期間根本看不到工具」是同一條主線推到 workflow-level。對你（Henry）做 Claude_auto 排程的延伸概念：每日 session 也可以拆成 fetch（只開放 WebFetch / WebSearch）→ filter（只開放 Read）→ write（只開放 Write/Edit）→ commit（只開放 Bash git）四 state——每個 state 看得到的工具不重疊，accidentally `rm -rf` 或誤 commit 到錯分支的風險結構性消失。對應 5/27〈契約 first-class 物件本身的「屬性」也要 first-class 化〉推到「agent 在不同階段該擁有什麼能力」這個屬性也要 first-class 化。
