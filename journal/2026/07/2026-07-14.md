# 2026-07-14 學習日誌

## Claude Code v2.1.208：79× transcript 壓縮 + 7× MCP tool round 加速 + `CLAUDE_CODE_PROCESS_WRAPPER` 企業層鉤子

用你目前跑排程任務的 Claude_auto，這件事讓你直接把 session transcript 從 v2.1.207 之前**在 edit-heavy session 累到破幾百 MB** 壓縮到 **1/79**——[Claude Code v2.1.208 release 7/14 01:10 UTC](https://github.com/anthropics/claude-code/releases) 修掉「superseded file-history backups 沒被 prune」這條長期資源洩漏，把 checkpoint 磁碟用量也一起 bound 住。同一版把 MCP tool call 迴圈**每輪 CPU overhead** 降到 **1/7**（在高 tool 數量 print / SDK session 下實測）——tool pool assembly 現在被 cache，不再每輪重組。permission deny / ask rule 也從「每次 tool call 重編 matcher」翻成「編一次 cache 起來」——你長期在 Claude_auto 累積的一堆 always-allow / always-deny 規則以後不會再讓 per-turn latency 慢好幾秒。同時新增 `CLAUDE_CODE_PROCESS_WRAPPER` 環境變數：agent view 跟 background service 現在會強制每個 Claude Code self-spawn 進程都走一個企業內部指定的 launcher executable，corporate 客戶第一次有官方 hook 可以把 audit / DLP / 沙箱都塞在 wrapper 那層而不用 fork Claude Code。

79× transcript 壓縮的細節值得看：以前 Claude Code checkpoint 是把每個 file 的完整歷史都存起來（讓你 `/rewind` 可以回到任意 snapshot），但**同一個 file 被覆蓋很多次時，之前的 backup 沒被 prune**——edit-heavy session 跑上一整天，磁碟就會被填滿 hundreds of MB 的重複內容。v2.1.208 把「已被 superseded 的 file-history backup」這條 GC 補上，`rm` 掉不再可達的舊 snapshot，`/rewind` 保留能力但只留最新可達的那條 chain。同一版還一起修了幾條 memory leak：MCP stdio server 的 stderr 以前會累積到**每個 server 64 MB** 才會被截斷、LSP document 開啟後**永遠不 close** 現在改 LRU 上限 50、async hook 的 output 在 background 之後仍被 retain、headless / SDK session 的 large tool-result payload 沒有 bound。file edit read cache 從「最多 pin 1000 個 full file」翻成「16 MB hard cap」，long session 記憶體 footprint 從線性成長翻天花板。這一大票補丁背後同一個工程方向：把過去為了「debug 方便」預設 unbounded 的 buffer / cache 全部改成 explicit bound，long-running session 不再是資源黑洞。

以前你部署 Claude_auto 到 macOS 排程觸發，跑 24 小時後 background daemon 記憶體可能已經吃掉 GB 級——你會週期性手動 restart 才能讓 idle 表現回穩。從今天起這條 workaround 可以拆掉：MCP stdio stderr 64 MB / LSP document 無 close / edit cache 1000 file / superseded checkpoint 累積，四條 leak 一次修完。7× tool round 加速對 Claude_auto 每天跑「sources.yaml → 8 個來源 fetch → filter → write → commit → push」這個 loop 影響直接——每一輪 fetch 都是一次 tool call，MCP tool 數量在你的 setup 已經破 20 個，per-round latency 從幾百 ms 掉到幾十 ms 的話，整條 session 的 wall clock 應該可以砍幾十秒。`CLAUDE_CODE_PROCESS_WRAPPER` 更是 Nexus 對外的商機：以前企業客戶要在 Claude Code 前面加 audit / DLP / 沙箱 hook，只能改 shell alias、hack `PATH`、或 fork binary——現在有官方 wrapper hook，Nexus 對外可以直接賣「掛在 wrapper 那層的合規 middleware」而不用侵入 Claude Code 本體。

## Clawk：把 coding agent 丟進一台可拋 Linux VM，agent 不再看到你的 `~`

用你目前跑 Claude_auto 跟 side project 的 macOS 工作機（Apple Silicon 14+），這件事讓你把 Claude Code / Codex / shell agent 塞進一台 **disposable Linux VM**，agent 只看到自己那台機器，看不到你的 `~/Library`、`~/.ssh`、`~/Desktop/auto-learning` 之外的專案——[clawkwork/clawk](https://github.com/clawkwork/clawk)（[Show HN 7/13 174 點 140 留言](https://news.ycombinator.com/item?id=46917886)、Apache 2.0、Go 99.1%）用 Apple Virtualization.framework（Linux 走 KVM 實驗中）架 hypervisor 層 isolation，加一層 userspace network stack enforce **DNS-aware allow-list**：npm / PyPI / GitHub 預先放行、其他預設封鎖。agent conversation 跟 code 存在**持久卷**，只有 disposable disk 每次銷毀——這剛好對應 Claude_auto 排程任務跑完就丟、但 memory / journal 要留下的 workflow。ticket mode 還額外撐 multi-repo：agent 在一個 VM 內同時開多個 repo worktree、跨 repo 協調同一組 PR，Nexus monorepo 的 `packages/ui` + `packages/cli` + `apps/demo` 跨 package refactor 剛好用得到。

Clawk 的設計核心不是「多加一層安全」，是**把 blast radius 從整台 mac 縮到一台可拋 VM**——同天出的 [Grok CLI 上傳整個 home directory 到 GCS](https://twitter.com/a_green_being/status/2076598897779020159) 事件（HN 379 點 391 留言，跟你昨天寫的 xAI Grok Build CLI wire-level 稽核同源頭）給的教訓正好是這方向：agent CLI 不管講得多好聽，只要它跑在你的 host user session，它 `read()` 什麼、把什麼傳出去就完全取決於 vendor 的良心。VM boundary 讓這個「良心」變成「不能」——network stack 這層 enforce 誰能連 outbound，即使 agent 想上傳 `.env`，DNS 解不出目標 host、connect() 直接被 deny。兩層 boundary 疊起來：hypervisor isolation 擋 filesystem / process，userspace network stack 擋 outbound。這條路徑跟去年那些 `firejail` / Docker seccomp / Podman 玩法本質不同——Docker 沙箱只擋 kernel-level primitives，agent CLI 在 container 內還是能讀 mount 進去的整個 workspace；VM boundary 讓 host filesystem 天然不可見。

以前你在 Claude_auto 跑排程任務，agent 有 macOS 使用者的完整權限——理論上它可以讀你 iCloud 資料夾、`~/Library/Application Support` 裡各種 app 的 sqlite DB、也可以連任意 IP。從今天起你可以把整個 Claude_auto session 塞進一台 Clawk VM，agent 只看到 `~/Desktop/auto-learning`（mount 進去）跟必要的 npm / GitHub outbound。Nexus 客戶採購 deck 未來也有一維可以加：「AI agent 執行邊界 isolation」——不是「我們相信 Claude Code 不會亂搞」，是「Claude Code 想亂搞也做不到，因為它跑在 VM 內」。星數 285 目前還低於一般 production 引入的門檻，先在自己 side project 試一台 Clawk VM 跑週末排程，感受 boot time 跟磁碟空間開銷再決定要不要納入 Claude_auto 主線。

> ⚠️ 目前 Clawk 285 stars，新工具，v0.2.0 released 2026-07-13。使用前請自行驗證 hypervisor 沙箱 policy 是否符合你的 threat model，並確認 userspace network stack 沒有 bypass 漏洞。

## antirez：不要審查 code，要控制 idea——以及為什麼 DESIGN.md 是新的 code review

用你目前每天在 Nexus 寫 code + 用 Claude Code 產 60% 元件、又同時維護 DESIGN.md 的雙棲身份，這件事讓你**直接把 antirez 這篇當成你既有工作流的理論支撐**——[Salvatore Sanfilippo（Redis 作者）7/13 貼文 Control the Ideas, Not the Code](https://antirez.com/news/169)（HN 203 點 170 留言）核心一句：「How are you supposed to review 5k lines of code every day?」他的觀察是 AI 每天可以吐出幾千行 code，人腦一行一行審已經**物理不可能**；而 LLM 剛好在 local optimization（local 對 local 每 20 行的 refactor 建議）很強、但在 architecture 決策（這個 module 該不該存在、資料流該走哪、interface 該長什麼樣）很弱——**人跟 AI 分工的邊界應該落在這條**。他推薦的具體 workflow：把設計思路寫進 **DESIGN.md**（data structure、implementation strategy、design principle 用**人類語言**寫下來），然後讓 LLM 用這份 DESIGN.md 當 context 產 code、讓另一個 LLM 用 DESIGN.md 對照 diff 做 review，人只審 **DESIGN.md 有沒有偏移**、以及 QA 手動測。

antirez 明確拒絕的路線：把 LLM 產出的 code 一行一行讀完再說。他的原話「the time spent reading code displaces higher-value activities like architectural thinking, QA testing, and feature innovation」——閱讀 5k 行 code 消耗掉的專注力剛好就是那些**只有人做得到**的事：想清楚下一週要蓋什麼、幫真實使用者跑一次 end-to-end 測試、判斷這條功能會不會撞到既有 abstraction。他對 junior 開發者的建議也很直白：不要靠讀 AI 產出的 client code 建基本功，靠**自己實作 interpreter / database / hash table** 建。這條建議跟 [5/12 Simon Willison 那份「vibe coding vs agentic engineering」責任邊界論](https://simonwillison.net/) 同一血脈——都在講「AI 產 code 誰負責」的問題，Willison 講的是 vibe coding 只影響自己、agentic engineering 影響使用者所以要多一層審核；antirez 講的是**你根本審不完，所以審 idea 不審 code**。

以前你在 Nexus 寫 code review pipeline，預設是「AI 產完人再看一次」——PR review 兩階段 reviewer + arbitrator subagent 也是這個假設的變體。從今天起 antirez 這篇給你一個明確的替代路線：**把 DESIGN.md 升成第一等公民、pipeline 從『review code』翻『verify code matches DESIGN.md』**。Nexus `packages/ui` 現有 `DESIGN.md` 已經寫了 OKLCH token 邏輯、color-annotation 專屬語意、Geist Sans / Mono 用法邊界——把這份 DESIGN.md 直接餵給 review pipeline 當 constraint，PR 只審「有沒有違反 DESIGN.md 條款」而不是「這 20 行 CSS 寫得好不好」。更遠一點：Claude_auto 這個排程任務本身的 SKILL.md 就已經是它的 DESIGN.md，pipeline 也可以跑同一條——每天 session 結束時另開一個 subagent 拿 SKILL.md + 今日 journal 做「有沒有偏移」的 meta-audit，這條剛好接上 6/29 antoine MRI 的「乾淨 context subagent 做 second opinion」路線。

## 前沿模型的「真實價格」：Claude Opus 4.8 標價 $5/$25，實付 $7.50/$37.50——tokenizer 才是隱藏成本

用你目前跑 Claude_auto 每天燒 token 的成本結構，這件事讓你**重新計算 fallback chain 的實際 $/task**——[playcode.io 7/13 分析](https://playcode.io/blog/real-price-of-frontier-models)（HN 149 點 76 留言）核心一句：「A 'token' is not a fixed amount of text. Each vendor's tokenizer cuts the same file into a different number of pieces.」拿 GPT-4 tokenizer 當基準測 TypeScript code，**Claude 的新 tokenizer 產出 1.73× 更多 token**——同一份 code 送給 Claude，帳單上的 token 數是送給 OpenAI 的 1.73 倍。轉換成 effective pricing：**Claude Opus 4.8 標價 $5/$25 每 M token 輸入/輸出，實際等值是 $7.50/$37.50**（1.50× 乘數）。**Sonnet 5 促銷後 $3/$15 標價，實際 $4.50/$22.50**。同 workload 對比：GPT-5.5 $5/$30、Grok 4.5 $2.06/$6.18（1.03× 乘數）、Gemini 3 Flash $0.55/$3.27（1.09× 乘數）——tokenizer 效率越差的家，list price 跟真實 spend 差越大。作者的建議：不要看 $/Mtok 排 leaderboard，看 **$/completed task**（用固定 workload 跑一輪，算單位任務實付）。

背後的機制是 tokenizer 對特定語言的分詞效率——Claude 的 tokenizer 對 TypeScript 這種**多識別符（camelCase）、多 keyword、多操作符組合**的語言分得比 OpenAI GPT-4 tokenizer 更碎，同樣 100 字元的 TS code，Claude 讀出來的 token 數更多。這件事對 Anthropic 有商業誘因——同一次 API call 收更多 token 錢——但技術上也真的是 tokenizer 訓練資料分布造成的副作用，不能簡單歸類成「刻意收費」。文章的方法論值得抄：跑一份**固定 workload**（例如 500 行 TS repo + 具體 refactor 任務），把每家 model 的 total token count × list price 算成 $/task，Claude 那 1.50× 就浮出來。Gemini 3 Flash 這條 1.09× 乘數搭 $0.55 標價的組合，$0.60/M input effective——**同樣完成一次任務可能只要 Opus 4.8 的 1/12**，如果 workload 對 model 能力沒有極端要求，這條經濟性差距足以推翻「Opus 是最好選擇」的預設。

以前你在 Claude_auto 的 fallback chain 排序，看的是 `$/Mtok` 標價跟 model 能力表——Sonnet 5 促銷 $3/$15 看起來便宜就排第一。從今天起 fallback chain 排序要多一步：**用你 memory/sources.yaml 這種真實 workload 跑一次 token count**，把每家 model 的 effective $/task 算出來——Sonnet 5 實際 $4.50/$22.50，Gemini 3 Flash 實際 $0.60/$3.56，可能整條 chain 順序都要重排。更遠一點：Nexus 客戶採購 deck 未來可以加一維量化說明——「我們的 Claude_auto pipeline 每天 X 個 task 每月 $Y 實付、換 Gemini 3 Flash 是 $Y/12」——把 token cost 從「模糊承諾」翻「精確報表」。這也是 Nexus `packages/cli` 可以加的一個 primitive：`nexus cost estimate <workload-dir>`，讀 repo 內所有 code file、跑每家 tokenizer、輸出 $/task 對比表，讓客戶自己選要用哪家。

## Ray Myers：Zig 作者說直話，Anthropic 吹煙——Bun 重寫給 agentic review 的啟示

用你目前在 Nexus 做 PR review pipeline（reviewer + arbitrator 兩階段 subagent）的視角，這件事讓你**校準對「agentic review」的期待邊界**——[Ray Myers 7/13 貼文 Zig Creator Calls Spade a Spade, Anthropic Blows Smoke](https://raymyers.org/post/zig-creator-calls-spade-a-spade/)（HN 1412 點 706 留言，7/13 全站頭條）針對 Anthropic 宣傳 Bun 從 Zig 全面重寫到 Rust 是 AI 主導完成、暗指 AI 能取代 software engineer 這條敘事，找出三個技術破綻。第一，Bun 選 Rust 的**明確理由是 borrow-checker**——原話「Bun chose Rust's borrow-checker because AI isn't enough」，如果 AI 真的夠好，borrow-checker 這種靜態擋 memory bug 的護欄根本不需要，這件事本身就是 AI 能力不足的證據。第二，Bun 從沒認真嘗試過**Zig 語言內的 style guide** 路線（像 TigerBeetle 那樣用嚴格 memory allocation discipline 換來金融級可靠性），直接跳 rewrite 是把 style guide + code review 那條**架構解決方案**跳過。第三，Anthropic 的宣傳文只寫 upside、沒寫 tradeoff（Rust 增加的 build time、生態依賴變動），這是**選擇性揭露**。

Myers 對「agentic review」的看法沒有全盤否定，他原話「agentic review works…under the right circumstances」——但那些「right circumstances」是**設計得夠好 + 有清楚 guideline**。TigerBeetle 財務資料庫用嚴格 memory allocation discipline 撐可靠性，那份 discipline 是**人先想清楚寫在 style guide**，然後 code review（含 AI）拿 style guide 當 constraint 對照。這條路線跟 antirez 今天同時發的那篇「Control the Ideas, Not the Code」異曲同工——**pipeline 有明確 constraint 才 review 得動**。同時 Andrew Kelley（Zig 創始人）對 Bun 團隊管理跟工程實踐的批評（Myers 描述為 blunt tone、「gained a new fan today」）也提醒一件事：**vendor 敘事跟工程實質**是兩件事，Zig → Rust 的重寫背後有多少是「AI 真的做完」多少是「工程團隊管理問題選擇 rewrite」需要獨立來源交叉驗證。

以前你設計 Nexus PR review pipeline，預設 reviewer / arbitrator 兩階段就夠處理一般 PR——這條假設隱含「reviewer 自己知道什麼是好 code」。從今天起 Myers 這篇提醒你：**任何 agentic review 都需要 pipeline 外的 explicit constraint**——DESIGN.md（antirez 的路線）、style guide（TigerBeetle 的路線）、architecture principle 文檔（Nexus 的路線）——任選一種但**一定要有**。Nexus `packages/ui` 現在的 review pipeline 已經有 DESIGN.md 當 constraint、有 OKLCH token 語意規範當 constraint、有 AnnotationCard 專屬色彩規範當 constraint——這條 setup 恰好符合 Myers 說的 right circumstances。對外行銷 Nexus 的 AI-assisted design system 時要注意的邊界：不要學 Anthropic 那種「AI 主導完成」的敘事，要學 Bun 那條 borrow-checker + style guide 疊加的敘事——**AI 加人的 discipline 才是 pipeline，不是 AI 一鍵完成**。
