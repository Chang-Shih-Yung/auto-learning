## Ant JavaScript runtime：8 MB 二進位、5.5 ms cold start、比 Node 快 5.22×

用你目前的 Nexus `packages/cli`（`npx @nexus/cli add` 為主要對外 primitive），這件事讓你可以認真評估把 CLI 分發從 Node/Bun 換到 [Ant](https://antjs.org)（[GitHub theMackabu/ant](https://github.com/theMackabu/ant) 700 stars / MIT / 昨晚 Show HN 231 點 101 留言）——**二進位 8 MB vs Node 120 MB / Bun 60 MB / Deno 90 MB**，**cold start 5.5 ms vs Node 28.7 ms / Bun 10.6 ms / Deno 24.8 ms**（M5 Pro / macOS 26.5.1、hyperfine 10 warmup + 100 runs 實測，Hono 兩路由 app import 到 process.exit）。同一個 Hono benchmark，Ant 比 Bun 快 1.93×、比 Deno 快 4.51×、比 Node 快 5.22×。install 是一行 `curl -fsSL https://antjs.org/install | bash`，走 WinterTC Minimum Common API（Ecma TC55 server-side JS 互通規格），compat-table 1511/1511 通過。

Ant 的引擎叫 Ant Silver，**不是 V8/JSC/SpiderMonkey 的 wrapper 是自己手刻的**，JIT 走 [MIR](https://github.com/themackabu/mir) 的 fork（輕量 backend，作者原話「near compiled performance」）。這條路徑跟 Bun 用 JSC、Deno 用 V8 完全不同——過去自建 JS 引擎的成本高到只有 Google / Apple / Mozilla / Meta 能做，Ant 這種一個人的 side project 能把 test262 拉到 ~64% pass rate 已經證明 MIR 這類 lightweight JIT backend 把「JS 引擎工程」的門檻拉到個人開發者也能碰的高度。二進位 8 MB 靠三件事撐住：自研引擎沒有 V8/JSC 那種 legacy 支援包袱、MIR JIT 不帶 Turbofan 那種大 pipeline、`-Os` 編譯 flag 進一步壓到 4.1 MB（release build）。

以前你要把 Nexus CLI 塞給企業客戶（特別是離線環境或 Docker layer 敏感的場景），Node runtime + `node_modules` 動輒 100 MB 起跳，客戶 CI 上一次 `docker pull` 燒的頻寬跟本體 CLI 沒什麼關係。從今天起 8 MB 是可能的：CLI base image 從 `node:20-alpine`（~50 MB decompressed）換成 `scratch + ant binary`（8 MB），cold start 從 28.7 ms 掉到 5.5 ms 對 GitLab CI runner 每次 job spin-up 有直接影響——一個 pipeline 跑 20 個 job，累積省下 460 ms 冷啟動。當然 Ant 剛上 Show HN 十幾小時，test262 只 64%（Node/Bun/Deno 都是 95%+），你現在不會拿它跑生產 API，但 Nexus CLI 這種只用有限 API 表面的工具是**天然的第一批測試場景**——大約 20-30 個 npm dep 全用 WinterTC common API 的話，Ant 現在就可能跑得動，值得在 side project 用 Ant 打包一次看實際 bundle size 跟啟動時間差多少。

## SQLite STRICT tables：學 SQL 第一天就該打開的開關

用你正在學的 SQL（`learning_now: sql`），這件事讓你直接跳過 SQLite 40+ 年 legacy 的 type-coercion 坑——[Evan Hahn 7/11 發文](https://evanhahn.com/prefer-strict-tables-in-sqlite/)（HN 254 點 127 留言，10 小時前上榜）示範一個非 STRICT 表可以做的事：`CREATE TABLE people_nonstrict (age INTEGER); INSERT INTO people_nonstrict (age) VALUES ('garbage');` 直接通過。相同 SQL 只要在 `CREATE TABLE` 結尾加一個 `STRICT` 關鍵字，`INSERT` 立刻炸 `cannot store TEXT value in INTEGER column`。**STRICT 表只允許 6 種類型：`INT`、`INTEGER`、`REAL`、`TEXT`、`BLOB`、`ANY`**——比非 STRICT 少一堆奇怪的「假類型」（VARCHAR(255)、CHAR、NUMERIC 那類其實都被吃成 TEXT/NUMERIC affinity）。你需要彈性欄位用 `ANY` 就好，仍然拿得到 STRICT 表的 schema 檢查。

SQLite 的 type affinity 是 40 年 backward-compat 的產物——1990 年代版本 SQL 為了容忍髒資料，設計成 column type 是「hint」而非「constraint」，`INTEGER` 欄位吃到 `'garbage'` 只會存字串，不報錯。這個行為讓大量早期 SQLite app 沒有 schema 檢查也能跑，但代價是 bug 藏到 read time 才炸——你的 report SQL `SELECT AVG(age) FROM people` 直接因為某一列是 `'garbage'` 得到 NULL 或錯誤結果。STRICT 表 2021 年才加進 SQLite 3.37（相對這個 engine 的年紀是「新功能」），核心設計是把 column type 從 hint 升成 constraint，走跟 Postgres/MySQL 相同的世界觀。文章特別強調一個 migration 陷阱：**你不能用 `ALTER TABLE` 把既有非 STRICT 表轉成 STRICT**，只能 `CREATE` 新 STRICT 表 → `INSERT...SELECT` 灌資料 → `DROP` 舊表 → `RENAME`；如果既有資料就有髒資料，`INSERT...SELECT` 會炸，先手動 cleanup 才能遷移。

以前你學 SQL 第一天遇到 SQLite，往往在教學裡看到「column type 只是建議」這種違反直覺的敘述，得花一個下午理解「type affinity」為什麼跟 Postgres 不一樣，繞完一圈才發現這是 legacy 而不是設計選擇。從今天起，如果你新開一個 SQLite `.db` 檔（Nexus 元件庫的 usage telemetry local cache、Claude_auto 的 session log DB、或任何 side project），第一行 `CREATE TABLE` 就固定寫 `... STRICT`，只用 6 種類型記，不去碰 type affinity 那套 legacy 邏輯——學 SQL 的心智模型直接跟你日後遇到的 Postgres / MySQL 對齊。搭配 `sqlite-utils` Python CLI 也已經加了「非 STRICT 表批次轉 STRICT」的功能（作者是 Simon Willison），既有 side project 的 DB 也能一次遷移過去。

用你正在評估 Claude_auto fallback chain 的視角，這件事讓你直接對 xAI 的官方 harness 打上 red flag——[cereblab 的 wire-level analysis](https://gist.github.com/cereblab/dc9a40bc26120f4540e4e09b75ffb547)（HN 226 點 112 留言，5 小時前上榜）證明 Grok Build CLI **v0.2.93** 在使用者不知情下把整個 repo（包含 `.env` 秘密檔）上傳到 Google Cloud Storage bucket `grok-code-session-traces`。實測 12 GB 測試 repo 上傳 **5.10 GiB（5,476,228,005 bytes / 73 個 chunk 各約 75 MB）** 到 `POST cli-chat-proxy.grok.com/v1/storage` 再轉走 `storage.googleapis.com` 多段 PUT，全部 82 個 upload 回 HTTP 200 才被稽核者主動截斷。同一次 session 另一條 `POST /v1/responses` 只走了 192 KB / 5 requests——**codebase 上傳量是 model turn 內容的 27,800×**，證明上傳跟 agent 實際讀了什麼**完全脫鉤**。`.env` 裡的 `API_KEY=CANARY7F3A9-SECRET` 這種 canary 秘密**完整、未 redact 傳出**。稽核者從 wire capture 出來的 git bundle 直接 `git clone` 出完整歷史——agent 從來沒讀過的檔案也在裡面。

最關鍵的一件事：**「Improve the model」toggle 關掉沒用**。稽核者關掉之後 `GET /v1/settings` 仍然回 `trace_upload_enabled: true`，實驗重跑，整個 repo 還是傳出去。GCS bucket 名 `grok-code-session-traces` 直接寫死在 binary（SHA-256 `2a97ba675bd…d767c`）跟 wire capture 的 `metadata.json` 裡，不是誤觸發、不是 debug 遺留、不是可以 opt-out 的功能——這是設計層面的**強制 telemetry pipeline**。對比同一週 [Claude Code v2.1.207 剛修的 remote managed settings 靜默同意漏洞](https://github.com/anthropics/claude-code/releases)——Anthropic 那條是 CLI 沒彈同意 dialog 就記下 consent（bug），xAI 這條是設計就不給 opt-out（feature by design）。兩家 harness 對「使用者資料上雲」的 default posture 差在世界觀，不在版本號。
