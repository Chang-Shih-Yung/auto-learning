## shadcn 4.13.0 — Base UI 翻預設，Radix 只剩 `-b radix` 一行 flag

你 Claude_auto 這個 Next.js + shadcn/ui + React 專案，過去每次 `npx shadcn init` 拉下來的 primitives 都是走 Radix；今天起（release shadcn@4.13.0，2026-07-03 12:29 UTC，HN 170 點 / 64 留言）新專案預設換成 Base UI，同一組件抽象、同一個 `components/` 目錄結構、同一份 Tailwind class 名稱——你原本 Claude_auto 的 shadcn 元件不用動，新拉的專案直接吃 Base UI 1.6.0（已標 stable、6M+ weekly downloads）。要留在 Radix 的話 `pnpm dlx shadcn init -b radix` 一行 opt-out；舊專案要遷移吃官方 migration skill `pnpm dlx skills add shadcn/ui` + 一次遷一個 component `migrate accordion to base-ui`——不是全炸重寫是每個 component 獨立可翻。shadcn 原話「The worst thing you can do for your production app is switch component libraries」直接寫進 changelog，「Radix is not being deprecated. You do not need to migrate」——policy 是「新專案給 Base UI 當預設，舊專案留 Radix 不強迫」。

背後是「headless UI library 的默契輪替」——shadcn/ui 走 copy-paste + 自己擁有原始碼路線本來就跟底層 primitives 解耦，只要新底層跟舊底層抽象一致（Popover/Dialog/Combobox/Tabs 這種 accessibility + 鍵盤導航 + focus trap 三件核心一樣），底層可換而 component API 對使用者不變。Base UI 是 MUI（Material UI）團隊三年拆出來的 unstyled primitive，過去一直卡 alpha，7/2 前後 1.6.0 標 stable + 6M+ weekly downloads 已達 production 門檻——shadcn 選這個時間點翻預設是等 Base UI stability + downloads 兩軸都到位。migration skill 一次一個 component 是「LLM 遷移的正確粒度」——過去換 primitive library 是「一次全炸重寫」風險 high、blame 難 pin；今天是「一個 skill 一次 migrate 一個 primitive、單一 PR 單一 blast radius」，AI-assisted refactor 已把「換底層」的成本從 project-level 降到 component-level。

以前你要換 shadcn 底層要開一個 spike branch + 一次 npm swap 掉 @radix-ui/react-* 所有 primitive + 手動處理各 component 的 API 差 + 一次 review 幾百行 diff + 抖三個月 UI 側 regression；現在 `pnpm dlx skills add shadcn/ui` 拿到 migration skill 一次 migrate 一個 accordion / dialog / combobox，Claude Code 讀 migration guide + 你的 component 源碼 + 產出單一 component PR、blast radius 收在單一元件。對你 Claude_auto Next.js 專案而言，短期不動（保 Radix）、下一次拉新 side project 直接吃 Base UI 感受 downloads/stability trade-off 之後再決定要不要遷。

## Armin Ronacher「Better Models, Worse Tools」— Opus 4.8 在 Pi 的 edit tool 20% fail，換 tool schema 就掉

Flask 作者 Armin Ronacher 7/4 發文（lucumr.pocoo.org / HN 192 點 65 留言）把一個過去講不清楚的痛點量化：新版 Claude 模型（Opus 4.8、Sonnet 5）整體能力升，但**跟 Claude Code 之外的 tool schema 相處變差**。他實測 Pi（他的 CLI agent）的 edit tool，Opus 4.8 一直發明 schema 上不存在的 field：`"requireUnique": true`、`"type"`、`"id"`、`"oldText2"`、`"newText2"`——他原話「a whole zoo of invented trailing keys」。在他其中一個使用者的 session 裡 Opus 4.8 **失敗率約 20%**，把 thinking blocks 剝掉之後失敗率砍一半（10%）——但 gpt-oss / OpenAI Harmony format 跑同樣的 schema 沒這個問題。他的診斷：Anthropic 用 RL 把 Claude Code 官方 tool schema 訓進權重，副作用是模型看到「像但不完全一樣」的 tool schema 會自己補上它覺得應該有的 field。你跑 Claude_auto 排程七步用到 WebFetch、Read、Write、Bash——都是 Claude Code 官方工具，Ronacher 這個問題不會直接打到你；但你未來把 Claude_auto SKILL.md 的 skill primitive 從「叫 Claude Code 內建工具」翻「叫自己包的 npm CLI + 自訂 tool schema」（例如 `nexus token-review` 命令）就會撞上。

背後是「tool schemas are not neutral」這條 Ronacher 的原話——LLM 對 tool schema 的順從度不是能力的線性 function，是**訓練分布**的 function。過去大家默認「模型越強、tool use 越穩」，但 RL post-training 若集中在單一 harness（Claude Code 官方那組工具），能力提升的路徑就是「這組 schema 越用越熟」而非「所有 schema 都越用越熟」。副作用是「你的 tool schema 跟官方越像但差一點」反而觸發模型「補上它以為應該有的 field」的 hallucination——比完全不同的 schema 還更容易錯。Ronacher 提的解法是**引擎層 constrained sampling**——OpenAI Harmony 用 grammar-aware decoding 在 token 生成時就擋掉不合法的 keys，Anthropic 目前靠 post-hoc validation（生成完再檢查）失敗只能重試不能阻止。這條軸接 6/29 antoine MRI「subagent 從平行加速翻 bias-free 判斷」+ 7/1 Sonnet 5 v2.1.197「context 從約束翻工作單位」演進到「schema 順從度從能力 function 翻訓練分布 function」，證明 LLM 的可靠性設計，越來越不能靠模型自律。

以前你以為「換更強的 model」就等於「tool use 更穩」——這個 heuristic 過去對 Sonnet 3.5 / Opus 4 / Sonnet 4.6 都對得上；今天 Ronacher 給你反例：Opus 4.8 對「非 Claude Code 官方 schema」的順從度可能比 Sonnet 4.6 差，換句話說**能力 vs 順從度**在 2026-Q3 開始解耦。對你 Claude_auto 而言短期沒動，但 (a) Nexus packages/cli 未來對外開放 MCP tool 時要**跟 Claude Code 官方 schema 保持顯著距離**（field 命名故意不撞 official pattern，讓模型不會 fallback 到熟悉 schema），(b) 排程觸發若真要包一層 custom shell agent，schema validation 端要走 JSON Schema strict + 拒絕未知 field 而非放寬吸收——不是靠模型自律，是靠 schema enforcement 硬擋。

## Claude Code v2.1.199/200/201 — 三天三 patch，default permission 從 auto 翻 Manual

Anthropic 三天連推 v2.1.199（7/2 23:35 UTC）、v2.1.200（7/3 16:52 UTC）、v2.1.201（7/3 23:50 UTC）——你 Claude_auto 排程明天早上如果沒鎖 requiredMinimumVersion 就會自動吃到這三版全部差異。最大的一件是 **v2.1.200 把 default permission mode 從 `default` 翻 `Manual`**——過去你不設 `--permission-mode` 或 `defaultMode` 就是 auto-approve 一批 low-risk 動作、遇高風險才 surface；今天起預設是每個工具都 surface 給人 approve。CLI、`--help`、VS Code 插件、JetBrains 插件全部同步這個新預設，但保留 backward-compat（`default` 這個字仍接受、只是名字換成 Manual）。同版順便把 `AskUserQuestion` dialog 的「auto-continue after idle timeout」預設關掉——過去 5 秒沒動作它會自己選預設答案繼續，現在必須顯式打開才有這行為。

技術上這是「permission posture 從 opt-out 翻 opt-in」的第一次官方預設翻牌——搭 6/26 v2.1.193 `autoMode.classifyAllShell` 把 Bash 命令一律過 classifier + 6/29 v2.1.195 hook matcher exact match + 7/1 v2.1.197 Sonnet 5 default 四條連續軸推到「session 開始時預設**不信任**」。v2.1.200 同時修好一票背景 agent 沉默失敗：daemon.lock 卡住不再重啟、subagent rate-limit 前無 output 時回空結果而非 fail、多版本 daemon handover 用 build timestamp 判定 recency 防舊 binary 蓋新 binary。v2.1.199 補 SSL cert error 立即失敗不再重試燒 token、streaming 中途 overloaded 保留 partial output 加 incomplete notice、subagent 遇 rate-limit 或 server error 現在回 partial 而非沉默 success。v2.1.201 針對 Sonnet 5 專案取消 mid-conversation system role for harness reminders——你 7/2 session 摘要提過 Sonnet 5 + 1M context 讓 monorepo 一次餵完，v2.1.201 讓長 context session 不再被中途系統訊息干擾 attention。

以前你 Claude_auto 排程七步一鍵跑到底靠的是 auto-approve 一批常用工具，人不在電腦前也能收工；現在 v2.1.200 預設翻 Manual 之後你排程一開就會卡在第一個 `AskUserQuestion` 或第一個工具授權——除非你在 SKILL.md frontmatter 顯式加 `defaultMode: default` 或 `--permission-mode default` 把舊行為叫回來。三件同時發生：**你 Claude_auto SKILL.md 要鎖 requiredMinimumVersion 2.1.199 或 2.1.201**（拿到 stacked slash-skill 修 + subagent silent-fail 修 + Sonnet 5 harness reminder 移除），**排程 flag 要顯式加 `--permission-mode default`**（不然預設 Manual 一開就卡），**Nexus PR review 背景 agent 要驗過三版 daemon.lock 修**（避免 6/29 之前寫的 auto-workflow 被 stale daemon 卡住 restart 不回來）。

## Figma-to-code 真正的轉折 — 「missing middle」跟 Design Engineer 新角色

Sébastien LaFlèche 這篇（dev.to slafleche 7/3）站在 monday.com / Shopify Polaris / Ramp / eBay Playbook / Twilio Paste 五個 production design system 案例把「Figma → code」整條鏈的**現況跟盲點**攤開。核心數字：82.3% designers 用 Figma 當主力 UI tool、60% 花 $100k+/年 Figma customers 每週用 Make、monday.com engineering team 70-90% 元件 code 由 pipeline 生成（Elad Mizrahi）、Shopify designers 講 80% 門檻、Ramp 講 70%——這條頂已經到了。但同一份 2025 年 158 個 design system 調查：37% 有 usage guidelines、21% 涵蓋 accessibility、13% document component content，只有 3 個系統（Polaris/Paste/eBay Playbook）拿滿分——「AI 讀不到的東西 pipeline 就會亂猜」。DTCG Design Tokens spec 2025-10 剛升 stable、Style Dictionary 已支援、Google 有 DESIGN.md 規格——工具鏈就位、卡點在**沒人做 middle**：Figma 給 bare float 值、code 側需要 semantic token，中間那層「哪個 hex 對應 primary-500、哪個間距對應 layout gap」目前**全丟給模型猜**。

背後是「missing middle」這個 LaFlèche 提出的概念——目前 Figma → code 鏈裡有 (a) design tool 端（Figma、v0、Lovable、Bolt、Figma Make、Anima、Subframe）、(b) code 端（React/Vue/Angular component）、(c) 中間 resolve + token + codegen 三段被當**確定性決策**塞給 LLM 猜。Romina Kavcic 兩句原話一針見血：「When a human expert fails, they come back with a reason. With agents, 25 failures land on your desk with no insight.」+「Agents can only work with what's documented. Many systems aren't ready for a human to use properly, let alone a machine.」他跟 monday.com 一致的解方是**把 middle 拆出來當 first-class artifact**——monday 的 agent 不返回「finished code」而是返回「structured context」讓 developer 拿；然後這個 middle 需要一個新職稱：**Design Engineer**，專門擁有「哪個 token 對應哪個語意 / 哪個 component 對應哪個 pattern / 邊界怎麼決」這條決策鏈。

以前 Figma → code 討論永遠停在「哪家生成器最強」（v0 / Lovable / Bolt / Anima / Subframe 拉鋸）——這篇把爭論翻掉，重新指出「70-90% 的天花板不是模型問題是文檔問題」。你 Nexus packages/ui 的 Figma → JSON → OKLCH Token → Angular 三段其實就是**middle 這一層的具體實作**——你 already 站在 Design Engineer 的位置。這篇文章給你的兩個具體 leverage：(a) **Nexus 客戶採購 deck** 加一段「我們不是另一個生成器，我們是 middle」用 82.3% + 158 個 design system 21% accessibility 這些數字支撐差異化；(b) **packages/ui 的 documentation 密度** 從 usage guideline 37% 業界基線推到 100% 覆蓋——因為 middle 值錢的部分不是「你的 CSS 寫多漂亮」是「你的 token 對應的語意有沒有文檔化到 agent 讀得懂」。

## ESLint 憑證掃描 842 → 0 false positives — regex + entropy 不夠，還要 identifier context

Ofri Peretz 7/3 發文（dev.to ofri-peretz）記錄一個典型 SAST 誤報翻修——他寫的 `eslint-plugin-secure-coding` 規則 `no-hardcoded-credentials` 在 vercel/ai repo 掃出 **842 個 findings**，抽樣後 807 個都是誤報：TypeScript union type literal 像 `'experimental_onToolExecutionStart'`、error class name 像 `'AI_ToolCallNotFoundForApprovalError'`、測試字串 `'test'`——實際硬編碼憑證數量：**0**。根因是規則用 generic regex `^[A-Za-z0-9_-]{32,}$` 想抓「32+ 字元隨機字串」，結果把所有 TypeScript 描述性命名（很多 32+ 字元 identifier）當作 credential match，同時 password check 把字面 "test" 全打成 password。修法不是升 regex，是引入**信心分層**：**high-confidence structural pattern**（JWT `eyJ...` / OAuth `ghp_`, `gho_` / AWS `AKIA[16 chars]` / DB connection string）直接報；**ambiguous pattern**（generic 32+ 字元 / 常見 password literal）**必須看 surrounding identifier context**（`apiKey`, `secret`, `password`, `token`, `clientSecret` 這些命名）才報。改完 842 → 0 誤報，precision 從 0.67 升 1.00，recall 保持 1.00。

背後是「pattern + entropy 判斷 credential」這條 40 年老 SAST 路線的**盡頭**——過去 gitleaks / trufflehog / detect-secrets 都靠 regex + Shannon entropy 判斷「這串像不像 credential」，準確度天花板卡在「無法區分『隨機字串』跟『長描述 identifier』」。TypeScript 這種強命名語言（同一段 code 常見一堆 30-50 字元 union literal + error class name + type name）把這個問題放大到「傳統 SAST 出 90% 誤報是常態」。作者的修法不是換更強的 regex 也不是升 entropy 閾值，是**引入語義層信心分層**——把「值本身」跟「上下文」拆開判斷，pattern 分兩層（結構性 vs 模糊）、模糊層必須有 identifier context 佐證才報。這條軸接 6/26 Scorer vs Decider「LLM 打分 + code 決策」+ 6/29 Semgrep Multimodal harness 設計比 base model 差距大——「檢測工具的準確度天花板越來越不在 pattern 而在 policy layer」。

以前你 Nexus GitLab CI 白箱 SAST 整合是「跑一輪 gitleaks + 出 100+ finding + 手動篩掉大部分」，每個 PR 都要 designer + engineer 兩人審一遍**誤報**才拿到真正的疑慮清單——每輪 15-20 分鐘 dev-time 白燒。這篇給你 (a) **SAST rule 分層策略**：high-confidence pattern（JWT/ghp_/AKIA/DB string）走 default report、ambiguous 走 `require-identifier-context` 過濾一層，能砍 90%+ 誤報同時保 recall；(b) **Nexus PR review pipeline 直接可套**：token JSON 觸及時跑 SAST 分層策略——`primary-500` 這種 semantic token 名稱旁的 hex 值走 low-confidence（跟 credential 完全無關），要有 `apiKey` / `secret` 這類命名旁的 hex 才升 high-confidence，把 Nexus PR CI 內部 SAST 誤報從常態變邊緣。

> ⚠️ `eslint-plugin-secure-coding` 目前是作者個人專案，尚未達 500 stars / 10k weekly downloads 門檻，新工具使用前請自行確認安全性；上述設計思路（confidence 分層 + identifier context）可獨立採用，不必綁定該套件。

## 今日總結

今天 5 條獨立來源的路徑指向同一個工程動作——**「以前藏在 LLM 訓練分布 / 底層 primitive / 預設信任 / 設計文檔缺口 / SAST regex 裡的黑盒判斷，都在被翻成可見的分層決策」**。

- **shadcn 4.13.0 換底層 primitives** 從「一次全炸 project-level swap」翻「一個 skill 一次遷一個 component」；
- **Better Models: Worse Tools** 用 Opus 4.8 20% invalid tool call 證明「能力提升 ≠ tool use 順從度提升」，schema 順從度是**訓練分布 function 而非能力 function**；
- **Claude Code v2.1.200 default permission Manual** 把 session 預設信任 posture 從 opt-out 翻 opt-in；
