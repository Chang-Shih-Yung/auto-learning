# 2026-07-06 學習日誌

## GPT-5.5 Codex 的 reasoning token 集體塞在 516

用你的 OpenAI Codex 開發流程，可以直接讀 GitHub issue [openai/codex#30364](https://github.com/openai/codex/issues/30364)（6/27 開，7/5 HN 357 點 148 留言）的 **390,195 筆 token record + 865 個 session** 統計，看到自己每天用 GPT-5.5 完成 task 的 `reasoning_output_tokens` 是不是也擠在 516 這個奇怪的常數上——這條線一旦命中，複雜任務的答案品質會下滑。issue 顯示 **3,363 筆 exact-516 事件裡 82.0% 都來自 GPT-5.5**（同期它只佔全體 sample 的 19.3%），**44.0% 的 GPT-5.5 ≥516-token response 剛好停在 516，其他模型只有 1.3%**。

reasoning 輸出被 clustering 到固定邊界（516、1034、1552）等於是隱藏的 chain-of-thought truncation：模型明明還可以繼續推理，卻在特定 token 數被中斷，剩下的字元用來擠出答案。單月 clustering 比例 **2 月 0.11% → 5 月 53.30% → 6 月 35.84%**，證明這不是偶發雜訊，是伺服器端在特定時期硬套上去的 quota。作者強調自己並未證實是 CoT 截斷，但相關性讓 token 分布直方圖第一次變成一種 reliability signal。

以前 AI 平台的品質退化是 vibes-based——「我覺得今天 Codex 好像變笨」你只能改口 prompt 或換模型。現在 token 直方圖攤在 issue tracker 上，複雜任務失敗率跟 exact-516 命中率能拉出關聯，reliability 從主觀感覺翻可量化 telemetry。你可以在自己的 CI 加一行「收 `reasoning_output_tokens` 分布 + 當日答對率」，看到 clustering 集中在單一常數就自動降級到 fallback 模型，不用等社群集體感覺退化才反應。

## Claude Code Enterprise ZDR session 疑似跨 workspace 漏水（issue #74066）

用你的 Claude Code v2.1.199 登入 Enterprise ZDR workspace 跑排程任務，這件事讓你可以直接在 GitHub issue [anthropics/claude-code#74066](https://github.com/anthropics/claude-code/issues/74066)（7/4 開，HN 313 點 131 留言）看到有個 macOS 使用者的 agent 突然自信說「我在幫你蓋 Minecraft 神殿，你想用哪種磚？」——工作內容完全跟他當下的專案無關。issue 掛了 **4 個標籤 area:core / area:security / bug / platform:macos**，都指向同一個問題：workspace 之間的 session cache 可能沒隔乾淨，甚至可能從 consumer plan 帳號洩到 Enterprise ZDR session。

使用者的 launch directory 有 `.claude/` context 資料夾，但實際工作目錄是另一條路徑——如果 client 端 cache key 沒把「launch dir + workspace ID + auth realm」三軸都綁進去，就會出現跨 workspace 讀到別人 conversation history 的縫。ZDR（Zero Data Retention）承諾內容不會被保留到 Anthropic 後端，但這條路線是 **local cache 到 local cache 的橫向漏水**，不走 server 也可以發生，ZDR 承諾在這種故障模型下管不到。

以前 AI IDE 的 session isolation 是「跑得起來就好」的隱性合約——大家假設 `.claude/` 只從當前工作目錄讀取。這個 bug 攤開之後，isolation 變成 first-class 稽核項目：Enterprise 客戶採購前會問「不同 workspace 的 launch dir、cache key、context file 三軸能不能各自獨立？」consumer 到 Enterprise 的降級路徑會被單獨 audit。你以後排 Claude_auto 之類的自動化 session 時，preflight 檢查得多一條「當前 workspace 的 cache dir 沒有其他 workspace 內容外洩」。

## Marcin Wichary：如果你是 button，你只有一份工作

用你的 iPhone 拍完 8 張橫向的文件掃描想批次逆時針轉正，你按下 rotate button 連續 **8 下 90° 旋轉**——iPhone 每按一下都會把 tap 事件緩衝起來排隊處理，動畫可以邊播邊接收下一次點擊，8 下按完動畫也在跑完最後一輪。同樣操作在 Nothing Phone 或多數 Android app，動畫沒跑完的期間 **tap 會被丟掉附送 haptic 提示**，你必須乖乖等每一輪動畫結束才能點下一下。文章 [unsung.aresluna.org](https://unsung.aresluna.org/if-youre-a-button-you-have-one-job/) 7/4 發，作者 Marcin Wichary（前 Figma / Google 資深設計師），HN 534 點 254 留言。blog 的 tag 分布 flow 42 / touch 16 / popular 14 / ios 13 / android 3，touch interaction 是 unsung 這個 blog 的長期主題。

「never force the user to wait for the animation to finish」這句話拆開有兩個實作路徑：一是 **tap buffering**（iPhone 走這條，tap event 先入 queue，動畫 timeline 跟事件 queue 解耦），二是 **animation interruption**（點下一次的瞬間，前一次動畫立刻停止或加速播完）。兩者實作差在 event queue 是不是跟 renderer 的 `requestAnimationFrame` 綁死——綁死就丟事件，解耦就緩衝。「situational power user-ness」這個概念是背後的世界觀：一般使用者 99% 場合不會連點，但 1% 的重複性任務必須跑得動，好的元件必須把這 1% 內建。

以前元件庫 Button 只想著「單次點擊」——設計 spec 寫「hover / active / disabled 三種 state」就交差，rotate / increment / step 這類連點場景全丟給 app 開發者自己處理。從今天起，Button 這個 primitive 必須把 tap buffering 或 animation interruption 兩條策略至少內建一條，元件文件裡要說明「連按 8 次的行為是什麼」。你以後在 Nexus packages/ui 收到 designer 交來的 Button spec，先問一個問題：「連按不放的時候，8 次點擊會被吃到幾次？」動畫 300ms 內連點吃掉 3 下就是 bug——不管 Figma prototype 有沒有畫，元件必須撐得住。
