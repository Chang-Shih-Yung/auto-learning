## Claude Code v2.1.215——把 `/verify` 跟 `/code-review` 從「自動觸發」翻「使用者顯式叫」

**你能做什麼**

如果你像 Henry 一樣用 Claude Code 排程跑每日任務（例如 Claude_auto 這種每天早上抓 AI 新聞、寫 journal、跑 lint、commit + push 的完整 pipeline），今天 v2.1.215（7/19 UTC 發布）這條 release note 只有一句話但直接改變你排程的行為模型——**「Claude no longer runs the `/verify` and `/code-review` skills on its own; invoke them with `/verify` or `/code-review` when you want them.」**。翻譯成人話：**過去 Claude Code 會根據 conversation context 自己判斷「這步驟該不該跑 `/verify` 或 `/code-review`」然後自動觸發，v2.1.215 起改成純顯式呼叫——你不打 `/verify` 就不會跑**。這條改動對兩類使用場景直接可見：**(1) 排程跑（scheduled / non-interactive session）**——你 SKILL.md 裡不再需要「祈禱 Claude 別自作主張跑 `/verify` 把 CI 給拖垮」，也不用寫 workaround 明確叫它別跑；改成你要什麼 skill 就在 SKILL.md 明寫呼叫。**(2) 互動 session**——過去偶爾會被 `/code-review` 自動觸發打斷（例如你在改一個 refactor 卡到一半，Claude 突然自己跑一輪 `/code-review` 花 30 秒才回你），現在完全不會。這條 v2.1.215 是**七月連續五版更新**（v2.1.211 subagent thinking 顯式化 + `--forward-subagent-text` / v2.1.212 subagent + WebSearch 200 quota + `/fork` 拆成獨立 background session / v2.1.214 `dir/**` allow rule 從遞迴放行改成當層放行 + EndConversation tool + docker daemon-redirect flag + Bash > 10,000 字元 + FD redirect 檢查 / v2.1.215 skill auto-invoke 反向）中一致的 **default posture 從自動翻顯式** 動作。過去六週 Claude Code 從 v2.1.197 的 Sonnet 5 default → v2.1.200 default permission mode Manual → v2.1.207 Auto mode 從 env var opt-in 翻 settings opt-out → v2.1.211 `--forward-subagent-text` → v2.1.212 subagent quota → v2.1.214 permission rule 顯式細粒度 → v2.1.215 skill 呼叫顯式化，是**七版一個方向**：**agent autonomy 每一條線都在從「相信 agent 會做對事」翻「使用者顯式簽名確認每個動作」**。

**背後怎麼運作**

`/verify` 跟 `/code-review` 這兩條 bundled skill 過去是 Claude Code 內建的自動 QA gate——`/verify` 會在 code 改動後跑 typecheck / test / lint、`/code-review` 會用另一個 subagent 對 diff 做 correctness / simplification 找 bug。兩條 skill 的「自動觸發」邏輯過去是**藏在 Claude 主模型的訓練分布裡**——Anthropic 用 RL 訓 Claude Code 讓它在「你改了 code」時傾向自己叫 `/verify`，在「你改動 diff 夠大」時傾向自己叫 `/code-review`。這條設計哲學是「skill 就像 IDE 的 auto-format on save，agent 該自己判斷什麼時候跑」——聽起來合理，實際上出現三個問題：**(1) 排程 session 一致性差**——每次跑 SKILL.md 的 flow，模型可能自己決定跑或不跑 `/verify`，你 SKILL.md 執行結果的可重現性被破壞。**(2) token 浪費**——`/code-review` 一次要 spawn 額外 subagent 讀完整 diff，一次呼叫成本可能是幾千 token，你不需要它跑時它跑一輪就多花錢。**(3) latency 干擾**——互動 session 中被自動觸發打斷，UX 從「我叫 Claude 做事」變「Claude 決定先幫我做別的事再回來」，掌控感下降。v2.1.215 的解法是**把觸發決策從 model layer 搬到 user layer**——skill 呼叫從「模型判斷」翻「使用者輸入 `/verify` 或 `/code-review` 才跑」。這條改動的背後哲學跟 v2.1.200（default permission Manual）、v2.1.207（Auto mode opt-in 翻 opt-out）、v2.1.211（subagent thinking 曝露）、v2.1.212（subagent + WebSearch quota）、v2.1.214（`dir/**` allow rule 顯式細粒度）是同一條——**「agent autonomy 的邊界必須是使用者的顯式輸入定義的，不是模型的隱式訓練分布定義的」**。這條 posture change 也對應了 6/28 Anthropic 內部政策文件那條「skills are user-invoked, tools are model-invoked」的區分——skills 是 workflow-level 動作、tools 是 primitive-level 動作，workflow 必須有使用者拉板機、primitive 才是模型隨叫隨用。

**這改變了什麼**

以前你寫 Claude Code SKILL.md 排程檔案，你的心智模型是「Claude 會在合適時候自己叫 `/verify`、我不用寫」，實際跑起來是「模型有時候叫、有時候不叫、每次結果不一樣」。今天起這個模糊區被關掉——**你要 `/verify` 或 `/code-review` 跑就得在 SKILL.md 顯式呼叫、你不寫它就不跑**。這條動作對 **Claude_auto** 直接可用——SKILL.md Step 4 目前是 `npm run lint:mdx` + `git commit` + `git push` 三條 Bash 命令，這條 pipeline 完全走 CLI 不呼叫 Claude Code bundled skill，所以 v2.1.215 對這條 flow 沒直接影響；但**未來如果考慮加一層 `/code-review` 對每天 journal 檔案的 markdown structure 做 sanity check**（例如「有沒有意外多寫一個 H1」、「AnnotationCard 屬性名有沒有拼錯」），現在你就必須顯式呼叫、不能靠 model 自己判斷。這條改動對 **Nexus packages/ui 未來對外開放的 CLI**（`npx @nexus/cli add`）也有直接啟示——**如果 Nexus CLI 內建「元件安裝後自動跑 typecheck」這種 skill，該學 v2.1.215 走顯式呼叫路線**（例如 `npx @nexus/cli add button --verify`），不要讓 CLI 自己判斷該不該跑，客戶排程要什麼行為就明寫一個 flag。這條 v2.1.215 也對 **Nexus 客戶採購 deck 第七維中立性「決策層 deterministic pipeline」** 補一個具體佐證——**Anthropic 自己都承認 model-driven 決策不夠可預測、要退回 user-driven 顯式觸發**，這條認錯跟 7/17 Salesforce Agentforce 9,000 → 5,000 裁員退回 deterministic automation、7/17 Pydantic「Human-in-the-loop is tired」是同一條 2026-Q3 產業共識。**七月連續五版一致方向的意義**：Anthropic 這波 default posture 改動不是「修 bug」，是**主動承認過去某些自動化決策方向錯了**——這條 vendor 側自我校準比任何官方公告更有說服力，值得寫進 Nexus 對客戶論述作為「industry-wide default posture shift」的第三方證據。

## Claude Code 底層 Bun runtime 已改用 Rust 重寫版——Simon Willison 逆向 binary 找出 561 個 Rust 檔名、Linux cold start 只快 10%、Jarred Sumner 一句「boring is good」

**你能做什麼**

如果你像 Henry 一樣同時用 Claude Code 排程跑事、也在做 CLI 工具（Nexus packages/cli），今天 Simon Willison 這篇 blog（HN 461 點、619 留言、頭條）給了**一份「大廠 CLI 底層 runtime 靜默換掉」的完整逆向報告**。事情發生在 **v2.1.181（release 6/17 UTC）**——Claude Code 底層的 Bun runtime 從原本的 Zig 版本換成 Rust 重寫版。這件事**Anthropic 沒公告、Bun 官方沒公告、release note 也沒寫**，是 Bun 作者 Jarred Sumner 六月中在 Twitter 才一句話認了。Simon Willison 用兩條方法驗證：**(1) `strings` 命令**掃 Claude Code binary，出現 `Bun v1.4.0`——這個版本比 Bun 官方最新 stable release 還早（Bun v1.4.0 canary 5/17 才推出、公開穩定版當時還沒發布）。**(2) 從 binary 抽出 561 個 Rust 檔名**（`grep '\.rs$'`），包含 `src/runtime/bake/dev_server/mod.rs`、`src/bundler/bundle_v2.rs` 等——確認整個 runtime 就是 Bun 那份 Rust codebase。第三條 verification 是**寫一個 TypeScript preload script 直接查 `Bun.version`**，回傳 `1.4.0`——三條路徑對得起來。**這件事最反直覺的數字是 performance impact**：Jarred Sumner 原話「Startup got 10% faster on Linux but otherwise, barely anyone noticed. Boring is good.」——換掉整個 runtime、跨越 millions of devices 的 production 部署，**Linux 冷啟動只快 10%、其他平台沒感覺**，使用者體感零。作者強調「barely anyone noticed」是這個 rewrite 最大的成功指標——**大規模基礎設施重寫最好的狀態是使用者根本不知道發生了什麼**。這條也對應 Bun 官方過去六個月一直被追問「你們到底重寫得怎樣了」——答案是**六月中就已經在 Claude Code 這條大 workload 上打完仗**，只是沒有官方公告。

**背後怎麼運作**

Bun runtime 從 Zig 改寫 Rust 這件事的完整脈絡可以往前推到 **2026-05 Anthropic 官方 blog「Bun's Rust rewrite: 90% agentic」**——那篇文章講「Bun 這個 rewrite 我們用了 Claude Code 幫忙寫 90% 的 code」，暗示 AI 能取代 software engineer 的敘事。**7/13 Ray Myers 那篇「Zig Creator Calls Spade a Spade / Anthropic Blows Smoke」**（HN 1412 點、706 留言全站頭條）針對這條敘事講了三個技術破綻——**(1) Bun 選 Rust 明確理由是 borrow-checker**，「AI 夠好、borrow-checker 就不需要」；**(2) Bun 從沒認真嘗試 Zig 語言內 style guide 路線**（像 TigerBeetle 那樣用嚴格 memory allocation discipline 換金融級可靠性）；**(3) Anthropic 宣傳文只寫 upside、沒寫 tradeoff**（Rust 增加 build time、生態依賴變動）。今天 Simon 這篇 blog 補上了**這條 rewrite 在 production 的真實 performance 數字**——**Linux cold start 只快 10%、其他平台無感**。換算成使用者價值：Claude Code 平均一次啟動時間就算是 200ms，10% 就是 20ms——**這條數字對「AI 主導的 rewrite 帶來壓倒性技術優勢」的敘事構成量化反證**。這條 rewrite 的**真正價值不在效能**，在**維護性**——Rust 生態工具更成熟、hire 更多開發者、debug 工具鏈更完整（Zig 這條依然小眾）。Jarred Sumner 那句「boring is good」是**對 rewrite 成本結構最誠實的一句話**——大規模 rewrite 的成功不是「效能爆快兩倍」，是「沒人注意到就換完了」，這種 boring 才是 production 級系統該追求的成功狀態。這條也對比出 **7/13 Ant JavaScript runtime**（8 MB binary、5.5ms cold start、自研 Ant Silver 引擎、比 Node 快 5.22×）那條「小廠獨立開發者做 runtime」的路線——兩條路徑走完全不同的成本模型：**Ant 是「一個人的 side project 追求極致 spec」，Bun rewrite 是「millions of devices production 上追求零 disruption」，兩者都合理，服務不同 workload**。

**這改變了什麼**

以前你評估「大廠 vendor rewrite」這件事的信任度是靠 vendor 官方 blog（「我們重寫得多好、AI 貢獻多少」），今天起你有**第三方逆向驗證這條路徑**——**Simon 這篇 blog 就是「不信 vendor 敘事、直接掃 binary」的示範**。這對 **Nexus 對外採購 deck** 有直接應用——**「vendor 敘事 vs wire-level / binary-level audit」這條中立性維度是 Nexus 可以打差異化的地方**：如果 Nexus CLI 對外開放，客戶（例如歐洲 GDPR audit 團隊）可以直接掃 Nexus binary 看有沒有 telemetry、有沒有藏 API endpoint，這條「可稽核性」對比 vendor 一句「我們尊重你的隱私」是完全不同層級的信任建立。**Bun v1.4.0 這條資訊**對 Nexus 也有時機性——**如果 Bun 官方 stable v1.4.0 未來幾週要正式發布**，Nexus packages/cli 若要打包成 standalone binary，可以評估用 Bun 這條路線（binary size 60 MB vs Node 120 MB、cold start 也快）。這條動作對 **Henry 個人的技術判斷力** 有一個更深的啟示——**「AI 完成度」跟「使用者可感差異」是兩件事**：Anthropic 講 90% agentic rewrite，但使用者體感 10% 冷啟動——**下次評估「AI-generated code / AI-driven refactor」這類敘事，該追問的不是「AI 貢獻了幾 %」而是「使用者拿到什麼可測差異」**。這條也對應 **7/14 antirez「Control Ideas Not Code」** 的哲學——review 應該從 code diff 級別搬到 idea level，但 idea level 的價值也要用 outcome level 的數字驗證。**Jarred Sumner「boring is good」這句話** 對 Henry 未來寫 Nexus packages/ui 對外 marketing 敘事也有直接參考——**Nexus 的成功不該講「元件庫 AI 生成 60%」（跟 Anthropic 講 90% 一樣容易被反駁），該講「客戶部署後幾週後就當作背景基礎設施、沒人再提元件庫這件事」**——這條 boring-is-good 的敘事對比業界「這是革命性 AI-native 元件庫」那條浮誇路線是絕對優勢。

## Kimi K3 上線 48 小時撞 GPU 天花板——Moonshot AI 暫停新用戶訂閱、會員拆成 Web/App/Work + Code 兩層、7/27 全權重開源時程不變

如果你在關心「開源大模型 vs 閉源 vendor 這條 2026-Q3 分岔」，或像 Henry 一樣在為 Nexus 設計 fallback chain（歐洲客戶要求 AI 呼叫必須有 self-hosted fallback），今天 Moonshot AI 官方 X 帳號（HN 247 點、Bloomberg + CNBC + TechNode + Global Times + Yahoo Finance 全報）宣布**Kimi K3 上線 48 小時後 GPU 撞頂、7/19 起暫停新用戶訂閱**——這是**開源大模型第一次公開撞到「demand 打爆 supply」的資料點**。時間軸：**7/17 Kimi K3 正式發布**（2.8T 總參數、Stable LatentMoE 16 experts × 896 dense-equivalent activation、1M 原生 context、DeepSWE 67.5 / Terminal Bench 2.1 88.3 / GPQA-Diamond 93.5 等 benchmark 全 top-3）、**7/19 官方一句「Kimi K3 has received far more love than we expected, and our GPUs are feeling it. **背後怎麼運作**

Kimi K3 這條 capacity crunch 的根因是**開源大模型的商業成本結構跟閉源 vendor 天差地遠**。閉源 vendor（Anthropic、OpenAI）的成本模型是「用戶付月費 / API 費用 → vendor 有錢買更多 GPU → scale capacity」——中間有一個內建的定價 signal 幫忙控 demand。Moonshot 走的是**「開源模型 + 極低 API 定價（$0.30 cache-hit input / $3 cache-miss input / $15 output per M tokens，是 Claude Opus 4.8 五分之一）」**的路線，這條定價策略在 demand ramp-up 期就是**「用低價換 market share，賭未來 hardware 成本會降下來或客戶會轉去自 host」**。7/17 一發布，Kimi K3 這條**「benchmark 打進 top-3、價格砍五分之一、1M context」**組合直接把大量 developer / enterprise 使用者從其他 vendor 拉過來——**48 小時就撞頂**證明這條定價 vs GPU capacity 之間的 gap 遠超 Moonshot 事前預測。這條動作的背後**商業戰略是「開源 + 低價」這條路線的 GTM playbook**——先用低價把使用者吸引過來、demand 爆炸時把權重放出去讓大家自 host、Moonshot 專攻高階企業 API（1M context 大單、大 workload 需要 SLA），這條 funnel 跟 DeepSeek、Qwen 那條路線一樣。**會員拆兩層**（Web/App/Work 一組、Code 一組）是**follow Claude Code / GPT-5.6 Codex 的 pricing playbook**——過去一年市場證明「AI Code workload 使用者比一般聊天使用者付費意願高 3-5 倍」，這條差異化定價讓 Moonshot 能在 Code 這條 vertical 上定較高單價、Web/App/Work 那條走 low-margin high-volume 路線。**7/27 全權重開源時程不變** 是這條 crisis 中 Moonshot 保留的最大槓桿——**「你要跑 Kimi K3、我 host 不動、你自己 host」**這條路徑對大企業客戶（合規要求 self-host、有自己 GPU cluster）是完美出口。**這條 capacity crisis 對「self-host 的市場需求」是最強第三方 signal**——過去大家講 self-host 是「隱私 / 合規需求」，今天起再加一條「vendor host 不動、你只能自己 host」的實務需求。

**這改變了什麼**

## AI 建議造成的「準確度掉、信心飆」剪刀差——Capraro / Marcoccia / Quattrociocchi 2026-07-19 preprint 首次量化人機協作的認知代價

**你能做什麼**

如果你像 Henry 一樣在建 AI-assisted workflow（Claude_auto / Nexus PR review pipeline），今天這份 Capraro / Marcoccia / Quattrociocchi preprint（University of Milano-Bicocca + École Normale Supérieure + Sapienza University of Rome 三方合著、2026-07-19 上 preprint、The Next Web 首篇報導、HN 323 點、182 留言）給了**第一份針對「AI 建議如何影響人類決策準確度跟信心校準」的量化研究**。實驗設計故意選一個 AI 會答錯的題型——**視覺細節回憶**（例如「Bend It Like Beckham 電影裡球員制服的顏色是什麼」這類問題）——因為研究者要看的不是「AI 準不準」而是「當 AI 給出錯誤答案時、人會信到什麼程度」。結果四個核心數字：**(1) 答對率**從 27%（無 AI 建議）掉到 9%（有 AI 建議）——**下降 68%**。**(2) 承認「我不知道」的意願**從 44% 掉到 3%——**下降 93%**。**(3) 信心分數**從 30% 升到 76%——**上升 153%**。**(4) 加金錢誘因**（答對給錢）後準確度救回 16%、「我不知道」意願升到 8%——**依然遠低於無 AI 的 baseline**。翻譯成人話：**參與者在有 AI 建議時、答錯的比例翻兩倍、拒絕承認不知道的比例翻十倍、對自己答案的信心翻兩倍多**——這條剪刀差量化了一個過去只是直覺的現象。**這條研究的關鍵設計** 是它不測 AI 品質、不測人類品質，只測「當 AI 出錯時人的 override 意願」——結果是**人幾乎沒有 override 意願，反而把 AI 的錯誤內化成自己的信心來源**。共同作者 Capraro 原話「recognition of the limits of our own knowledge」被拿走了——AI 建議把「認識自己知識邊界」這條認知能力抹平。

**背後怎麼運作**

這條研究背後的心理學機制是**「anchoring bias」在 AI 建議情境的極端強化版**——傳統 anchoring 是「先看到的數字影響後續判斷」，AI 建議是「權威來源的完整答案影響後續判斷」，強度差一個量級。過去 30 年 human-computer interaction 領域對「automation bias」有大量研究（例如飛行員過度依賴 autopilot、醫生過度依賴 CAD 診斷輔助），但過去研究都在**「AI 大部分時候是對的、偶爾錯」**的情境；這條 preprint 的獨特處是**設計成「AI 幾乎全錯」，看人到底能不能發現**——結果**發現不了**。這條實驗設計的三個技術細節值得留意：**(1) 為什麼選視覺細節回憶**——因為這是「使用者自己看過電影、應該有直覺記憶」的題型，如果連自己記憶都能被 AI 蓋掉，那 AI 對「使用者沒直覺記憶的題型」（工作、程式碼、決策）影響會更嚴重。**(2) 為什麼加金錢誘因也救不回**——因為問題不是「使用者懶得思考」，是「AI 的存在改變了使用者對問題的認知框架」——加錢讓使用者更用力思考，但思考方向仍被 AI 建議定型。**(3) 為什麼「我不知道」意願崩到 3%**——因為 AI 提供了一個答案（不管對錯），使用者現在有一個可以 anchor 的答案、不需要面對「不知道」的認知不適。**這條動作跟 7/17 Pydantic「Human-in-the-loop is tired」是同一條認知線的雙側證據**——Pydantic 那篇從**工程師視角**講「AI 讓 satisfying 部分自動化、exhausting supervision 部分留給人」，這篇 preprint 從**認知科學視角**講「AI 存在本身改變人的判斷結構、supervision 這條認知能力被鈍化」。**兩篇合起來的結論是**：「human-in-the-loop」這條設計不能靠讓人 review AI 產出就成立——**人 review 的品質會被 AI 的存在污染**，你需要**制度性 override 誘因**（例如強制 blind review、獨立 second opinion、金錢誘因加大到能突破 anchoring）才能保留 review 品質。

**這改變了什麼**

以前你設計 AI-assisted workflow 是「AI 產出 → 人 review → decision」——這條流程假設「人 review 是 unbiased second opinion」。今天起這個假設**被實驗證明不成立**——**人 review 已經被 AI 建議 anchored、不是 unbiased**。這條動作對 **Nexus PR review pipeline** 直接可用——**過去設計「AI 找 bug → 人 review → decide」這條流程該加一層「blind review」——先讓另一個獨立 subagent（或另一個獨立的人）在不看 AI 建議的情況下獨立走過一遍、再跟 AI 建議 diff、看兩者不一致的地方**。這條 blind review 是**唯一能繞開 anchoring bias 的設計 pattern**。這條研究也對 **Claude_auto SKILL.md** 有一個更深啟示——**你 SKILL.md Step 5 自我優化這步是「Claude 讀自己上個 session 的 output 決定下次怎麼改」，這條 loop 有嚴重 anchoring 風險**——Claude 讀自己昨天寫的 journal、幾乎不可能質疑昨天的判斷、只會朝昨天的方向 refinement。**該加一個 blind checkpoint**——例如每週一次讓 Claude 在不讀 session-log 的情況下獨立重新評估今天的候選文章，跟 session-log 的判斷 diff。這條研究對 **Nexus 對外採購 deck第七維中立性「決策層 deterministic pipeline」** 補一個科學論證——**「LLM-mediated decision-making 不只是 fallback risk（vendor 撞牆），還有 cognitive risk（人 review 品質被污染）」**——這條認知搭 7/17 Salesforce Agentforce 認錯、7/17 Pydantic Human-in-the-loop is tired、v2.1.215 Anthropic 退回顯式呼叫、今天 AI advice study，是 2026-Q3 產業對「AI 全自動」祛魅的第五塊拼圖。**Capraro 那句「recognition of the limits of our own knowledge」** 對 Henry 個人的職涯發展也有直接參考——**你身為前端架構師、對 Nexus 每個技術決策的信心來源該有兩條**：**(a) 自己實作驗證過**、**(b) 明確承認「這條我沒實作過、需要研究」**——不要讓 AI 建議把「不知道」這條認知能力鈍化。
