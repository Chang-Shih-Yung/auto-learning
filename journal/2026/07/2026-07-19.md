# 2026-07-19 學習日誌

週日今天三條線把「個人開發者怎麼安全放養一台 AI agent 到自己家的機器上」這件事推進一大步——**ykdojo 的「Claude Controls Mac」設定指南**（HN 179 點）用一份 step-by-step 手冊示範怎麼把家裡多的那台 Mac 改造成 Claude Code 專用執行機（SSH + tmux LaunchAgent + `pmset` 全套 no-sleep + fresh local user 隔離）；**charlesazam 的 Fable 5 vs GPT-5.6 Sol 在 NP-Hard 問題上 /goal 對照實驗**（HN 214 點）用 3×2×2 共 12 次 30 分鐘實跑量出 `/goal` 這條 feature 的真實影響——**兩個模型都因為 /goal 把 mean 弄差**（Fable 5 32,386 → 33,145、Sol 34,261 → 35,129），但 Fable 5 的 range 是 Sol 的 6 分之 1，consistency 遠贏 aggression；**Transcribe.cpp**（handy-computer/transcribe.cpp、249 stars、v0.1.0）把 ggml 系的 speech-to-text 推到 16 個 ASR 家族 60+ 模型的統一 inference layer，Vulkan / Metal / CUDA / TinyBLAS 全支援，在 RK3566 ARM SoC 上比 realtime 快、只吃 a handful of watts。三件事看起來各切各的——一件是**執行環境**、一件是**收斂條件**、一件是**離線推理層**——但同一個大方向被三個角度切開：**「AI agent 從雲端 vendor 的 hosted 服務往你自己的機器上搬」這條路，2026-Q3 的三個必要基礎設施今天各補一塊**。

## Claude Controls Mac——把家裡那台備用 Mac 改造成 Claude Code 24 小時執行機（SSH + tmux LaunchAgent + fresh local user 隔離 + computer use over SSH）

**你能做什麼**

如果你像 Henry 一樣有 Claude_auto 這種每天排程跑的 AI 任務，或者手邊有台 M1/M2 時代退役的 MacBook 想給它一個新用途，今天 ykdojo 這份 step-by-step 指南（HN 179 點、133 留言）給了一份完整可跑的手冊——**兩台 Mac 用同一個 Wi-Fi，一台當「source」（你日常主機），一台當「target」（Claude Code 專用執行機）**。整套 setup 建議分七層做：**(1)** target Mac 建全新 local user、跳過 Apple ID 登入、給 admin 權限（原則是「這台機器上沒有你的個人資料、iCloud 也不會同步下來，Claude Code 就算開 `--dangerously-skip-permissions` 也炸不到你」）。**(2)** SSH 設好——`sudo systemsetup -setremotelogin on` 開 remote login、對 target 帳號設 passwordless sudo、source 端 `ssh-copy-id` 對過去讓 key auth 生效。**(3)** 用 `pmset` 四條命令關掉這台 target Mac 所有 sleep 行為：`sudo pmset -c sleep 0`（接電時不 sleep）、`sudo pmset -c disablesleep 1`（clamshell 蓋起來也不 sleep）、`sudo pmset -c displaysleep 0`（螢幕不休眠）、`defaults -currentHost write com.apple.screensaver idleTime 0`（不進 screensaver）——讓這台機器變成一台**顯示器蓋起來、Wi-Fi 常開、24 小時聽 SSH 的無人值守伺服器**。**(4)** target Mac 上裝 Claude Code（走 `curl -fsSL https://claude.ai/install.sh | bash -s -- <version>`），且 PATH 要寫進 `~/.zshenv`（不是 `~/.zshrc`）——因為 SSH non-login shell 只讀前者，這條坑很多人踩過。**(5)** 如果你要用 Claude 的 computer use（螢幕截圖、滑鼠鍵盤自動化），這步是整份指南最有價值的部分：**跑 setup script 裝一個 persistent tmux LaunchAgent，讓 tmux server 掛在 GUI login session 裡；之後你 SSH 進來 attach 這個 tmux server，繼承 GUI 的 display privileges 就能截圖跟輸入**。這個 workaround 繞開了「macOS 要求 Screen Recording 跟 Accessibility 權限只能在 GUI System Settings 裡按核」這條限制——因為權限一次授給 tmux binary，之後 SSH 進來 attach 的 process 全部繼承。**(6)** clipboard sync（`clip.sh` 腳本，`clip send` 從 source 推、`clip get` 從 target 拉，圖跟文字都支援）。**(7)** 遠端存取（Tailscale 讓你出門也能從手機摸這台機器、Chrome extension 讓 target 上的 Chrome 也能被 Claude 控制）。作者對 use case 給了三條實在的答案：**(a)** 想跑但不敢在主機跑的 research / experiment（例如任何 `rm -rf` 有機會發生的腳本）、**(b)** 手機上想操作 Claude Code 時走 SSH 進這台備用機比在 iOS 官方 app 順、**(c)** 需要跑 Mac 專屬 GUI app（例如 Xcode、Photoshop）時透過 computer use 遙控。

**背後怎麼運作**

這份指南的關鍵設計決策是**「把 AI agent 隔離到一個沒有你個人身分的 macOS 使用者上」**——這條隔離不靠 VM、不靠 container、不靠 firejail，只靠 macOS 原生的 multi-user 帳號體系。它的成本模型很符合家庭用戶：不用學 Docker、不用學 systemd、不用改任何 network topology，就是**一個乾淨帳號 + SSH + tmux + pmset**四件事。tmux LaunchAgent 這個 trick 尤其巧妙——**macOS 的權限模型把「能截圖」跟「能控制滑鼠鍵盤」這兩件事綁在 GUI login session 的 process tree 上，SSH 進來的 process 因為不屬於 GUI session，預設沒有這些權限**。作者的解法是讓 tmux server 由 launchd 在使用者登入時就啟動、常駐在 GUI session 裡（tmux binary 本身在 System Settings 裡授過 Screen Recording + Accessibility），之後 SSH session attach 到這個 tmux server 就等於「把你 SSH 進來的 shell 塞進 GUI session 的權限樹裡」，Claude Code 從這個 shell 呼叫 screencapture、cliclick、AppleScript 等命令就能拿到 display access。這個設計本質上是**把 macOS「GUI session vs SSH session 權限分離」這條 sandbox 的邊界，用 tmux 這個 shared IPC daemon 給打通**——嚴格說起來這是繞過 Apple 原本的安全設計，但因為 tmux binary 是使用者主動安裝並主動授權，Apple 的門檻是「防止未授權 process 拿到權限」而不是「防止使用者主動打洞」，所以這條路合規。這條 workaround 也解釋了為什麼作者強調 target Mac 要用 fresh local user——**因為 tmux 打洞打到的是這個帳號的 GUI session，如果帳號裡有你的 iCloud、Photos、Keychain，那 Claude Code 就能透過 screencapture 看到這些**。乾淨帳號等於把「打洞後能看到的資料」壓到零。

**這改變了什麼**

以前你想放養一台 24 小時跑 AI agent 的機器，選項是：**(a)** 雲端 VM（付費、你的 API key 存別人機器上、latency 對某些 workflow 太慢）、**(b)** Docker container 跑在主機（跟主機共用 kernel、`--dangerously-skip-permissions` 一開就穿）、**(c)** 買一台 Raspberry Pi 或 mini PC（設定新 OS 麻煩、macOS 專屬工具不能用）——三個選項各有明顯缺點。今天起第四條路成立：**「家裡那台你原本已經有的備用 Mac + 一份 90 分鐘的 setup 指南」**。這條動作對兩類人是直接可用：**第一類是 Henry 這種有 Claude_auto 排程的個人開發者**——目前 Claude_auto 每天早上跑在主機、跟你日常開發的 process 共享權限，這個模式的問題是「排程萬一出錯或遇到 injection、影響會擴到你主機所有檔案」；把這條排程搬到備用 Mac 之後，最壞情況就是 target Mac 上那個 fresh user 被搞爛（大不了重灌那個 user），主機零風險。**第二類是任何想試 Claude 的 computer use 但不敢對自己日常 desktop 用的人**——computer use 本質是「AI 看你螢幕、動你滑鼠鍵盤」，這件事對日常主機做很嚇人，對一台專用 Mac 做很合理。這條路徑跟 7/14 Clawk（Apple Virtualization.framework 起 VM）、7/17 LM Studio Bionic（獨立 app 專職 agent harness）是同一條演化：**AI agent 的執行環境從「跟你主機共享」全面往「跟你主機隔離」搬**，只是每條路徑選的隔離 primitive 不同——Clawk 選 VM、Bionic 選 process 隔離、ykdojo 選 physical machine + fresh user 隔離。**physical machine 這條路的獨到價值**是**它是零學習成本的「終極隔離」**——不用 hypervisor、不用 namespace、不用 network policy，就是一台實體的第二台電腦，任何有兩台 Mac 的人 90 分鐘就能設好。這條「用你原本已有的硬體 + 一份腳本」的路徑跟 vendor 那條「幫你 host 一個更貴更複雜的雲端 sandbox」的路徑是完全不同的成本結構——**vendor 走的是「你付月費、隔離複雜度我扛」，ykdojo 這條走的是「你已經有硬體、複雜度靠腳本壓到最小」**。這條動作對 Anthropic 產品線也有反饋：**如果 Claude Code 官方 SDK 未來要加「second machine mode」（例如 `claude connect ssh://target-mac` 一鍵套用整份 ykdojo 指南）會有明確市場需求**。

## Fable 5 vs GPT-5.6 Sol 在 NP-Hard 問題上的 /goal 對照實驗——`/goal` 這條 feature 在兩個模型上都把 mean 弄差，但 Fable 5 的 range 是 Sol 的 6 分之 1

**你能做什麼**

如果你在 Claude Code 或 Codex 用過 `/goal` 這條命令（把「什麼算完成」變成一級設定，agent 會 loop 到滿足條件才停），charlesazam 這篇 blog（HN 214 點、107 留言）給了第一份**跨模型跨平台的量化對照實驗**——用 KIRO 這個 NP-Hard 光纖網路設計問題（連接分配點跟終端點、用 loop 跟 chain 鋪 cable、目標最小化總長度、Paris 一座城市搜索空間下限就 **10^1223** 種配置）當 benchmark，測 **Claude Fable 5** 跟 **GPT-5.6 Sol** 這兩個模型在**「plain mode」跟「/goal mode」兩種設定 × 3 次獨立 30 分鐘 run**——共 12 次實跑。結果非常反直覺：

| 模型 | Plain mean | /goal mean | Best score | Range |
|------|-----------|-----------|-----------|-------|
| Fable 5 | 32,386 | 33,145 | 31,934 | 319 |
| GPT-5.6 Sol | 34,261 | 35,129 | 32,703 | 1,958 |

（分數越低越好，代表 cable 總長度越短。）**兩個模型在開了 /goal 之後 mean 都變差**（Fable 5 +759、Sol +868），儘管 `/goal` 在 6 次個別 trial 裡贏了 4 次。作者的解讀是「**/goal 讓好決策更持久、也讓壞決策更持久**」——一旦 agent 進了一條有 promise 的搜索路徑，`/goal` 會鼓勵它 grind 下去而不切換；但一旦進了不好的路徑，`/goal` 也讓它花更多算力沉沒在那條路上，downside risk 被放大。**跨平台差異**：兩個平台實作 `/goal` 的方式不同——**Claude Code 用一個獨立的 evaluator model（預設 Haiku）判定完成、且 evaluator 只看 conversation transcript**（意思是 background subagent、worktree 裡跑的 test、side effect 全部 evaluator 看不到，只看模型自己在 chat 裡寫了什麼）；**Codex 把 goal 當 persistent thread state**，配專用工具讓正在跑的 model 自評完成度（同一個模型當運行者跟評判者、狀態跨 turn 保留）。而**consistency 差異**是這篇 blog 最實用的數字：**Fable 5 三次 run 的 range 只有 319 分，Sol 的 range 是 1,958 分——差 6 倍**。同樣 30 分鐘、同樣 max reasoning，Fable 5 給你的是「可預測的中等表現」，Sol 給你的是「時好時壞的高變異」。

**背後怎麼運作**

`/goal` 這條 feature 的哲學來自「LLM agent 最大的痛點是不知道什麼時候該停」——傳統 prompt 跑完就 return，agent 會在還沒真正解完問題時就宣告完成、或反過來 loop 到超出預算才被 timeout 砍掉。`/goal` 的解法是**把「停止條件」從隱含的 prompt 慣例升成一級設定**——「你要跑到 all tests green AND commit pushed AND deploy verified 才算完」。這條設計在**線性任務**上很好用（例如 CI/CD 流程、code review pass 條件），但這篇 blog 把它推到**組合最佳化搜索**這個場景，暴露了兩個結構性問題：**第一個問題是「stop 條件在探索型問題上很難定義」**——KIRO 的最佳解是未知的（10^1223 空間內），你只能定義「至少 X 分」這種相對條件，但 X 太保守你 agent 一下就滿足停下、X 太積極 agent 永遠達不到就一直 grind。作者實驗中用的是「盡量小」這種開放條件，這條會讓 `/goal` 變成「不到 budget 耗盡不停」的無限迴圈，跟不加 `/goal` 的差別只在「決策稠密度」。**第二個問題是 Claude Code 跟 Codex 對 `/goal` 的實作哲學徹底不同**——Claude Code 走**「evaluator 只看 transcript」**這條保守路線，是為了避免 evaluator 被 side effect 誤導（例如 test suite 恰好過但 agent 其實改壞了東西）；但這條也意味著 Claude Code 的 `/goal` 完全看模型「說了什麼」不看「做了什麼」，如果 agent 在 chat 裡描述得再天花亂墜、實際 output 很爛，evaluator 也給過。Codex 反過來，evaluator 是正在跑的 model 自己，能看到自己所有 side effect，但這條也意味著**「自己判自己作業」**——一旦模型認定完成就完成、缺乏外部 check。**consistency 差異**（Fable 5 range 319 vs Sol range 1,958）反映的是兩個模型 sampling 分佈的形狀——Fable 5 訓練時明顯往「窄變異」方向調過，這條特性在**排程任務跟企業 workflow** 上是絕對優勢，因為你排程任務出去要能預測結果會落在什麼範圍；Sol 是「high variance high ceiling」，best score 32,703 比 Fable 5 的 31,934 差、但單次 run 有機會爆出好結果。

**這改變了什麼**

以前你用 `/goal` 這條 feature 是憑感覺——「我加了 /goal，agent 應該更會收斂」，charlesazam 這篇實驗給了第一份**真實量化證據**顯示 `/goal` 不是萬能藥：**在探索型 / 組合最佳化任務上，`/goal` 可能讓 mean 變差**。這對 Claude_auto 這種每天排程的 workflow 有直接影響——**排程任務的核心價值是「可預測」不是「有時候特別好」**，這條實驗告訴你在排程情境選 Fable 5（range 小、可預測）比選 Sol（range 大、變異高）更符合排程哲學。**跨平台 `/goal` 實作差異**也第一次被寫清楚——**Claude Code 走 transcript-only evaluator，你要用 `/goal` 就得確保 agent 把重要 side effect 寫進 chat 讓 evaluator 看得到**（例如強制 agent 在跑完 test 後把結果 paste 進 chat 而不是只在 background 執行）；Codex 走 self-evaluator，你要用 `/goal` 就得多加一層外部 check（例如 CI 跑完再驗一次）以避免「模型自己說完成就完成」。這條認知對 Nexus 這種未來要對客戶提供 AI-assisted 元件生成的產品也有直接應用——**如果 Nexus 內部用 Claude Code 排程跑元件更新，`/goal` 條件必須顯式包含「lint pass AND type check pass AND visual regression < X%」等看得到的 side effect**（在 chat 裡把這些數字寫出來），不能只靠 agent 說「done」。搭 7/14 antirez「Control Ideas Not Code」的哲學看：**`/goal` 是 vendor 對「什麼是完成」這條 idea 的第一次 first-class 實作，但 charlesazam 這篇證明 idea 的實作細節（evaluator 看什麼、怎麼判定完成）比 idea 本身更決定結果**。這條實驗給 vendor 也有反饋——**Claude Code 的 evaluator 應該加一個 mode 讓使用者選「evaluator 也能看 file diff / test output / build artifact」**，只看 transcript 對複雜任務太保守。

## Transcribe.cpp——ggml 系 speech-to-text 統一 inference layer，16 個 ASR 家族 60+ 模型 Vulkan / Metal / CUDA / TinyBLAS 全支援、RK3566 embedded ARM 上比 realtime 快

**你能做什麼**

如果你關注 local ASR（speech-to-text，把語音轉文字）這條技術線，handy-computer/transcribe.cpp（MIT license、v0.1.0、GitHub 249 stars、HN 57 點）給了一個新的統一 inference layer——**支援 16 個 ASR 模型家族、60+ 個具體模型**（Whisper 系列、Moonshine、Distil-Whisper、Nvidia Parakeet、Faster-Whisper 等都在支援名單），共用同一套 ggml runtime、GPU acceleration 走 **Vulkan（跨平台 GPU）+ Metal（Mac）+ CUDA（Nvidia）+ TinyBLAS（無 GPU fallback）** 四條後端。作者對 v0.1.0 的定位是「**a trustworthy, embeddable transcription engine**」——它是他們自家跨平台 app「Handy」的底層 engine 抽出來開源。與 whisper.cpp 相比的差異：**(a) 支援模型家族更多**（whisper.cpp 只支援 Whisper 系）、**(b) numerically validated**（每個模型都有跑 WER / Word Error Rate 測試確認 output 跟 reference implementation 一致，不是「跑得動就好」）、**(c) 支援 streaming 跟 batch 兩種模式**、**(d) 官方維護 Python / JS-TypeScript / Rust / ObjC-Swift 四個 language binding**。硬體 spec 面的具體數字：作者強調在 **RK3566**（一顆 ARM Cortex-A55 四核 SoC，常見於單板電腦 / 嵌入式裝置）上「models run faster than real time」且「a handful of watts」——意思是**這條 pipeline 能塞進 Raspberry Pi 級的低功耗裝置做 24/7 always-on 語音辨識**，不需要 GPU、不需要雲端。

**背後怎麼運作**

ggml 是 llama.cpp 作者 Georgi Gerganov 那條「把 transformer inference 從 Python + PyTorch 搬到 pure C/C++ + 手寫 SIMD」路線的 tensor library，過去這條線最有名的成果是 llama.cpp（LLM inference）跟 whisper.cpp（ASR inference）。transcribe.cpp 這條新專案的關鍵設計決策是**「把 whisper.cpp 那條路徑推廣到不只 Whisper」**——過去每個 ASR 家族（Moonshine、Parakeet、Distil-Whisper）都要自己寫一份 C++ port 才能離開 Python，這條路線碎片化嚴重、每個 port 品質不一、GPU backend 支援也差異大。transcribe.cpp 走的是**「用 ggml 作為共同 tensor layer、模型架構寫成 config-driven 而不是 hardcoded」**——這條抽象讓新增支援一個 ASR 家族的成本從「重寫一份 C++ implementation」降到「寫 model architecture 定義 + 準備 weight 轉換腳本」。**numerical validation 這條實踐**特別值得注意——過去 llama.cpp / whisper.cpp 這條線最常被詬病的是「output 跟 reference 有偏移但沒人量」，transcribe.cpp 對每個支援模型跑完整 WER 測試對比 reference implementation，確保 quantization / SIMD 優化沒有偷偷降精度。GPU backend 走 Vulkan / Metal / CUDA / TinyBLAS 四條路線的設計意涵是**「不綁 Nvidia 特定生態」**——Vulkan 讓 AMD / Intel GPU 也能跑、Metal 讓 M 系 Mac 原生跑、TinyBLAS 保底無 GPU 環境也不會直接 crash。RK3566 這條硬體宣稱是這條 library 最有價值的宣告——**如果一個 ASR pipeline 能在 £30 的單板電腦上比 realtime 快，那所有邊緣裝置（家用智慧音箱、車機、工廠現場 handheld）都能塞下 always-on 本地語音辨識**，不需要把音訊 stream 到雲端。

**這改變了什麼**

過去你要在 app 裡加語音轉文字這件事，選項是：**(a)** 用雲端 API（Google Speech-to-Text、AssemblyAI、OpenAI Whisper API）——付費、latency、資料出裝置、需要網路；**(b)** 用 whisper.cpp 或 faster-whisper——只支援 Whisper 家族一種模型、GPU backend 常常只支援某一條路徑；**(c)** 用各家原生 SDK（Moonshine、Parakeet 等）——散落在不同 codebase、每家品質不一。今天起第四條路是**「一個 library 一次搞定 16 個模型家族、四條 GPU backend、四個語言 binding、都經過 WER 驗證」**。這條動作對兩類人是直接可用：**第一類是做 desktop / mobile app 想加語音功能的獨立開發者**——不用綁定特定模型家族、可以隨時換模型（例如上市時用 Whisper Large、日後 Moonshine 出新版就換過去）而 API 不變。**第二類是做嵌入式 / 邊緣裝置的硬體開發者**——RK3566 級的低功耗 ARM SoC 能跑 real-time ASR 意味著**智慧音箱、車機、工廠 handheld 都能塞下本地語音辨識**，不用把音訊上傳雲端。這條路徑跟 7/15 Bonsai 27B（27B 模型 1-bit 量化塞 iPhone 17 Pro）、7/17 LM Studio Bionic（桌面級 open-weights agent harness）是同一條演化——**「AI inference 從雲端 vendor 全面往本地端搬」，只是每條路徑選的模態不同**：Bonsai 選 LLM、Bionic 選 agent harness、transcribe.cpp 選 ASR。**ASR 這條模態的獨到價值**是**它是即時互動的入口**——語音辨識延遲從「上傳雲端來回 300-800ms」壓到「本地跑 < 50ms」對 UX 差異巨大（使用者感受從「等一下」變「即時反應」）。這條 library v0.1.0 才剛開始，未來一年若能持續累積模型支援、把 v1.0 stable API 定下來、加上更多 language binding，會成為 whisper.cpp 之後**下一代 local ASR 的事實標準底層**。

## 今日總結

今天三條線同時把「AI agent 往你自己機器上搬」這條 2026-Q3 主線推進三個必要基礎設施：

1. **執行環境**（ykdojo Claude Controls Mac）——**physical machine 隔離**是零學習成本的終極 sandbox，你家裡那台備用 Mac + 90 分鐘 setup 腳本就能拿到「主機零風險」；跟 7/14 Clawk VM 隔離、7/17 LM Studio Bionic process 隔離同一條演化，但走的是最平民的路。
2. **收斂條件**（charlesazam /goal 對照實驗）——`/goal` 這條 feature 用 12 次 30 分鐘實跑證明**在探索型任務上會把 mean 弄差**（Fable 5 32,386 → 33,145、Sol 34,261 → 35,129），且**Fable 5 range 是 Sol 的 6 分之 1**（319 vs 1,958）——排程情境該預設 Fable 5，且 `/goal` 條件必須顯式包含可觀察 side effect（不能只看模型說了什麼）。
3. **離線推理層**（Transcribe.cpp）——ggml 系從 whisper.cpp 進到**16 家族 60+ 模型統一 inference layer**，RK3566 embedded ARM 上比 realtime 快、a handful of watts；跟 7/15 Bonsai 27B、7/17 LM Studio Bionic 同一條「AI inference 從雲端往本地搬」演化，但補的是 ASR 這條入口模態。

三條線合起來的洞察是：**過去 6 個月「AI agent 從 vendor cloud 往你機器上搬」這條大方向的三個必要基礎設施（隔離的執行環境、可預測的收斂條件、離線的推理層）今天各補一塊——每一塊都可以獨立實作，但三塊拼起來才能構成一個真正「vendor-independent」的 AI agent 部署形態**。這條 pattern 對 Henry 有直接應用：**(a)** Claude_auto 搬進備用 Mac（隔離）、**(b)** SKILL.md 排程 model 預設 Fable 5、若加 `/goal` 就顯式包含 lint / commit / test 三條可觀察 signal（收斂）、**(c)** 未來 Nexus 加語音輸入元件觀察 transcribe.cpp 到 v1.0 stable 後整合（推理）——三條動作在時間軸上不衝突，第一條 90 分鐘做完、第二條下週 SKILL.md audit 時做、第三條半年到一年後評估。
