## Claude Code v2.1.196 藏 steganographic marker——你的 date 字串裡的 apostrophe + 分隔符是給 Anthropic 後端讀的路由碼

你在 Claude Code v2.1.196 裡看到系統提示詞底下有一行 `Today's date is 2026-06-30.` 看似平淡，其實這行字**藏了 4 bit 給後端讀的路由標記**。thereallo.dev 6/30 blog（HN 頭條 1429 點 409 留言）從 minified bundle 挖出 `Vla(date)` 函式，兩個標記軸同時作用：**(1) timezone 軸**——若你的系統時區是 `Asia/Shanghai` 或 `Asia/Urumqi`，日期分隔符從 `-` 翻 `/`（`2026-06-30` → `2026/06/30`）；**(2) hostname 軸**——若你的 `ANTHROPIC_BASE_URL` 環境變數指向已解碼的域名列表（`baidu.com`/`alibaba-inc.com`/`bytedance.net`/`moonshot.ai`/`anyrouter.top`/`claude-code-hub.app`/`claude-opus.top`/`openclaude.me`/`proxyai.com`/`yunwu.ai`/`zenmux.ai` 等 Chinese corporate + AI + reseller 域名）或 URL 內含 lab keyword（`deepseek`/`moonshot`/`minimax`/`xaminim`/`zhipu`/`bigmodel`/`baichuan`/`stepfun`/`01ai`/`dashscope`/`volces`），apostrophe 從 ASCII `'`（U+0027）翻三種不同 Unicode 變體：**known domain** → `'`（U+2019 right single quotation mark）、**lab keyword** → `ʼ`（U+02BC modifier letter apostrophe）、**兩者都有** → `ʹ`（U+02B9 modifier letter prime）。作者本機時區 Asia/Hong_Kong + `ANTHROPIC_BASE_URL` unset 條件不觸發，binary 是 Anthropic 官方簽名（TeamIdentifier `Q6L2SF6YDW`、SHA256 `6fc6e61a…`）。域名跟 keyword 列表用 base64 儲存 + XOR 解碼（key `91`）二層混淆。

設計核心：**訊號隱藏在使用者跟 model 都不會注意的位元組裡**，走 in-band watermark 路線而非 out-of-band header。這是典型 anti-distillation / anti-reseller 手段——如果第三方代理商拿 Claude Code 客戶端接自己的 API endpoint 對外賣 Claude 存取（reseller），或用同一個 harness 蒸餾對話產本地 model 訓練資料（distillation），Anthropic 後端只要看 system prompt 裡的 apostrophe 是不是 U+2019/U+02BC/U+02B9 就能標記「這條 request 來自可疑客戶端」——即使流量透過 proxy 轉，marker 已經 embedded 在 prompt 內容裡跑不掉。走 in-band 有兩個必要條件：**(1) marker 必須視覺上不可察**（三種 Unicode 變體在 monospace font 幾乎看不出來）、**(2) marker 必須跟合理內容耦合**（放在日期字串符合「系統會塞當前時間」預期，不會被 diff review 抓出來）。二層混淆（base64 + XOR key 91）是防被靜態掃描工具立刻辨識出敏感字串列表，反編譯者要多花一步才能列出來。同時只在 `ANTHROPIC_BASE_URL` 指向非 Anthropic host 時觸發——直連官方 API 不打 marker，是「只針對可疑路徑做 fingerprint」的精準策略。

以前 Henry 跑 Claude_auto SKILL.md `requiredMinimumVersion` 追每一版 Claude Code 只從 changelog release notes 看 feature/bugfix，**假設 minified bundle 內容跟 release notes 是等價的**——今天 thereallo 用 5 段 JS 反編譯戳破這個假設：**binary 可能有 release notes 沒提的行為**，且該行為會改變送給 model 跟後端的內容。對 Henry 三件事：**(1) Nexus 賣給歐洲客戶時的合規論述**——過去 6/25 客戶採購 deck 論「不鎖 vision agent provider」+ 6/29 補「不鎖 security review provider」，今天要補第三維「client binary transparency」，因為即使客戶自架 GLM-5.2 走 `ANTHROPIC_BASE_URL` 指向自家 endpoint，Claude Code 客戶端仍會在 prompt 內加 marker——這對「AI 內容稽核鏈完整」承諾是實質破口；**(2) Claude_auto SKILL.md 檢查條**加一行「session 開始檢查 `env | grep ANTHROPIC_BASE_URL`，若指向非 `api.anthropic.com` 需在 session log 標注」，把「可能被 marker」這個狀態 first-class 化；**(3) 選 fallback chain 底層**時，理由不只成本/能力/合規三軸，還要加「client binary 是否會替我加 telemetry」第四軸——直連 GLM-5.2 或 Ornith 走它們自己 CLI（不透過 Claude Code）跟走 Claude Code + `ANTHROPIC_BASE_URL` override，兩條路徑同樣是「用 open weights」但 telemetry 表面完全不同。對應 5/3 VS Code Copilot 默默注入 Co-Authored-By trailer 條目「稽核訊號必須由獨立稽核層產生」洞察——今天 thereallo 把這條推到下一層，**執行層自己就是被稽核對象時，稽核訊號必須跳到 wire-level（tcpdump / mitmproxy / diff prompt content vs source）**才可信，client-side flag / env var 都不夠。

## Nano Banana 2 Lite——1k 圖 2.7× 快、角色一致性保留，Figma → Component preview 有了低成本 pre-render 層

你 Nexus 專案改個 OKLCH token 值想預覽對 UI 的影響，過去要跑一輪 Storybook build + Chromatic snapshot 或手動在 Figma 改再 export，今天 Google DeepMind 放出 **Nano Banana 2 Lite**（Gemini image flash-lite），**1k 解析度 image gen 比 Gemini 3.1 Flash Image 快 2.7×**，主打 character consistency 保留（同一個 UI mockup 反覆改細節，主體構圖不會漂）。可透過 Google AI Studio / Gemini API / Gemini app / Gemini Enterprise Agent Platform 呼叫，官方稱「approaching full Nano Banana 2 quality」但沒公開具體 side-by-side benchmark 分數。定價未公開具體數字但描述為「a fraction of the cost of heavier production models」。HN 6/30 條目 308 點 120 留言。限制：圖內文字準確度仍不完美、複雜編輯跟 advanced blending 會有 artifact、character consistency 強但不保證。

設計核心：**image gen 從「作品層」翻「工作層」**。過去 Midjourney / Stable Diffusion / 早期 Nano Banana 定位是「產一張最終作品」，latency 十幾秒到分鐘級是可以接受的，因為預期 output 是 hero image / marketing asset 級成品。Lite 版本 2.7× 快是不同定位——放進 IDE 內即時 preview loop、放進 Figma plugin 讓 designer 改一個 slider 立刻看變化、放進 CI 讓 PR merge 前跑一輪視覺 regression。character consistency 是 Lite 版本能撐這條路線的關鍵：如果 preview 每次隨機構圖，designer 沒法比對「這次改對還是改錯」——consistency 保留讓 output 從「新作品」翻「同一作品的變體」，才能當工作 loop 內的中間產物。1k 解析度是 pragmatic 折衷——設計預覽不需要 4k、1k 足夠讓 designer 判斷。

以前 Henry 跑 Nexus packages/ui `packages/tokens.json` 改 OKLCH lightness / chroma 值想預覽對 button / card / dialog 三個 component 的視覺影響，要完整跑 `pnpm build` + Storybook + Chromatic snapshot 才看到差異，一輪 5-10 分鐘——今天 Nano Banana 2 Lite 給另一條路：CLI 或 Figma plugin 內把「tokens.json diff + 三個 component base screenshot」餵 Lite model，2.7× 快的 gen speed 意味秒級 preview（實際數字視 Lite 的絕對 latency 而定）。對 Henry 三件事：**(1) Nexus packages/cli 加 `nexus preview <token-key> <value>` 命令**，input = token change + base component screenshots，output = Lite gen 的 mock preview，工程師在 CLI 就能判斷「這個值改動要不要繼續跑完整 Storybook build」；**(2) packages/ui Figma plugin 加 preview mode**，Figma 內拖 OKLCH slider 直接顯示 Lite gen 預覽，取代目前只顯示 CSS 變化的文字面板；**(3) CI/CD pipeline 加輕量 visual sanity check**——PR CI 跑 Lite gen 對比 baseline，差異超過閾值才 trigger 完整 Chromatic run，把「跑 Chromatic」的觸發條件從「每個 PR」翻「Lite 判斷有視覺變化的 PR」，Chromatic quota 消耗會下降。對應 6/26 OpenKnowledge codebase-wiki「agent 撰寫 agent 讀」+ 6/29 Adrafinil「sleep state 跟 agent state 縫成因果鏈」延伸到 design token → visual output 這條 chain 加一層「AI 快速預覽」中間節點。
